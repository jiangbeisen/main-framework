## Step 0 前置：截图内容辅助识别

**仅当上游传入的上下文中包含用户附带的截图时执行；无截图直接跳过，进入 Step 0。**

### 触发条件

- 上游上下文中携带一张或多张 TikTok App 截图（用户提问时直接上传的图片）。
- 用户问题涉及 **"这个页面 / 这里 / 这一栏 / 这个按钮 / 右上角那个 / 底部那排 / 图里的 XX"** 等需要结合截图才能定位的指示性表达；或问题虽未出现指示性表达，但用户明显是在询问截图中所展示的产品模块/功能。

### 动作

1. 调用 `tiktok-screenshot-recognition` skill，将截图作为输入传入。
2. 接收该 skill 返回的结构化结果，关键字段包括：
   - `page`：一级页面 slug（14 类之一或 `unknown`）
   - `page_zh`：对应中文页面名
   - `confidence`：识别置信度
   - `sub_hints.extra_context` / `evidence`：视觉线索描述

### 产出消费

把截图识别结果作为 **视觉上下文补丁** 并入后续 Step 0 的实体/关键词解析：

- 截图识别出的一级页面（如 `foryou` / `shop` / `inbox`）可作为 **产品模块** 实体候选，供 Phase 1 在 [主框架规范 one page] 中定位时参考。
- 若用户原问题里的关键词指代不清（"这个页面"、"这一栏"），优先用截图识别出的页面名和元素线索把关键词补全，再进入 Phase 1。
- 若截图识别返回 `unknown`（截图不属于 14 类一级页面、非 TikTok 界面、或是二级页面/弹窗），**不得**把猜测的页面名作为实体候选；此时继续按原问题文本走 Step 0，必要时在结果中说明"根据截图无法定位具体页面"。

### 约束

- **截图识别结果不是最终答案**，仅用于补充视觉上下文，后续仍必须走完整的 Step 0 → 子意图判定 → 权威文档定位流程。
- **禁止** 在未调用 tiktok-screenshot-recognition 的前提下，基于自己对截图的直觉描述开展实体解析。
- **禁止** 把截图识别的 `unknown` 结果当作有效实体候选，或据此强行套用某个产品模块。

## Step 0：实体关键词权威解析

进入本 skill 后，**在判定子意图之前**，先用上游传入的实体关键词做一次权威信息预查找，消歧义并富化上下文。

若 **Step 0 前置（截图辅助识别）** 已产出一级页面 slug 或元素线索，本步骤的输入应同时包含**原始实体关键词 + 截图识别补丁**。当用户问题里的指示性表达（"这个页面"等）与截图识别结果可映射时，以截图识别结果替代/补全原始关键词再进入 Phase 1。

### Phase 1：权威索引预定位

根据主实体类型，在对应的权威文档**索引层**做快速定位（不深入读全文）：

| 实体类型 | 预定位动作 | 产出 |
|---------|-----------|------|
| **产品模块** | 在 [主框架规范 one page] 中搜索关键词 | 匹配的页面/容器名称 + 规范文档链接 + 层级（Page/Container/未命中） |
| **业务方向** | 在找人地图目录/标题层搜索关键词 | 匹配的方向条目 + 所属产品域 |
| **专项** | 飞书搜索标题含关键词的项目文档 | 匹配的文档链接 |
| **需求** | 在 [主架构评审需求登记表] 中搜索关键词 | 匹配的评审记录行 |
| **流程** | 在 [主框架规范 one page]「产品流程 // Process」section 索引层定位 | 匹配的流程条目 + 对应流程规范文档链接 |
| **指标** | 在 [TikTok 核心指标] 中按指标名搜索（`sheets +find`） | 匹配的指标行 + 所在 sheet/cell 坐标 |
| **组织事务/其他** | 跳过（暂未开发） | 直接返回"未解析" |

**团队 onboarding 文档检索约束（强制执行）**：当用户问的是某个团队（尤其是主架构 / Product Infrastructure）的 onboarding / 新人入职 / 新人文档时，只有当搜索结果的**标题**同时包含“团队名线索”与“onboarding / 新人入职 / 新人文档”等 onboarding 信息，才可判定为可参考来源。仅命中泛 onboarding、通用入职、其他团队 landing 文档，或正文里偶然提到 onboarding，但标题未体现团队归属的，一律不得作为该团队 onboarding 的回答依据。

**约束**：Phase 1 只做索引级查找，严格遵守窄检索协议，不扩词、不深入读全文。

### Phase 2：解析验证

基于 Phase 1 的结果，验证上游分类：

1. **实体类型验证** — Phase 1 的匹配结果是否与上游实体类型一致。例：上游标"业务方向"但 one page 命中了同名容器 → 可能实际是产品模块
2. **层级细化**（产品模块专用） — 关键词在 one page 精准命中 → Page 或 Container；关键词是某容器下的具体场景/卡片/弹窗 → Feature/Instance
3. **产品域验证** — 查找过程中暴露的产品域归属是否与上游一致
4. **术语精确匹配验证** — 检查命中的对象是否与用户原词严格一致；禁止把 hashtag 映射成 tag、topic、label 等词形相近对象
5. **系统边界验证** — 检查命中的对象是否处于与用户相同的系统语境；Mint / 后台 / 配置台 / 运营平台 / C端 / Creator tools / Publisher tools 之间禁止跨系统偷换

若发现偏差，以权威索引的结果为准修正，并记录修正依据；若只能命中“相关对象”而非“同一对象”，则标记为未匹配，不得强行进入后续 owner 提取。

### Phase 2.5：one page 直命中容器校对（产品模块专用）

为避免把 one page 已明确收录的标准页面/容器误判成“待确认对象”或误用实例防呆规则，处理产品模块问题时遵循以下压缩规则：

- 若用户所问对象能在 **[主框架规范 one page]** 的主架构产品规范表中 **直接同名命中**（如头像挂件、异形卡、锚点、系统消息、主页功能区等），默认按 **one page 已明确收录的页面/容器名** 处理，**不得追问“你说的是不是这个容器/模块”**。
- 一旦 direct hit，默认进入“已精准命中 one page”的流程：继续沿 one page 给出的权威规范链接阅读，**禁止停在确认阶段**。
- 只有当用户表述 **比 one page 里的标准名更长、更具体**，即是在标准页面/容器名基础上又加了场景/业务实例修饰（如“购物车锚点”“好友推荐异形卡”“推送授权弹窗”），才允许继续判断是否为 Feature/Instance。
- **禁止反向误用实例防呆规则。** 如果用户问的就是 one page 中直接列出的容器本名，不能因为历史上常见“实例误判”而为了求稳再次向用户确认。
- 做“标准 / 使用规范 / 准入规则 / 定义 / 流程”类查询时，只要 one page direct hit，必须直接继续查对应规范，不得把本可执行的问题退回给用户补充确认。

### Phase 2.6：页面名 + 容器名 收缩命中（产品模块专用）

为避免像“个人页高级功能区”“Inbox 系统消息”这类 **页面名 + 容器名** 组合短语，因为未按原词直命中而被误判为“未命中”，新增以下强制收缩规则：

- 当产品模块关键词由 **页面名/页面别称 + 容器名/容器别称** 组成时，必须先尝试拆分为两段：
  1. 上位页面语境（如“个人页”）
  2. 真正待命中的标准容器名（如“高级功能区”）
- 若拆分后，后半段容器名可在 **[主框架规范 one page]** 中直接命中标准页面/容器，则默认判定为 **已命中该标准容器**，不得因为整串原词未直命中就回退为“未命中”。
- 页面语境的作用是 **辅助缩小范围、确认挂载页面**，不是新的实例修饰词；像“个人页高级功能区”中的“个人页”不能把“高级功能区”打成实例级对象。
- 只有当“页面名 + 容器名”后面还带了更具体的业务修饰（如“个人页高级功能区橱窗卡片”“Inbox 系统消息关注提醒卡”），才继续按 Feature/Instance 判定。
- 若页面语境与容器在 one page 中可形成唯一稳定映射，应把本次解析状态视为 **精准匹配**，并直接沿 one page 对应规范继续阅读。
- **禁止把“页面名 + 容器名”误判为“更长短语 = 业务实例”。** 是否属于实例，取决于容器名后是否还叠加了具体业务对象，而不是前面是否带页面语境。
- **页面别称归一化（强制执行）：** 若页面语境存在中英文别名或历史别称，必须先做页面归一化后再判断挂载关系。例如：**个人页 = Profile**。因此当用户问“个人页高级功能区”时，必须按“Profile 页面下的高级功能区容器”理解；不得因为 one page 或规范里写的是 `Profile` 而把“个人页”误判为未命中页面。
- 当页面归一化后已能确认“该容器挂在该页面之下”，就必须把该问题视为 **标准容器命中**，继续读取该容器规范；**禁止停留在‘原词没命中’这一层拒答。**

### 解析结果及后续影响

| 解析状态 | 后续行为 |
|---------|---------|
| **精准匹配** | 锁定权威来源 → 后续权威文档定位跳过搜索步骤，直接读已定位文档的相关章节 |
| **模糊匹配** | 带着候选列表进入后续流程，在文档中进一步确认 |
| **未匹配** | 回退到常规流程，按实体类型从头执行权威文档定位 |
| **跨系统误命中** | 直接停止当前对象映射；明确当前命中的是另一系统/另一术语下的对象，不得继续拿来回答 owner |
| **跳过（暂未开发）** | 直接走固定口径，不附带额外信息 |

## 子意图判定

完成 Step 0 后，判定用户问题的**子意图**：

| 子意图 | 判定条件 | 典型问法 |
|--------|---------|---------|
| **找owner** | 问题焦点是"谁负责 / 谁来跟进 / 该找谁" | "这个归谁管？""谁负责这块？""应该找谁对接？" |
| **问详细信息** | 问题焦点是现状、进展、具体内容、背景、标准、规则等 | "进展到哪了？""具体方案是什么？""准入标准是什么？""数据是多少？" |

判定后进入对应的处理分支。

## 权威文档定位

无论子意图是"找owner"还是"问详细信息"，都需要定位权威文档。按问题焦点选择一个主实体类型；若同时涉及多个实体，仅保留一个次实体作为辅助。

**与 Step 0 的联动**：若 Step 0 已产出**精准匹配**的解析结果（含权威来源和定位位置），则本步骤直接使用该结果，跳过对应 method 中的搜索/定位步骤，从已锁定的文档/章节继续。若 Step 0 为模糊匹配或未匹配，则按下方常规流程从头执行。

### 已开发的实体路由

#### 1) 业务方向

- 方法名：`direction-method`
- 适用场景：用户询问某业务方向相关信息
- 步骤：
  1. 先识别产品域
  2. 如果问 **TikTok** 产品域
    - 先完整阅读 [TikTok 整体找人地图] 找是否有匹配的业务方向，如果有匹配的方向，定位到对应条目
    - 如果能找到业务，但是不是精准匹配的方向，再从 [主架构找人地图] 中详细寻找精准匹配
  3. 如果问 **TikTok Lite** 产品域
    - **优先完整阅读 [Lite 找人地图]**，按其中的 Modules / POC 映射找精准匹配的方向
    - 如果 Lite 找人地图中没有命中，再完整阅读 [Lite 介绍文档] 的 Lite POC 部分，补充查找对应方向
  4. 如果问 **其他产品域**（TikTok Pro、抖音、CapCut、Lemon8）
    - 当前暂未收录对应产品域的业务方向找人地图，回答：**该产品域的业务方向找人暂未收录，请与对应产品域的主架构人工确认**
  5. 如果仍无匹配的方向，回答：**暂不支持查询未收录方向，或者请与主架构人工确认**

#### 2) 专项

- 方法名：`initiative-method`
- 适用场景：用户询问某专项项目相关信息
- 步骤：
  1. **使用产品域 + 专项的名称，在飞书文档搜索精准匹配的项目文档**，名称通常含有"专项"，"kick off"等表述，找到后阅读专项文档的具体内容
  2. **专项文档时效性强校验（强制执行）：** 在基于专项文档输出任何结论前，先检查该文档的飞书系统元数据 `update_time`。
     - 若最近更新时间**早于当前时间 3 个月以前**，则**不得**继续把该文档作为回答依据。
     - 此时必须继续寻找**其他更近、且可作为权威来源的专项文档**。
     - 若没有其他可用的权威来源，则直接回复：**当前不知道 / 暂不能确认**。
  3. **禁止基于超过 3 个月未更新的专项 kick off / 项目文档回答 owner、POC、最新分工、最新目标、最新进展。** 这类文档最多只能作为历史背景线索，不能作为当前结论依据。

#### 3) 需求

- 方法名：`requirement-method`
- 适用场景：用户询问某个产品需求的评审状态、评审结论等信息
- 步骤：
  1. 从用户问题中提取 **PRD 文档名称**（或需求名称）作为搜索关键词
  2. 在 [主架构评审需求登记表] 中搜索定位到包含该 PRD 的评审记录
  3. ✅ **评审状态优先级规则：仅优先读取「Conclusion / 最终结论」列的状态值作为主结论，其他列状态、备注、标记仅作补充参考，不覆盖主结论列状态**
     - 若标记为 `Finalized` 为已通过评审
     - 若标记为 `On Hold` 为已暂停
  4. 基于命中的评审记录，回答用户问题（如评审状态、评审结论、评审时间等）
  5. 若未搜索到匹配记录，回复：**在主架构评审需求登记表中未找到该需求的评审记录，请确认 PRD 名称是否准确，或与主架构人工确认**

**主架构评审登记表按日期列需求（强制格式）**
- 当用户问的是 **“主架构评审登记表里某一天/某次评审有哪些需求”**，必须优先读取 [主架构评审需求登记表] 当前季度 sheet，按 `Date` 列锁定对应日期，**枚举该日期下的全部需求行**。
- 如用户后续追问 **“只保留 PRD 链接”**，禁止直接输出登记表里的 `Meego link`；必须按如下链路补齐真实 PRD 飞书文档链接：
  1. 从命中行读取 `Meego link`
  2. 从 Meego link 中提取 `project_key/simple_name` 与 `work_item_id`
  3. 到对应 Meego 工作项中读取 `wiki / PRD / 需求文档` 字段
  4. 仅当该字段真实返回飞书 doc/wiki 链接时才输出
- **禁止把 Meego 链接误当成 PRD 文档链接。** 若用户要的是“PRD 链接 / 文档链接”，默认指飞书 doc/wiki 链接，不是 meego story 链接。
- 如果用户进一步要求带上登记表中的行号，必须输出 **sheet 内真实行号**，并按以下固定格式返回：
  - `[行号] + 空格 + PRD链接`
  - 每行一条，不加项目符号、不补标题、不加额外解释
- 当前约定场景：当用户问“主架构评审登记表里某一天的需求”并最终要 PRD 链接时，默认按今天确认过的形式处理：**先按日期枚举需求 → 再经 Meego 反查 PRD 字段 → 最终按 `[行号] + PRD链接` 输出。**

#### 4) 产品模块

- 方法名：`module-method`
- 适用场景：用户询问某模块相关信息
- 步骤：
  1. 先识别产品域
   - **默认按 TikTok**
   - 用户明确说"抖音、剪映、Lite"等才切到对应口径。

  2. 识别模块层级（若 Step 0 已完成层级细化，直接使用解析结果，跳到步骤 3）
    - 先阅读 [主框架规范 one page] 的「原则 // Principles」和「规范 // Guidelines」，了解最新 TikTok 主架构产品原则、产品规范、设计规范、实验规范、产品流程、找人地图等入口
    - 再在 [主框架规范 one page] 里看是否能精准匹配到页面或者容器
    - **若用户关键词是“页面名 + 容器名”组合，必须先做收缩命中：优先识别其中的标准容器名，并用页面语境校验该容器是否挂载在对应页面；若页面存在别称，先做页面归一化（如 个人页 = Profile）再校验；若成立，则按该标准容器 direct hit 处理，不得因整串原词未直命中就判未命中。**
    - 根据结果明确用户询问的对象是：**页面（Page）**、 **容器（Container）**、**功能/业务实例（Feature/Instance）** 里的哪一层。
    - **判断标准要严格：** one page 里能直接命中的，是页面或容器；在该容器下面的某个具体场景、卡片、弹窗、模板、玩法、资源位，一律优先按**功能/业务实例（Feature/Instance）**理解，不能偷换成容器。
    - **禁止用“短语里含容器词”反推它就是容器。** 例如："购物车锚点"里虽然有"锚点"，但"锚点"才是容器（Container），"购物车锚点"是锚点容器下的具体业务实例（Feature/Instance），不能直接把实例 owner 回答成锚点容器 PM。
    - **禁止混淆示例：**"异形卡"是容器（Container）；"好友推荐异形卡"是具体业务实例（Feature/Instance），不能直接把"好友推荐异形卡"的 owner 回答成"异形卡容器 PM"。
    - 如果用户描述的模块比**容器（Container）**更具体，那大概率是**功能/业务实例（Feature/Instance）**
    - **强制停点规则：** 若当前问题是找 owner，且你目前只命中了上层页面/容器、只拿到了页面/容器 POC，但用户实际问的是该容器下更具体的业务实例（如“购物车锚点”“好友推荐异形卡”“推送授权弹窗”），此时**不得直接回答页面/容器 owner**。必须继续在容器规范中查该实例；若查不到实例级 owner，就明确回复“当前无法确认该业务实例 owner”，禁止拿上层 owner 代答。
    - **输出前硬校验：** 在给出 owner 前，必须显式核对 `用户所问对象层级` 与 `当前证据指向的 owner 层级` 是否一致。
      - 若用户问的是 **Feature/Instance**，但证据仅指向 **Page/Container** → **禁止输出 owner**。
      - 此时只能继续查实例级证据；若仍无结果，只能回复“当前无法确认该业务实例 owner”。
      - **不得**因为文档开头有容器 POC，就默认当作实例 POC。

  3. 如果能匹配到页面或者容器，**必须继续完整阅读对应规范文档，不能停留在 one page 链接层**
    - 在 [主框架规范 one page] 里找到对应容器模块，并**只沿 one page 中给出的对应规范链接继续阅读**
    - **禁止为了"更快命中"而再去飞书文档搜索同类关键词（如"模块名 + 设计 + POC / owner / 规范"）补找规范。** 只要 one page 已命中，就必须把 one page 里的对应规范当作唯一优先权威入口
    - **权威文档判断原则（产品模块分支强制执行）：** 只有以下两类文档可以直接作为最终结论依据：
      1. **one page 直接命中的规范文档**；
      2. **在有效规范中被明确指定 / 引用为权威入口的文档**。
    - 若文档不属于上述两类，即使能搜到 PRD、sheet、tracker、找人地图、周报、争议材料、复盘、专项过程文档等，也**一律只能作为辅助线索，不能直接用于确认实例 owner / POC / 标准结论**。
    - **优先查看该规范文档开头的 POC / PM / 分析 / 设计 / 研发名单**
    - **命中标准页面/容器后的强制提取规则：** 只要已成功命中标准页面或标准容器，并且对应规范文档开头已明确给出 POC / PM / owner 名单，就必须先提取该名单作为 owner 候选结论；**禁止在已读到明确 POC / PM 后仍回退成“无法确认 owner”。**
    - **对“个人页高级功能区”这类已归一化为 `Profile 页面下的高级功能区容器` 的问题，若对应规范文档已明确给出 POC，则默认按容器级 owner 回答。** 这类问法不是实例级问法，不得误套实例防呆规则。
    - **按「规范管理方式」中的判定规则检查当前规范的有效性**；若规范不判定为"有效"，在回答中附加提示：**当前规范可能已过期，请及时联系 owner 确认。**

  4. 如果询问的是具体的功能/业务实例，则在对应容器的规范文档中搜索线索
    - 如果直接能找到，则定位到对应条目
    - 若无法找到，则统一回复"该模块规范暂未详细列出此功能 POC，更多细节咨询 [该容器的 PM 负责人]"

  5. 如果询问的容器或者业务实例不在 [主框架规范 one page]
    - 明确写出：**该模块不是主架构负责范围**。
    - 再补充候选 owner / 团队线索 / 证据来源 / 置信度。
    - 禁止把候选线索包装成主架构官方结论。

#### 5) 流程

- 方法名：`process-method`
- 适用场景：用户询问某产品流程相关信息（如评审流程、实验流程、上线流程、提审流程、申请流程、扩量流程、退场流程等）
- 步骤：
  1. 先完整阅读 [主框架规范 one page]，定位到「产品流程 // Process」section。
  2. **把该 section 下列出的所有流程文档完整读一遍后再作答**。流程之间常有相互引用与衔接（如评审流程引用准入标准、上线流程依赖实验流程结论），只读一篇容易漏掉关联约束。
  3. 基于已读完的全量流程文档，回答用户问题（找 owner / 流程节点 / 准入条件 / 产出物 / 时效 / 例外情况等）。
  4. 若用户问的流程在 one page 「产品流程」section 中没有覆盖，明确回复：**该流程不在主架构产品流程规范范围内，请与对应业务/流程 owner 确认**。

**约束（强制执行）：**
- **禁止只读 one page 索引层就直接回答流程问题。** 索引层只能告诉你流程清单，不包含节点、准入、产出物等细节；必须深入读完每一篇流程文档。
- **禁止跳过 one page 直接飞书广搜流程文档。** 只以 one page 「产品流程」section 中列出的文档为权威来源；若 one page 未覆盖，按步骤 4 兜底，不得自行扩搜补答。
- **禁止跨流程偷换。** 用户问 A 流程时，不能拿 B 流程文档中"看起来相关"的规则当 A 流程答案；只有当流程文档之间存在明确引用且引用关系成立时，才能基于被引用流程补充信息。
- **禁止仅凭流程名直觉补答。** 即使流程名"看起来很标准"（如"上线流程"），也必须以读到的流程文档内容为准；不能用通用经验或其他业务域的流程去补节点。
- **流程文档时效性参考 module-method 的规范有效性原则**：若流程文档已明确标注无效/过期/废弃，停止使用其作为答案依据；否则正常输出，必要时在末尾附一句"当前流程规范可能已过期，请及时联系 owner 确认"。

#### 6) 指标

- 方法名：`metric-method`
- 适用场景：用户询问某个 TikTok 核心指标的定义、口径、计算方式、归属业务、负责人等信息。
- 权威来源：**[TikTok 核心指标]**——这是该 method 的唯一权威来源，禁止飞书广搜补充其它指标文档。
- 步骤：
  1. 从用户问题中提取 **指标名称**（中英文皆可，含缩写）作为搜索关键词。
  2. 在 [TikTok 核心指标] 中按指标名做关键词搜索，按 lark-bot-playbook 的 `sheets +find` recipe 执行：

  3. 若一次未命中，先尝试中英文别名 / 缩写补搜一次（如 "DAU" ↔ "日活" ↔ "Daily Active Users"），仍无命中再回退兜底。
  4. 基于命中行的字段回答用户问题：
     - 问定义/口径/计算方式 → 直接给该行对应字段
     - 问归属业务/负责人 → 给负责人字段；若负责人是 OpenID，必须按核心行为准则反查成姓名再输出
  5. 若搜不到匹配指标，回复：**在 TikTok 核心指标文档中未找到该指标，请确认指标名称是否准确，或与主架构人工确认**。
- 引用规则：按本 skill「输出要求」第二条，回复末尾必须附 [TikTok 核心指标] 飞书链接。

**约束（强制执行）：**
- **禁止仅凭指标名直觉作答**——即使指标名"看起来很标准"（DAU、留存、CTR 等通用指标），口径在不同业务/平台可能不一样，必须以 [TikTok 核心指标] 文档里读到的口径为准。
- **禁止跨文档偷换口径**：不能拿其它产品域（抖音、CapCut、Lemon8）或通用 wikipedia 式定义补答 TikTok 指标口径。
- **禁止把候选指标当确认指标**：若 [TikTok 核心指标] 里同时存在多个相似指标（如 "DAU" / "MAU" / "WAU" / "Active DAU"），必须按用户原词精确匹配；模糊匹配只能列出候选让用户确认，不得替用户挑一个就答。

## 分支二：问详细信息

### 执行顺序

1. **利用 Step 0 解析结果 + 权威文档定位**，找到用户询问实体对应的权威文档。
2. **在定位到的文档中，读取与当前问题直接相关的章节**，提取可验证的信息。
3. 基于文档中获得的可验证信息回答用户问题。
4. **默认只回答用户当前显式询问的最小充分信息**，不得主动扩展到用户未问的相邻信息。
5. **如果没有拿到足够的可验证信息**，必须直接说明"当前无法确认/需要找对应 owner 进一步确认"。

### 收口规则（问详细信息强制执行）

- 当用户询问某对象的 **"标准 / 准入规则 / 使用规范 / 定义 / 口径 / 上线标准"** 时，最终回复默认只输出该对象对应规范中的**直接答案本身**。
- **禁止主动追加**以下内容，除非用户显式追问，或缺少该信息会导致主结论失真：
  - owner / POC / 联系人
  - 接入流程 / 提审流程 / 审批流程
  - tooltips_key、埋点、代码接入等研发细节
  - 规范时效提示（如“当前规范可能已过期”）
- **“上线标准” ≠ “上线流程”**。当用户问的是标准、规则、定义、口径时，禁止自动切换到流程说明；只有用户显式问到“怎么上线 / 怎么接入 / 怎么提审 / 申请流程 / 审批流程”时，才展开流程内容。
- **规范有效性检查必须内部执行**。只有当：
  1. 规范明确无效，导致主结论不能成立；或
  2. 用户明确追问“规范是否还有效 / 当前规范是否过期”
  才把时效提示写入用户正文。否则不在正文中外显。
- **若用户问题只问一个点，则默认单点收口，不做并列扩写。** 例如只问“上线标准”，就只回答标准，不顺带补“怎么申请上线/扩量”。
- **截图问弹窗时的强制补充规则：** 若用户上传截图并询问“这是什么弹窗 / 弹窗 key 是什么 / 这个 popup 是什么”，且通过截图识别 / Stage 2 popup 识别已经拿到 `popup_id`、或能高置信映射到具体平台 key（如 `sms_normal` / `edm_normal`），则最终回复里**必须直接写出弹窗 key**；不要只回答弹窗类型后等用户二次追问。若只能识别到弹窗族而不能精确到 key，要明确写“更像/疑似 `<key>`”，不要把推测说成已验证事实。

## Guardrails

### 回答质量

- 无可靠依据时，不臆测负责人姓名。
- **禁止在缺少权威来源或可验证依据时，用通用产品/架构语境补答案。** 用户要的是准确细节，不是泛化猜测。
- **禁止把"为了先帮到用户"当作理由进行脑补式回答。** 一旦依据不足，唯一正确动作就是明确说无法确认。
- **禁止因为 one page 命中上层容器、且规范开头恰好写有该容器 POC，就产生“已经找到答案”的错觉。** 对 owner 类问题，必须确认该 owner 与用户所问对象处于同一层级；如果只验证到了上层容器而未验证到实例层，答案状态仍然是“不可回答”。
- **禁止对象替换。** 不能把“购物车锚点”偷换成“锚点”，不能把“好友推荐异形卡”偷换成“异形卡”，不能把“推送授权弹窗”偷换成“弹窗”。
- **禁止术语替换。** 不能把 `hashtag` 偷换成 `tag`、`topic`、`label`；不能把后台字段名、模块名改写成相近术语后再检索。
- **禁止系统替换。** 不能把 `Mint 后台模块` 偷换成 `C端产品模块`、`Creator tools 模块`、`Publisher tools 模块`；即使名字相同或相关，也不能默认共用 owner。
- **命中相关对象 ≠ 回答完成。** 若当前证据只命中“相关模块”“同名模块”“另一系统中的相似模块”，必须停止回答 owner；只有命中与用户原话同术语、同系统、同层级的对象时，才可输出。
- **命中容器 ≠ 回答完成。** 若 one page 或规范只证明了上层容器存在，不能据此宣布已找到实例 owner；实例级问题只有在拿到实例级证据时才算完成。
- **错例记忆（必须规避）：** 曾出现“购物车锚点”问题中，先命中锚点容器，再误把锚点规范开头的容器 POC 当成实例 POC输出；也曾出现把“Mint 后台 hashtag 模块”误判为“C端 tag 模块”。后续遇到同型问题，必须先做`术语一致性 + 系统一致性 + 层级一致性`三重校验，不通过就停止回答 owner。
- 在共享场景中，仅输出完成任务所需的最小信息。

### 流程控制

- **Step 0 不可跳过**：即使关键词"看起来很明确"，仍须执行权威索引预定位，不能凭直觉直接进入子意图分支。
- **先判定实体分支是否已开发**：若分支标记"暂未开发/待补充"，必须立即按固定口径返回，禁止继续追问。仅当分支已开发且确有必要时，才可要求补充线索。
- **禁止跳过权威文档定位逻辑直接回答。** 即使"问题看起来比较基础"或"可以先给个大概口径"，也不能绕过。Step 0 的精准匹配可以跳过搜索步骤，但不能跳过权威文档的阅读步骤。

### 产品模块专项约束

以下规则适用于所有产品模块类问题（无论子意图是找owner还是问详细信息）：

- 如果问题里出现 **"标准 / 准入 / 规则 / 定义 / 口径 / 流程 / 怎么接入 / 怎么上线"**，**必须把 one page 命中的规范文档读到对应章节**，不能只做 owner 查询就停止。
- 如果 [主框架规范 one page] 已经精准命中对应容器/规范，**禁止回复"当前没有可验证来源"**；正确动作是继续读规范。
- 如果 [主框架规范 one page] 已经精准命中对应容器/规范，**禁止再去飞书做同类广泛搜索来重新找规范、找 POC 或找 owner**；应当先把 one page 指向的规范读完并以其为准。
- **即使实例级 POC 没写清，只要容器规范里存在用户追问所需的规则/标准，也要继续基于该规范回答可验证信息。**
- 只有在 **one page 未命中**，或者 **命中的规范里确实没有该信息** 时，才允许回复"当前无法确认/需要找 owner 进一步确认"。
