# Skill Eval

## Invocation Rule

- 不直接面向用户问题触发。
- 仅接受 `orchestration` 路由调用。
- 当主意图识别为 **[内部]技能评测** 时触发。

## 输入

| 参数 | 必填 | 说明 |
|------|:---:|------|
| **skill 名称** | 是 | 待评测的 skill 标识，对应 `skills/` 下的目录名 |
| **评测文档** | 是 | 包含问题和期望答案的文档，用于逐条验证 skill 的输出 |

## 处理流程

1. **加载 skill** — 读取 `skills/{skill名称}/SKILL.md`，确认 skill 存在且已开发
2. **解析评测文档** — 从用户提供的文档中提取问答对（问题 + 期望答案）
3. **逐条评测** — 对每条问题，按"默认评测模式：端到端"用隔离子运行触发目标 skill，将实际输出与期望答案进行比对
4. **输出评测报告** — 汇总各条目的通过/失败状态，计算通过率，列出失败条目的差异分析

## 默认评测模式：端到端（E2E）

当用户**未显式指定**评测某一具体层时（例如只说"评一下 X skill"，没有说"只评分类器"或"只评下游本体"），默认按**端到端评测**执行：子运行必须像真实用户提问一样，从 `question-understanding` 起步，经 `orchestration` 路由，直到下游 skill 产出最终结果。

**缺省即全量**：不确定就按 E2E 全量加载，不要擅自省略必读文件或跳过上游链路。

### E2E 子运行必读文件(完整清单)
子运行不会天然继承主会话的脑内上下文，必须在任务中显式列出以下全部文件并要求先行读取：

- `/root/.openclaw/workspace/IDENTITY.md`
- `/root/.openclaw/workspace/SOUL.md`
- `/root/.openclaw/workspace/AGENTS.md`
- `/root/.openclaw/workspace/MEMORY.md`
- `/root/.openclaw/workspace/TOOLS.md`
- `/root/.openclaw/workspace/USER.md`
- `/root/.openclaw/workspace/skills/question-understanding/SKILL.md`
- `/root/.openclaw/workspace/skills/orchestration/SKILL.md`
- `/root/.openclaw/workspace/skills/{评测目标 skill}/SKILL.md`
- 目标 skill `references/` 目录下所有 `.md`（如 `requirement-review/references/*.md`）
- `orchestration` 在本题中可能二次路由到的其它下游 skill 的 `SKILL.md`（只要链路上可能被触发）

### 何时可窄化必读清单
仅当用户**显式**声明评测目标为某一具体层时（例如"只评分类器"、"只评 info-query 本体、跳过上游"），才可按"严格版稳定性评测"中的窄化规则精简必读文件并绕开上游执行。

## 严格版稳定性评测（新增）

当用户不是要跑整份评测集，而是要验证**某一个具体问题**在目标 skill 下是否能稳定输出时，按以下“严格版稳定性评测”执行。

### 适用场景
- 用户要求“同一个问题跑 5 次 / 10 次”
- 用户要求“清空上下文，独立跑多次”
- 用户要求验证某条分类/路由规则是否稳定收敛
- 用户要求“更新 skill 后立刻复测”

### 执行原则
1. **必须使用隔离子运行**，每一遍都视为独立样本，禁止复用上一遍的中间判断。
2. **必须显式指定必读文件**，不能假设子运行天然继承主会话脑内上下文。
3. **必读文件清单**：
   - **默认（E2E，用户未指定层）**：按"默认评测模式：端到端"中的完整清单加载全部文件
   - **窄化（仅当用户显式指定单层时）**：
     - 目标 skill 的 `SKILL.md`
     - `/root/.openclaw/workspace/MEMORY.md`
4. 如用户明确追加，还可加入 `SOUL.md` 或其他指定文件。
5. **禁止只说“按某 skill 风格输出”** 就开始评测；必须把标签体系、输出契约、必读文件约束清楚写进任务。
6. **禁止把未严格加载 skill 的试跑结果，当成 skill 本身稳定性的正式结论。**
7. **必须先判断评测对象到底是哪一层：**
   - **默认（用户未指定）**：评的是**端到端链路**，评测目标是真实用户问答从 question-understanding 到下游 skill 的完整输出，子运行必须加载 E2E 完整必读清单。
   - 若评的是 `question-understanding` / 分类器，则评测目标是**分类输出本身**。
   - 若评的是 `info-query`、`opinion-judgment` 等下游 skill，则评测目标是**该下游 skill 的完整执行结果**，不能只停在分类标签层。
8. **评下游 skill 本体时，必须补齐其所依赖的上游上下文。** 例如评 `info-query` 时，不能只把用户原句丢进去；必须在任务中显式给定：主意图、主实体、产品域、实体关键词，以及“不要重新做 question-understanding / orchestration”。
9. **timeout 要按 skill 类型设置，不要沿用过短默认值。**
   - 纯分类型稳定性评测：可用较短 timeout。
   - 需要读权威文档 / 拉飞书文档 / 走完整下游执行链的 skill：默认 **600s**。
   - 若用户明确要求更长，或目标 skill 已知文档很长/链路很深，可再提高，但不得低于能稳定覆盖完整执行链的水平。

### 标准任务模板
对每个隔离子运行，任务中至少要包含：
- 明确声明本轮评的是哪一层（**E2E / 分类器 / 下游 skill 本体**）
- 按该层对应的必读文件清单加载全部文件
- 严格以加载的必读文件为唯一依据
- 禁止调用 `memory_search`

- 若评的是**端到端（默认，用户未指定层时）**：
  - 按"默认评测模式：端到端"中的 E2E 必读清单显式列出并要求读取全部文件
  - 输入只有用户原句，不做任何预处理或改写
  - 要求子运行按真实链路依次执行 question-understanding → orchestration → 下游 skill，不得跳层或脑内模拟
  - 若下游依赖飞书文档 / 权威来源，必须实际执行查询，不得停在纸面分析
  - 只输出最终正式结果，不要解释、不要分步复述
- 若评的是**分类器**（需用户显式声明）：
  - 先读取 `skills/question-understanding/SKILL.md` 与 `/root/.openclaw/workspace/MEMORY.md`
  - 禁止做后续 orchestration / 下游执行
  - 输入问题只有用户指定的那一句/那一段
  - 只输出分类结构化结果，不要解释，不要补充
- 若评的是**下游 skill 本体**（需用户显式声明）：
  - 先读取目标 skill 的 `SKILL.md`、其 `references/` 目录下所有 `.md`，以及 `/root/.openclaw/workspace/MEMORY.md`
  - 禁止再调用 `question-understanding`
  - 禁止再做 `orchestration`
  - 必须把上游上下文显式写进任务（如主意图、主实体、产品域、实体关键词）
  - 必须要求子运行按目标 skill 的**完整流程执行到底**，而不是只做纸面分析
  - 若该 skill 依赖飞书文档 / 权威来源，必须明确要求按 skill 指向的权威来源实际执行查询
  - 只输出目标 skill 的最终正式结果，不要解释，不要补充评测说明

### 输出检查维度
稳定性评测汇总时，至少检查以下 4 类结果：
1. **一致性**：多次运行结果是否完全一致
2. **schema 合法性**：输出字段和值是否符合 skill 的输出契约
3. **正确性**：是否命中用户认定的正确答案 / 期望答案
4. **漂移点**：若不一致，明确指出摇摆发生在主意图、次意图、主实体、次实体、产品域中的哪一层

对**下游 skill 本体**，除上述 4 类外，还要额外检查以下执行层漂移：
5. **命中层漂移**：是否有的样本停在“未命中 / 无法确认”，有的样本已命中标准页面、标准容器、标准文档
6. **证据链漂移**：是否有的样本已进入权威规范正文，有的样本仍停在 one page / 索引层
7. **owner 提取漂移**：是否出现“有的样本输出姓名、有的样本输出 open_id / mention-user、有的样本仍拒答”
8. **文案级漂移 vs 结论级漂移**：要区分只是引号/措辞不同，还是最终结论（如 owner 人名）真的不同
9. **超时漂移**：是否有样本在当前 timeout 下超时，导致结论缺失；若有，优先调大 timeout 后再判断 skill 稳定性

### 复测迭代方法
如果第一次严格版评测未稳定收敛：
1. 先总结不稳定具体发生在哪些字段 / 哪一层执行链
2. 反推是哪类规则缺失或优先级不够清晰
3. 直接把新规则写回目标 skill
4. **必须对同一题目再次做 5 次严格版复测**
5. 只有当多次结果完全一致时，才可宣称“该题已稳定”

对**下游 skill 本体**，优先按以下顺序修：
1. **先修命中规则**：先确保页面/容器/实例层级、别称归一化、标准容器命中稳定
2. **再修证据链规则**：命中后必须继续读 one page 指向的权威规范，不能停在索引层
3. **再修提取规则**：如 owner / POC / PM 的抽取与姓名归一化
4. **最后再修输出文案**：仅当主结论已稳定时，才去收口措辞和格式

**禁止跳过前置层直接修后置层。** 例如：若连标准容器都未稳定命中，就不要先优化 owner 文案；若连权威规范都未稳定读到，就不要先优化姓名展示格式。

### 噪音隔离提醒
- 长背景句中出现的礼貌措辞、协同语气、参与方名称、治理/流程背景，常常会污染次意图或次实体。
- 当用户要求验证“是否稳定输出正确主干结果”时，要额外检查：
  - 背景噪音是否误进了次意图
  - 背景噪音是否误进了次实体
- 若主标签已正确但次标签仍漂移，不能算“完全稳定”。

### 结果汇报要求
汇报时默认包含：
- 每次运行结果
- 汇总结论（几次一致 / 几次合法 / 几次正确）
- 若已稳定：明确写“已达到 5/5 完全一致”
- 若未稳定：明确指出还需补哪类规则，再继续复测

## 输出格式

```
评测对象：{skill 名称}
评测条目：{总数}
通过：{通过数} | 失败：{失败数}
通过率：{百分比}

--- 失败条目 ---
#{序号} 问题：{问题内容}
  期望：{期望答案}
  实际：{实际输出}
  差异：{差异说明}
```
