# 批量审核回写技能

按下面流程严格执行，不跳步。审核判断逻辑遵循 `system-message-review` skill 的全部规则。

## 0. 确认目标表格

默认目标表格：
- Wiki URL：`https://bytedance.larkoffice.com/wiki/UugLwoEiaiyHbek4LDCcgHs6nah`
- Sheet ID：`2FMrds`

如果用户指定了其他表格 URL 或 sheet，以用户指定的为准。

## 1. 读取表格 & 发现结构

使用 `feishu_sheet` 读取目标表格的表头行：

```
feishu_sheet(action="read", url="<wiki_url>", range="<sheet_id>!1:1")
```

读取完成后，根据表头行内容**动态定位**所有列，不硬编码列号。

### 输入列（业务方已填，AI 读取用）

按表头名称定位以下列（名称可能有细微差异，按含义匹配）：

| 表头名称 | 对应评审输入 |
|---------|-------------|
| id | 工单 ID |
| template_name | 模版名称 |
| channel | Channel |
| category | Category |
| title | 消息标题 |
| content | 消息正文 |
| prd | PRD / 合规工单链接 |
| business_line | 业务线 |
| reason_for_sending | 发送原因 |
| target_users | 目标人群 |
| trigger_notice | 触发逻辑 |
| exit_mechanism | 退出机制 |
| send_user_amount | 预估发送量 |
| can_new_users_receive | 新用户是否可收到 |
| reason_for_new_users_can_receive | 新用户可收到原因 |
| has_freq_ctrl | 是否有频控 |
| freq_detail | 频控详情 |
| reason_for_unlimited_freq | 无频控原因 |
| must_reach | 是否必达 |
| is_priority | 是否优先推荐 |
| reason_for_priority | 优先推荐原因 |
| image_type | 是否有图片 |

### AI 输出列（共 7 列）

以下是 AI 需要写入的列及其表头名称：

| 表头名称 | 填写内容 |
|---------|---------|
| AI审批结果 | `通过` / `拒绝` / `权限不够` |
| AI判断逻辑 | 核心依据，2-4 句话 |
| AI给业务反馈的拒绝原因 | 仅拒绝时填写，面向业务方的反馈措辞 |
| AI置信分组 | `高置信通过` / `高置信拒绝` / `边界需人工看` / `信息不足` |
| AI置信分组逻辑说明 | 为什么归入该置信分组，1-2 句话 |
| 命中规则编号 | 1-3 个规则代码，逗号分隔（代码表见 `review-rubric.md` 第十一节） |
| 前置校验清单 | 7 项校验逐项结果，格式：`完整性✓ 合规✓ Channel-Category✓ 必达✓ Priority— 格式✓ 图片—` |

### 人工复核列（共 4 列）

| 表头名称 |
|---------|
| 人工审批结果 |
| 人工拒绝原因 |
| AI是否准确\n0 结果不对\n0.5 审批结果对但是拒绝原因不对\n1 和人工完全匹配 |
| 误判类型 |
| 补充结论 |

## 1.5 自动补齐表头和列

读取表头后，检查 AI 输出列和人工复核列是否已存在。按以下逻辑处理：

### 判断规则

逐个检查上述 7 个 AI 输出列 + 5 个人工复核列的表头名称是否在表头行中存在（按精确匹配）。

### 如果所有列都已存在

记录每列的实际列号，跳到第 2 步。

### 如果有缺失列

按以下顺序在表格最右侧依次追加缺失列的表头：

1. 先补齐所有缺失的 **AI 输出列**（按上表顺序）
2. 再补齐所有缺失的 **人工复核列**（按上表顺序）

写入表头的方式：找到当前表头行最后一个非空列，从下一列开始依次写入缺失列的表头名称。

```
feishu_sheet(action="write", url="<wiki_url>", range="<sheet_id>!{起始列}1:{结束列}1", values=[["AI审批结果", "AI判断逻辑", ...缺失的表头]])
```

写入后 read-back 确认表头正确，然后重新读取完整表头行，更新所有列的列号映射。

### 注意事项

- **绝对不能覆盖已有列**：只在最右侧空白区域追加
- **已有列不移动**：如果 AI 输出列已存在但中间缺了某列，只在最右侧追加缺失的列，不插入到中间（飞书 Sheet API 不支持 insert column）
- **人工复核列如果已有数据，不动**：只补缺失的表头，不修改已有列的位置或内容
- 补齐后，后续所有读写操作都基于**动态定位的列号**，不再假设固定列号

## 2. 筛选待审核行（必须使用枚举校对模式）

**禁止** 只凭当前读到的一小段内容直接开始处理。必须先做完整枚举，再开始写回。

### 2.1 第一遍全表枚举

遍历所有数据行（第 2 行起），按以下规则建立清单：

- **业务有效行**：`id` 非空，且核心业务输入（如 `template_name/title/content/channel/category/reason_for_sending/target_users`）不全为空
- **待审核行**：在“业务有效行”中，`AI审批结果` 列为空
- **已审核行**：在“业务有效行”中，`AI审批结果` 列非空

建立一份枚举清单，至少包含：
- 行号 `row`
- 工单 `id`
- `template_name`
- 当前 `AI审批结果` 是否为空
- 本轮是否已处理（初始为否）

### 2.2 生成待处理队列

从枚举清单中筛出 **`AI审批结果` 为空** 的业务有效行，作为待处理队列。

统计：
- 业务有效行总数
- 已审核行数
- 待审核行数 **N**

并告知用户：`"共发现 N 行待审核，开始逐行处理。"`

如果没有待审核行，直接告诉用户"所有行已审核完毕"并结束。

### 2.3 清单驱动，不得脱离枚举表作业

后续所有写回动作，必须以这份枚举清单为唯一依据：
- 每处理完一行，就把该行在清单中的状态改为“已处理”
- 绝不能靠肉眼扫表判断“应该都写完了”
- 绝不能因为分页截断、range 截断或中途插入空行，就默认后面没有数据

## 3. 逐行审核

**必须处理完待处理队列中的每一行，中途不得停止。** 处理完一行后，立即继续下一行，不等待用户确认，不提前结束。只有当队列中所有行都已写回并校验通过后，才进入第 5 步输出汇总。

对每一行待审核数据，执行以下子流程：

### 3.1 提取输入

从该行提取所有输入列的值，组装成审核输入：

```
工单 ID：{A}
模版名称：{F}
Channel：{H}
Category：{I}
标题：{J}
正文：{K}
PRD/合规工单：{L}
业务线：{M}
发送原因：{N}
目标人群：{O}
触发逻辑：{P}
退出机制：{Q}
预估发送量：{R}
新用户是否可收到：{S}（原因：{T}）
是否有频控：{U}（详情：{V}，无频控原因：{W}）
是否必达：{X}
是否优先推荐：{Y}（原因：{Z}）
是否有图片：{AA}
```

### 3.2 执行评审（遵循 system-message-review 全流程）

严格按 `skills/system-message-review/SKILL.md` 的步骤 1-9 执行：

1. **明确审核对象**：从上述输入中提取消息文案、发送原因、目标人群、触发逻辑、PRD
2. **前置校验**：工单完整性、合规评估、Channel-Category 合法性（查 `skills/system-message-review/references/channel-category-map.md`）、必达合法性、Priority、内容格式
3. **三轴初筛**：必须告知 / 用户行为相关 / 功能推广活动引流
4. **高置信通过口径**：必须告知类、已发生结果通知类、无门槛利益点
5. **高置信拒绝口径**：功能推广/活动引流/运营催促、利益诱导、强营销金融触达
6. **边界案例**：判断主信息、特殊通道（Live APP only、Surveys）
7. **人群最小化**：是否只发给明确受影响用户、新用户规则、大人群量级
8. **频控**：同功能/活动频控、全局频控
9. **落结论**：按判定顺序给出最终结论

遇到边界案例或细则时，读取 `skills/system-message-review/references/review-rubric.md`。

### 3.3 确定置信分组

根据审核过程中的判断路径，确定置信分组：

| 置信分组 | 判断标准 |
|---------|---------|
| **高置信通过** | 命中 SKILL.md 第 4 节任一高置信通过口径，且无前置校验问题 |
| **高置信拒绝** | 命中 SKILL.md 第 5 节任一高置信拒绝口径，判断无歧义 |
| **边界需人工看** | 进入第 6 节边界案例处理，或通过/拒绝口径之间存在张力 |
| **信息不足** | 必填字段缺失或者无法阅读到 PRD ，无法做出最终判断 |

### 3.4 组装输出

根据审核结论，填写 7 列内容。以下用字段名称而非固定列号表示（实际列号以第 1.5 步动态定位结果为准）：

**通过时：**
- `AI审批结果` = `通过`
- `AI判断逻辑` = 核心依据（2-4 句话，说明为什么通过）
- `AI给业务反馈的拒绝原因` = （留空）
- `AI置信分组` = `高置信通过` 或 `边界需人工看`
- `AI置信分组逻辑说明` = 为什么归入该置信分组
- `命中规则编号` = 命中规则代码，逗号分隔，如 `4.2-结果通知, 规则B-结果通知`
- `前置校验清单` = 如 `完整性✓ 合规✓ Channel-Category✓ 必达✓ Priority— 格式✓ 图片—`

**拒绝时：**
- `AI审批结果` = `拒绝`
- `AI判断逻辑` = 核心依据（2-4 句话，说明为什么拒绝）
- `AI给业务反馈的拒绝原因` = 面向业务方的反馈措辞（参照 `review-rubric.md` 第九节输出模板中"拒绝"的推荐措辞风格）
- `AI置信分组` = `高置信拒绝` 或 `边界需人工看`
- `AI置信分组逻辑说明` = 为什么归入该置信分组
- `命中规则编号` = 命中规则代码，如 `5.1-功能推广`
- `前置校验清单` = 逐项结果

**信息不足时：**
- `AI审批结果` = `拒绝`
- `AI判断逻辑` = 当前能给的阶段性判断 + 缺什么信息
- `AI给业务反馈的拒绝原因` = （留空）
- `AI置信分组` = `信息不足`
- `AI置信分组逻辑说明` = 说明缺失了哪些关键字段
- `命中规则编号` = 已命中的规则代码 + `前置-工单不完整`（如适用）
- `前置校验清单` = 缺失项标 ✗

**含图片素材时（叠加在通过/拒绝/待补充之上）：**
- `AI判断逻辑` 追加 `[含图片-待确认]`；`AI置信分组` 若图片可能改变结论方向则降为 `边界需人工看`
- `命中规则编号` 追加 `规则G-含图片`
- `前置校验清单` 图片项标 `⚠待确认`，如 `完整性✓ 合规✓ Channel-Category✓ 必达✓ Priority— 格式✓ 图片⚠待确认`

## 4. 写回表格

### 4.1 单行写入

对每行审核完成后，立即写回该行的 7 个 AI 输出列。使用第 1.5 步动态定位的列号：

```
feishu_sheet(action="write", url="<wiki_url>", range="<sheet_id>!{AI审批结果列}{row}:{前置校验清单列}{row}", values=[[...7 个值，按列顺序排列...]])
```

如果 7 列不连续（因为表格原有布局），则分段写入，每段覆盖一组连续列。

### 4.2 写后立即 read-back 校验

写入后，立即回读同一区间确认写入正确：

```
feishu_sheet(action="read", url="<wiki_url>", range="<sheet_id>!{AI审批结果列}{row}:{前置校验清单列}{row}")
```

校验要点（与 `system-message-review` SKILL.md 第 10 节"写回前自检"一致）：

**一致性检查（最重要）：**
- `AI审批结果`=通过 → `AI置信分组` 不能是 `高置信拒绝`
- `AI审批结果`=拒绝 → `AI置信分组` 不能是 `高置信通过`
- `AI判断逻辑` 的论证方向必须与 `AI审批结果` 一致（逻辑说应该通过但结果写了拒绝 = 错误）
- `命中规则编号` 中的规则方向必须支撑结论（只命中 5.x 拒绝类规则但结果=通过 = 错误）

**完整性检查：**
- `AI审批结果` 是否为 `通过` / `拒绝` / `待补充` 之一
- `AI判断逻辑` 是否非空
- 如果结果=拒绝，`AI给业务反馈的拒绝原因` 是否非空
- `AI置信分组` 是否为四个分组之一
- `命中规则编号` 是否非空，且每个代码均在规则代码表中
- `前置校验清单` 是否包含 7 项校验结果

如果发现矛盾，以 `AI判断逻辑` 的实际论证方向为准，修正结果或置信分组后重写。如果 read-back 发现不一致，立即重写该行，不要跳过。

### 4.3 相邻行保护

写入时**只更新目标行的 AI 输出列**，绝对不能覆盖相邻行或其他列。每次 write 的 range 必须精确到动态定位的 AI 输出列范围。**绝不能写入人工复核列。**

## 5. 进度报告与完成确认

### 5.1 过程中进度报告

每完成 5 行，用**一句话**简短报告进度（如 `"已完成 10/47 行"`），然后**立即继续处理下一行**，不要停下来等用户回复。

### 5.2 第二遍全表枚举校对（必须执行）

**待处理队列跑完后，不能直接结束。** 必须重新读取整张表，再做一遍全表枚举校对：

校对项：
1. 是否仍存在“业务有效行”但 `AI审批结果` 为空
2. 第一遍枚举时在清单里的待处理行，是否都已真正写入
3. 是否存在 `AI审批结果` 与 `AI置信分组` 明显不一致的脏数据
4. 是否存在 `AI判断逻辑` 非空但 `AI审批结果` 为空的异常行

若发现遗漏行：
- **立即继续处理遗漏行**
- 处理完后再次做校对
- 直到校对结果为 0 遗漏，才能进入最终汇总

### 5.3 全部完成后输出汇总

**只有当第二遍全表枚举校对确认 0 遗漏后**，才输出以下汇总：

- 业务有效行总数
- 本轮新审核行数
- 通过 / 拒绝 / 待补充 各多少行
- 高置信通过 / 高置信拒绝 / 边界需人工看 / 信息不足 各多少行
- 如果有写入失败的行，列出行号
- 如果本轮发现过遗漏并补写，明确说明"已通过枚举校对补齐"

### 5.4 禁止提前结束

以下情况**不得作为停止处理的理由**：
- "已处理了足够多的行" — 不存在"足够多"，必须处理完全部
- "剩余行可以稍后处理" — 不可以，必须当前一次性处理完
- "先给用户看一下已处理的结果" — 不需要，继续处理直到全部完成
- 单行写入失败 — 记录失败行号，继续处理下一行

## 6. 异常处理

- **表格读取失败**：停止，告知用户检查表格权限或 URL
- **单行写入失败**：记录失败行号，继续处理下一行，最后统一报告失败行
- **Channel-Category 映射表读取失败**：跳过 Channel-Category 合法性校验，在 AG 中注明"未校验 Channel-Category"
- **PRD 链接无法访问**：在 AG 中注明"PRD 未读取"，基于工单已有信息给阶段性判断

## 注意事项

- 本 skill 的审核判断逻辑完全遵循 `system-message-review` skill，不做任何简化或跳步
- 写回时遵循 workspace MEMORY.md 中的规则：先读回确认行号 → 只更新目标行 → 写完立即 read-back 校验
- 对相邻工单尤其谨慎，不要把 A 行的结论写到 B 行
- 如果表格列结构与预期不同（如列号偏移），先根据表头行重新定位列号，再继续
