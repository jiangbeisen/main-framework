## 一、修正规则 A-F（来自 3.31 / 4.2 复盘）

### 规则 A：活动体系内消息从严判断

下面这些即使业务描述成"用户状态变化"，也要先按活动运营消息从严判断：

- 被邀请成功加入活动
- 邀请成功，有人通过你的邀请加入活动
- 活动结束提醒、任务提醒 / 倒计时提醒
- 海报领取 / 分享引导
- 功能探索 / 首播拉起 / 产品能力推广

判断原则：

- 消息主要服务于活动承接、裂变、留存、拉活、传播 → 通常不通过
- **但若同时满足"经营意愿/权益相关 + 人群已精准圈选 + 主信息更接近已发生结果"→ 进入边界复核池，不一刀切拒绝**
- 活动结束提醒、任务催促、分享传播 → 仍默认不通过
- 即使目标人群是创作者 / 主播 / 达人等经营型人群，**活动即将结束提醒**若不直接对应其经营权益、资格状态、收益结果，而只是提醒其继续参与活动、投稿、完成任务，仍按**纯活动营销/活动提醒**拒绝；若业务有强诉求，优先建议走**订阅机制**

### 规则 B：真正可通过的结果通知

优先通过：

- 放款成功 / 交易动账 / 资金到账
- 处罚生效 / 权限受限 / 年龄限制生效
- 举报结果已出
- 授权请求到达、等待用户确认
- 协议签署完成且可查阅
- 商责赔付、补偿券、积分、奖励**已实际到账**
- 关键流程受阻且影响用户继续使用

### 规则 C：活动内分三档

- 已获得积分 / 已收到赔付 / 已到账奖励 / 已产生活动结果或荣誉结果 → **可通过**
- **已完成前置任务，奖励已解锁 / 已获得领取资格 / 已可领取** → **可通过**（按结果通知处理；即使文案里出现 claim / claim now，也不能机械打成利益诱导）
- 邀请成功 / 被邀请成功 / 获得活动资格 / 订阅用户收到活动更新 / 特殊经营人群收到活动状态承接（且涉及经营意愿、人群精准）→ **边界池**
- 去做任务拿积分 / 去分享海报 / 去参与活动 / 活动快结束了 / 去上传 / 去投稿 / 去首播 → **拒绝**

### 规则 D：金融类看文案主信息，不看业务自述

先判断**用户是否有主动申请行为在先**：

- **用户已主动申请**贷款/信用额度 → 审批结果通知（approved / disbursement / use your funds）属于结果通知，**倾向通过**，即使文案中带引导语
- **用户未主动申请**，平台主动推送 → claim now / exclusive offer / get approved / fast disbursement 属于金融营销触达，**拒绝**

文案维度的辅助判断：
- was successfully sent / 已放款成功 → 通过
- approved / 获批、即将放款（且用户有申请行为）→ 通过
- claim now / exclusive offer（无用户申请行为）→ 拒绝

### 规则 E：订阅机制是单独可通过通道

前提必须全部满足：

- 用户主动订阅行为真实存在
- 触达人群只覆盖订阅用户
- 不是借订阅名义泛化触达

规范原文：在业务相关场景内给用户提供是否接收某通知的选项，且用户**主动**选择接收该通知。

### 规则 F：人群最小化与必要性的优先级

- 收费规则变更、政策变化：若覆盖潜在用户 → 优先拒绝或要求收敛
- 处罚、年龄限制、举报结果、授权请求：只要用户本人已受影响 → 可通过
- **创作者 / 商家 / 主播 / 达人 / 广告主 / 已开通商业化能力的经营型人群**：若消息与经营意愿、经营权益、经营效果、能力使用收益、商业化资格、经营效率提升直接相关，且**已命中必要性 + 已做人群最小化 + 不属于重复催促**，在此基础上**倾向通过**，不应仅因其属于活动或流程推进就直接否决。注意：必要性按规范原文理解，**满足其一即可**，尤其不能把“与用户行为/利益直接相关的信息”错误排除在外。对于经营型人群，若某条**活动/功能推广本身**就与其经营利益直接相关，且是该活动/能力/经营机会的**首次承接通知**，也可以进入通过或边界通过池，不要求必须等到“结果已发生”或“资格已变化”后才能通过。典型可通过场景：
  - 创作者入驻/认证引导（如 KYC 认证提醒、商家注册完成引导）
  - **身份验证 / 资格流程承接通知**：若用户已完成前置验证或资格状态已推进，当前消息是在承接后续身份/账户配置/资格激活流程，则优先按**资格状态变化后的流程通知**理解，而不是按泛化能力推广拒绝
  - 开播能力推荐（如邀请符合条件的主播使用直播工具）
  - 变现资格通知（如满足某变现项目参与门槛）
  - 经营工具上线通知（如商家后台新功能与其经营直接相关）
  - 面向已投放、已开通能力或已有商业化经营行为的广告主，发送与投放效果提升、能力使用收益、成本优化、经营结果改善直接相关的能力通知/权益通知
- **特殊人群活动消息补充规则**：若目标人群不是泛用户，而是“已订阅用户 / 创作者 / 商家 / 主播 / 达人 / 广告主 / 已获资格用户 / 已进入某经营链路用户”，则不能简单按普通活动消息一刀切；要继续判断：
  1. 该人群是否已具备明确的订阅关系、经营身份、广告投放行为、能力权限或活动资格
  2. 消息是否已命中必要性（满足其一即可）
  3. 是否已做到人群最小化，而不是泛化到可能感兴趣人群
  4. 是否属于该活动/能力/经营机会的首次承接通知，而不是后续催促
  5. 消息是否在承接该身份/资格/订阅关系/既有经营链路，而非泛化拉活
  6. 主信息是否偏“状态更新/资格承接/经营承接/经营机会通知”，还是偏“继续行动召回/利益诱导”
  满足 1+2+3+4+5 时，可进入边界池或通过池；不能仅因文案含活动、奖励、join、try、claim 等词就机械拒绝
- **广告主人群补充判断**：若目标是广告主 / Promote advertisers / SMB advertisers，还要额外看：
  1. 是否已有投放行为、经营行为或能力权限，而不是泛潜客
  2. 是否与其既有经营链路直接相关，而不是单纯拉新试用
  3. 是否已命中必要性（例如“与用户行为/利益直接相关的信息”）
  4. 是否已通过权限、活跃度、历史行为做最小化圈选
  5. 主信息是否在承接经营收益、经营效率提升、能力使用权益或经营机会，而不只是泛化促销本身
  6. 是否属于该活动/能力/经营机会的首次承接通知，而不是后续反复提醒
  同时满足时，应优先进入通过或边界偏通过池；若只是泛化促销、潜客拉新、单纯优惠刺激，或已变成重复催促，仍应拒绝

### 规则 G：含图片素材的消息须额外确认

系统消息如包含图片素材（banner、插图、商品图、活动海报等），**文字工单无法完整反映图片内容是否合规**，需额外向业务方确认图片信息后才能给出最终结论。

**如何识别消息含图片**：
- 工单/PRD 中明确提及"带图""banner""插图""图片素材"
- 模版名称或正文中含图片占位符（如 `{image}`、`{banner_url}`、`{img_src}`）
- PRD 设计稿中可见消息包含图片区域
- 文案描述中提及"查看图片""点击图片"等

**处理方式**：
1. 图片不影响主信息判断 — 先基于文字内容完成主流程审核（步骤 1-9），给出**基于文字部分的阶段性结论**
2. 在 review notes 中标注 `[含图片-待确认]`，并明确需要业务方补充的信息：
   - 图片具体内容是什么（截图或描述）
   - 图片是否包含营销性质的文案/元素（如促销价格、限时标签、利益诱导）
   - 图片是否包含用户隐私信息或合规敏感内容
3. 如果图片本身可能改变结论方向（例如文字是结果通知但图片可能是营销 banner），在结论中注明"最终结论取决于图片内容"

**不需要标记的情况**：
- 系统默认 icon / app logo（非业务自定义图片）
- 纯文字消息，无任何图片相关描述

## 二、营销类消息标准分类（来自规范 FAQ）

以下类型均属于营销/活动引流，应拒绝：

| 类型 | 说明 |
|------|------|
| Promotional Offers and Discounts | 促销优惠、折扣、专属优惠 |
| Limited-Time Offers | 限时促销、倒计时、闪购 |
| Loyalty Programs and Rewards | 积分、会员权益、复购激励 |
| Personalized Marketing Messages | 基于用户数据的精准推荐 |
| Event Promotions | 活动推广、提升注册/参与 |
| Event Reminders | 活动提醒、截止日期提醒 |
| Cross-Selling and Upselling | 关联推荐、增购引导 |
| Referral Programs | 裂变邀请、推荐有奖 |
| Seasonal Campaigns | 节日/季节营销活动 |

## 二点五、最高优先级冲突样例（主 skill 的冲突仲裁在这里给例子）

### 样例 1：`freq_detail` vs `exit_mechanism`
- 场景：`freq_detail=无频控`，但 `exit_mechanism=one time send only`
- 正确口径：**以 `freq_detail` 为准**，最终仍按频控不合规处理
- 错误口径：因为 exit_mechanism 看起来像一次性，就直接通过

### 样例 2：理想一次性写法 vs 系统落地可填写口径
- 场景：消息语义上是一次性通知，但申请系统不支持填写“一次/生命周期一次/同一事件仅一次”，业务只能填 `30天1次`
- 正确口径：**`30天1次` 视为当前系统能力下的合规替代写法**
- 错误口径：仅因没写成理想的一次性表达就拒绝

### 样例 3：订阅授权范围成立 vs 文案看起来像福利/更新召回
- 场景：PRD 已证明用户主动订阅，消息落在授权范围内，但文案是 `Claim your gift pack` / `Open to play the latest version`
- 正确口径：先认定**消息类型本身有发送基础**；若拒绝，应优先拒在**订阅频控不合规 / 前置项不完整**
- 错误口径：回头用“福利召回/版本召回，所以内容本身不能发”直接否掉

### 样例 4：状态可重入 vs 看起来像一次性状态通知
- 场景：age restricted / eligibility state 类消息，历史协作或 PRD 已确认同一用户可多次进入该状态
- 正确口径：先按**可重复状态通知**理解，再看 `freq_detail` 是否匹配
- 错误口径：回退成“一次性通知”口径，仅因 `一天一次` 就拒绝

### 样例 5：当前会话已纠正口径 vs 默认旧判断
- 场景：用户刚在当前会话明确说过某 case 的硬规则或事实前提，但复审时又按旧默认判断
- 正确口径：**当前已纠正口径优先**，后续复审/稳定性测试必须继承
- 错误口径：继续沿用 skill 里更旧、更一般化的默认判断

## 三、频控细则

### 全局频控

非必达消息：**每 5 天最多收到 1 条**（全局频控，各频道共享，平台自动生效）。

审核时不要只检查“有没有频控”，还要检查**频控是否足够严格**。尤其是活动提醒、任务催促、促活、推广类消息，若出现如“每7天30次”“每天多次”“无频控但非必达”等，应视为显著风险。**若最终因此拒绝，写给业务方的拒绝原因里必须明确写出可执行修改方案，不能只停留在“频控不合理”；默认建议口径是：对非必须告知 / 非交易 / 非合规类消息，建议收敛到 `30天1次`。**

不受频控限制的类型：
- 用户行为（举报、下单）直接触发的通知
- 合规、交易动账类的系统通知
- 必达消息（新用户可接收 且 Category 不可退订）

### 同功能/活动频控

遵循**最低频次原则**：除用户行为（举报、下单）直接触发的通知，或合规、交易动账类的系统通知外，同属一功能/活动的信息，至多对单个用户下发**一条**消息通知（触达目的一致，仅文案或下发时间不同的消息仍属同一消息），可设置为 30 天 1 次。

若业务方主张因合规或其他强诉求需要多次触达，也应继续遵循“最低频次”要求，优先收敛频次与打扰范围。

### 频控判断四分法

**补充一条执行原则**：频控判断不只是在“理想业务语义”层面完成，还要同时检查“当前系统里申请人实际能怎么填”。若理想口径与系统落地可填写口径冲突，优先按**系统落地口径**执行；但这条放宽仅适用于已确认的 `30天1次` 替代写法，不适用于 `无频控`。

后续遇到频控争议，统一先把消息分到以下四档，再判断 `freq_detail` 是否匹配：

1. **默认档**：非必须告知、非交易、非合规、非订阅、非可重复状态变更消息 → 默认按 `30天1次`
2. **一次性通知档**：单次异常处置、单次迁移影响、单次开通完成、单次下线通知、一次性补通知 → 应写成“同一事件仅一次 / 生命周期一次”
3. **可重复状态变更档**：同一用户可能多次进入/退出同一状态（如恢复后再次受限、年龄状态反复切换、资格反复生效/失效、风控状态重复命中）→ 不要机械按一次性通知处理；可接受 `一天一次` 或更严格的事件去重型频控，但前提是业务上确有重复触发机制
4. **订阅档**：必须满足 **1天≤1条、1周≤3条**

**关键提醒**：不要把“是状态通知/结果通知”直接等同于“只能发一次”。先判断该状态对同一用户是否可能重复进入；只有天然只会发生一次时，才按一次性通知去要求频控。

### 审核检查项

- "是否有频控"= No 且非必达消息 → 标记风险
- 频控逻辑在外部服务 → 需确认是否真实生效且符合 5 天 1 条标准
- 批量一次性发送 → 不适用周期性频控，但要更严看人群精准度和发送量级

## 四、退订权利细则

- 除合规类消息外，用户对所有消息所在的一级账号或某一消息品类，都有明确的"退订"权利
- 非必达消息的 Category **必须**为可退订类型
- 若非必达消息选了不可退订的 Category → 不合规，需要求修改

## 五、新用户与大人群规则

### 新用户

定义：注册/登陆 **3 天内**的用户。

规范要求：除用户行为（举报、下单）直接触发的通知，或合规、交易动账类的系统通知，**不对新用户下发其他任何消息**。

若工单中"新用户是否可收到 = Yes"但消息不属于上述豁免类型 → 标记为风险。

### 大人群量级

除合规类消息，若下发人群量级超 **10M**，需先小流量 (<10%) 下发验证：
- 转化率 >2%
- CTR >7.5%

满足后才可扩量下发。审核时若发现量级超 10M 且非合规类，应要求业务方说明小流量验证计划。

## 六、冲突样例对照

### 活动类

| 消息 | 旧直觉 | 当前规则 |
|------|--------|---------|
| 邀请成功，有人通过你的邀请加入活动 | 像结果通知，可能通过 | 若主要是裂变承接，先进边界池；若和经营意愿/权益相关且人群精准，可倾向通过；否则拒绝 |
| 你已加入活动 / 被邀请成功 | 像状态变化，可能通过 | 不一刀切；先做边界复核，看是否只是活动承接还是与权益/经营资格直接相关 |
| 你已获得积分 / 奖励到账 | 可通过 | 继续通过，但要确认是"已到账"不是"快去领取/继续完成" |
| 你已完成任务，奖励已解锁 / 已获得领取资格 | 过去容易误判成“claim 激励” | **通过** — 前置任务已完成，主信息是结果已产生，不因 claim 文案改变性质 |
| 活动结束提醒 / 倒计时 / 去完成任务 | 有时误判成必要提醒 | 统一按活动运营提醒拒绝 |

### 金融类

| 消息 | 旧直觉 | 当前规则 |
|------|--------|---------|
| 放款成功 / 资金已发出 | 通过 | 继续高置信通过 |
| 用户主动申请贷款后的 approved / disbursement 通知 | 曾从严拒绝 | **通过** — 用户有主动申请行为在先，属于结果通知 |
| 用户主动申请后的 "use your approved funds" | 曾按营销拒绝 | **通过** — 虽有引导语，但主信息是告知申请结果，需在工单中确认用户有申请行为 |
| 平台主动推送的 claim now / exclusive offer / fast disbursement（无用户申请行为） | 有时被 must reach 干扰 | 统一按促转化金融触达拒绝 |

### 功能推广类

| 消息 | 规范判定 |
|------|---------|
| 向普通用户发送某新功能上线通知 | 拒绝 — 系统消息不用于功能推广，建议用更原生方式触达 |
| 向用户发送关于某账号的推广消息 | 拒绝 — 系统消息不承担"引流"职责，从平台视角推广某账号有不可测风险 |
| 向符合条件的创作者推荐开播工具/直播能力 | **通过** — 目标人群是有经营意图的主播，消息与经营权益直接相关，人群精准 |
| 向创作者发送 KYC/认证完成引导 | **通过** — 与创作者利益直接相关（如提现、税务优惠），属于经营权益通知 |
| 向已投放且已有特定广告能力权限的广告主发送能力使用/经营优化通知 | **通过/边界偏通过** — 目标人群不是泛潜客，消息与既有经营链路和经营利益直接相关 |
| 向潜在广告主或未投放用户发送“来试试广告能力/领优惠去投放” | **拒绝** — 本质仍是泛化拉新或促销刺激，不属于经营承接通知 |

### 特殊通道

| 场景 | 规则 |
|------|------|
| Live APP only（仅在 Live Studio 等直播工具类 App 内触达） | 不在普通系统消息审核标准约束范围内，可通过 |
| Surveys 类 Category | 若人群精准且符合频控，可通过 |

### 订阅类

- 普通活动提醒 → 默认拒绝
- 用户主动订阅后的活动更新/资格提醒 → 只有在订阅真实、只发给订阅用户、且 `freq_detail` 同时满足 **1天≤1条、1周≤3条** 时，才可通过；若只写了日上限或 `freq_detail` 与订阅规范不一致，仍应拒绝
- **一旦已确认属于订阅授权范围，拒绝点必须优先写成“订阅频控不合规 / 前置项不完整”，不能再写成“内容本身不能发”**

### 规则/收费类

- 规则变化通知给明确受影响用户 → 可通过
- 规则变化通知、收费规则变更若泛化到潜在人群 / 普通 TikTok 账号用户 / 未实际受影响人群 → **拒绝或要求收敛**；关键拒绝点是**人群未最小化**，不能只因通知内容重要就放行

## 六点五、这轮复盘新增执行规则（AI 侧）

1. **频控前置，不再后置补充**
   - 在当前执行口径下，先判断 `freq_detail` 能否过，再判断内容类型
   - 即使内容像结果通知/资格承接/经营机会通知，只要 `freq_detail` 不合规，最终先拒在频控
2. **拒因排序按最可整改优先**
   - 对外默认顺序：工单/合规工单缺失 → 频控 → 订阅频控 → emoji/格式 → 人群最小化 → 内容类型
   - 不要优先给业务抽象的大类判断
3. **文案一致性校验是强制步骤**
   - 写回前检查 AI 判断里提到的产品/活动/行为/场景词，是否真的来自本行 `title/content/reason_for_sending`
   - 若不一致，按串案/误读处理，不能写回
4. **区分两层结论**
   - 先回答：消息类型本身是否有发送基础
   - 再回答：当前申请版本为什么能过/不过
   - 不得把“类型可发但当前频控/工单不过”误写成“内容本身不能发”，也不得反过来把“内容本身不该发”误写成“仅需改频控”

## 七、常见误判

1. **活动事件发生 ≠ 必须通过** — "你已成功邀请到人""你已加入活动"不再自动等于可通过，要看是否仍服务于活动承接、裂变、增长
2. **提到利益 ≠ 用户利益相关** — 要看是已到账结果、已解锁结果、已获得领取资格，还是为诱导行动描绘的潜在收益
3. **业务标签不可盲信** — must reach 不是自动通过理由，仍需回到三轴判断
4. **"状态变化"过于抽象** — 活动加入、活动结束、资格获得不一定是系统消息可承接的"关键状态变化"，更稳的口径是：处罚、权限、资金、协议、赔付、举报结果、授权请求、关键流程阻断
5. **功能推广的隐蔽形式** — 面向普通用户的"新功能上线通知""某账号推广消息"都属于拒绝范围
6. **经营型人群不能简单按功能推广拒绝** — 对创作者/商家/主播/达人/广告主等有经营意愿或商业化行为的人群，入驻引导、认证提醒、开播推荐、变现资格、广告能力开放、经营优化通知等与经营权益或经营收益直接相关的消息，在人群精准的前提下倾向通过
6.1 **经营型活动/任务的直接经营利益口径** — 若某条消息面向的不是泛用户，而是**明确收敛的经营型人群**，且消息所邀请参与的**任务 / 活动 / challenge / campaign 本身就是该类人群稳定经营链路的一部分**，完成后可直接带来变现、经营成长、商业合作机会、经营效率提升或其他明确经营收益，则不能仅因文案含 `join` / `invite` / `task` / `challenge` / `get rewards` 就机械按普通活动引导拒绝。此时应先进入**经营利益相关池**判断。判断时拆三步：①消息要用户做什么；②做完后用户能获得什么；③这些收益是否正是该类经营人群天然追求的经营利益。若 ②③ 明确成立，且该人群已被业务按资格/身份/经营链路做过最小化圈选，则该消息类型本身可具备发送基础。
6.2 **区分普通活动奖励与直接经营利益** — 不是所有“有奖励”都算直接经营利益。面向普通用户的签到奖励、泛活动抽奖、投稿娱乐奖励、短期拉活激励，仍按普通活动营销从严；但面向经营型人群的、与其经营身份直接绑定的变现机会、商单机会、经营成长任务、推广合作任务、直播经营挑战等，可视为经营利益相关内容，不应与普通用户活动奖赏混同。
6.3 **经营型活动消息的最终结论仍受其他硬门槛约束** — 即使已认定属于经营利益相关池，也不代表当前版本必然通过。仍需继续检查：是否首次承接通知、是否为重复催促、`freq_detail` 是否合规、工单是否完整、图片/格式是否合规。也就是说，**“消息类型本身可发送”** 与 **“当前申请版本可直接通过”** 必须分开判断。
7. **金融类要先看用户是否有申请行为** — 用户主动申请后的审批结果通知（approved/disbursement）是结果通知，不应按营销触达拒绝。区分关键是"用户是否有主动申请行为在先"
8. **任务完成后的“claim”不等于利益诱导** — 若用户已完成前置任务，消息是在通知奖励已解锁/已获得领取资格/已可领取，则主信息是结果通知，不应因 claim now / claim your reward 这类措辞被机械打成拒绝
8. **工单信息不完整也是拒绝理由** — 即使消息内容合理，若必填字段（合规工单、PRD、目标人群等）缺失，也应拒绝要求补充。特别是当 `reason_for_sending`、`target_users`、`trigger_notice`、`exit_mechanism` 等字段写成“历史模版，待补充”时，应直接视为缺失，不能因为主信息像处罚通知/结果通知/权限提醒就放行
9. **含图片消息不能只看文字就 final** — 消息中若包含图片素材，文字部分可能看起来是合规的结果通知，但图片可能含营销元素（促销 banner、利益诱导图等）。必须标注 `[含图片-待确认]` 并要求业务方补充图片信息
10. **频控不能只过字段，不过强度** — 频控校验缺失的常见表现，不是字段空白，而是默认把明显偏松的频控也视为“已通过”。后续要把频控强度也纳入判断。
11. **频控判断以 `freq_detail` 为准** — 但在当前执行口径下，还要进一步前置：先卡频控，再讨论内容可发性
12. **串案/误读比口径漂移更危险** — 若 AI 理由里的产品名、活动名、用户动作和本行文案对不上，先判为串案/误读，不要直接拿去总结口径差异

13. **频控判断以 `freq_detail` 为准** — 当 `freq_detail` 与 trigger_notice / exit_mechanism / reason_for_unlimited_freq / PRD 文字描述 / 业务口头解释 等其他字段冲突时，必须以 `freq_detail` 为最终判断依据；不能因为其他字段写了 one time sending / service control / 每月一次 / 仅一次，就覆盖 `freq_detail=无频控`、`一天一次` 等明确信号。审批口径要与执行机制保持一致：系统最终只按 `freq_detail` 生效，因此审批也只能按 `freq_detail` 落最终频控结论。
12. **状态可重入时，不要误判为一次性通知** — 对 age restricted / permission restricted / risk state / eligibility state / capability enabled-disabled 这类状态类消息，先判断同一用户是否可能多次进入、退出、再进入该状态。若可能重复进入，则 `一天一次` 或更严格的事件去重型频控可以接受；只有确认该状态天然只发生一次时，才按一次性通知处理。
13. **订阅消息不能只看“已订阅”** — 若消息面向订阅人群，必须继续核查订阅机制是否合规：订阅是否发生在业务自有场景、是否为用户主动订阅、订阅内容是否明确、是否可快捷退订、当前消息是否落在订阅授权范围内。任一不满足，都不能按订阅消息放行。
13. **订阅消息频控仍看 `freq_detail`，且要满足订阅上限** — 订阅不豁免频控。除继续以 `freq_detail` 为准外，还要额外对照订阅规则：一天至多1条、一周不超过3条；超出即不能按订阅消息通过。若因此拒绝，给业务的整改建议也应优先写成**满足订阅频控上限（1天≤1条、1周≤3条）**，不要机械套用普通系统消息的 `30天1次`。
14. **批量回写要防错行/串写** — 只看连续区间、只按顺序写、写后不做 `id` 级 read-back，极易出现把 A case 的判断写到 B case 上。后续必须按 `id -> 行号` 精确映射写回
15. **对外输出要先控长度、再保留信息密度** — 群聊/即时问答里，优先给“结论 + 2~3 条最关键依据”，默认控制在 3 句话或一个短列表内；不要先铺完整长文，再等用户要求精简。需要展开时再补充长版。
13. **拿不到权威文档正文时不要靠经验硬答** — 如果当前问题本质依赖指定规范/权威文档，而我还没读到正文，只能做权限申请、等待授权或明确说暂时不能负责任地回答；不能先用经验印象输出“看起来像对”的泛化总结。
14. **授权链路只在必要时触发一次，并避免重复打扰** — 当搜索能用但正文读取缺权限时，应先确认问题是否真的必须读正文；若必须，则用最小打扰方式请求一次授权，之后等待结果，不要短时间内重复弹多张授权卡或连续多次催授权。
15. **同轮内避免自相矛盾或风格摇摆** — 先说“还没读到正文，不能正式比较”后，就不应紧接着给出一版像正式结论的长答案；如果后续拿到正文再回答，要显式基于新证据输出，保持口径前后一致。
16. **用户当轮纠正后的口径优先于旧判断** — 当用户在当前轮明确指出某条 case 的关键事实或审批规则（如频控应为 `30天1次`、某些字段实际是“历史模版，待补充”），后续对同一 case 的复核、稳定性测试、5次复跑都必须按纠正后的口径收敛，不能继续复用已经被用户否定的旧判断。
17. **身份验证/资格流程承接通知不能机械按能力推广拒绝** — 若用户已完成前置身份验证、资格验证或状态推进，当前消息是在承接后续账户配置、资格激活、流程补完，则应优先理解为资格状态变化后的流程通知。
18. **规则/收费类通知也必须做人群最小化校验** — 即使主信息是收费调整、规则变更、费用说明，只要目标人群扩大到潜客、泛用户、未明确受影响人群，仍应按“人群未最小化”拒绝或要求收敛。
19. **活动结束提醒默认按纯活动营销处理** — 即使目标是创作者/主播等经营型人群，只要消息不是在同步经营权益、资格状态、收益结果，而只是提醒活动要结束、继续投稿、继续完成任务，就应按纯活动营销拒绝；若业务有强诉求，建议转订阅机制。
20. **避免把“需要用户动作”机械等同于营销推广** — 对经营型人群，要额外判断：消息引导用户完成的动作，在完成后是否会直接带来这类人群天然追求的经营权益、经营能力、获客能力、变现能力或收益提升。如果答案是“会”，则不能仅因消息里存在 verify / enable / complete setup / unlock / join / try / claim 等动作导向词，就直接按能力推广拒绝。
21. **经营型人群消息优先判断“动作完成后的结果”** — 审核这类消息时，先拆三件事：①消息要用户做什么；②做完后用户能获得什么；③这些能力/权益/收益是否正是该类经营人群本身想要拥有的。若 ②③ 都成立，且消息已命中必要性并做人群最小化，则应优先进入经营权益/经营收益相关的通过或边界通过池，而不是先入为主按活动推广拒绝。
22. **必要性命中后，不要再反向否认必要性** — 一旦某条经营型人群消息已经满足规范里必要性的任一项（尤其是“与用户行为/利益直接相关的信息”），后续争议点应转到“是否仍属于泛化营销 / 是否人群未最小化 / 是否与既有经营链路无承接”上，而不要再说它“不满足必要性”。
23. **重复引导/催促要单独拦截** — 即使消息面向经营型人群、也满足利益相关与必要性，只要它已经不是首次承接通知，而是同一活动/同一触达目的下的倒计时提醒、任务催促、再次召回参与、反复提醒继续完成，就应拒绝。此时拒绝点不在“利益不相关”，而在“重复引导超出系统消息可承接范围”；如业务确有持续提醒诉求，建议改为订阅机制。
23.1 **首条经营机会通知 vs 后续催做通知** — 对经营型活动/任务类消息，第一条用于承接经营机会、告知可参与并变现/成长的通知，可进入通过或边界偏通过池；但第二条及之后若主信息已转成“快来参加”“继续完成”“活动快结束了”“别错过奖励”，则应优先按重复引导/催促拒绝。不要因为首条有发送基础，就把后续催做也一并放过。
24. **误判防范顺序** — 遇到经营型人群的争议消息，默认按下面顺序自检：
   1. 先判断是否已命中必要性（满足其一即可）；
   2. 再判断是否已做人群最小化；
   3. 再判断是否属于首次承接通知；若已是后续催促，直接偏拒绝；
   4. 再拆清用户动作与动作后的结果，不只看文案表面像不像“推广”；
   5. 如果表格信息不够，必须继续读 PRD 正文，不停留在表格摘要；
   6. 判断重点从“有没有引导动作”切换到“动作完成后得到的是否属于经营权益/收益能力”。
25. **先分开判断“消息类型是否可发送”与“当前申请版本是否可直接通过”** — 某条消息即使在主信息层面属于可承接类型（如资格承接通知、权限结果通知、经营型机会通知），也不等于当前工单版本就能直接通过。后续必须继续完成前置校验、频控、人群最小化、订阅授权范围等检查；其中任一项不通过，都要把最终结论落到拒绝/需调整，不能停留在“消息类型本身可发”。
26. **频控否决优先级不能漏落到最终结论** — 审核时如果已经识别出“主信息可承接，但 `freq_detail` 不合规”，最终结论必须按频控问题收口为拒绝或至少不能直接通过。尤其对资格承接、权限承接、经营机会通知这类容易先被判成“类型可发送”的 case，要强制再问一句：`如果只看 freq_detail，这条还能直接过吗？` 若答案是否，就必须把频控否决真正写进结果，而不是只在分析里提到。
27. **`freq_detail` 是最终频控判断主字段，不能被“one time sending / service control”类表述冲掉** — 若 `trigger_notice`、`exit_mechanism`、`reason_for_unlimited_freq` 或 PRD正文里写了 one time sending、系统内控去重、service control 等信息，但表格 `freq_detail` 仍写成 `一天一次` / `无频控` / `每7天30次` 等明显偏松值，审批结论仍必须以 `freq_detail` 为准从严处理；除非业务明确把 `freq_detail` 本身改到合规值，否则不能按“实际应该只发一次”直接放行。
28. **一次性通知不得用“未来可能再有新事件”来放宽本次 `freq_detail`** — bug 事故通知、迁移通知、开通完成通知等，如果当前申请文案围绕的是某个具体事件的单次告知，那么即使业务说“以后如果有新的 bug / 新的迁移 / 新的开通，会再申请新消息”，也不能据此接受当前 `freq_detail=一天一次`。当前 case 仍应按一次性通知要求，写成“同一事件仅一次 / 生命周期一次”。
29. **订阅频控必须完整体现日上限和周上限** — 订阅消息即使已经写了“一天一次”，若 `freq_detail` 没有同时体现“1周不超过3条”，也不能视为满足订阅机制；应按订阅频控填写不完整处理并拒绝。
30. **已确认有发送基础后，不要再在内容层面重复否决** — 一旦某条消息已经被判断为“消息类型本身可发送”（尤其是订阅授权范围成立、经营型人群经营利益相关、状态类通知属于可重复状态通知等场景），后续若最终不过，应把拒绝点明确落在频控、完整性、图片/格式或其他前置项上；不要在最终结论里再次回头写成“内容本身不能发”。
31. **最终结论必须区分两层** — 每次复核时都要能单独回答：①这条消息类型本身有没有发送基础？②当前申请版本为什么能过/不过？如果这两问答不清，说明把“可发性”和“当前申请可通过性”混了，需要重做。
32. **AI复盘时优先按“误判类型”分组，而不是逐条散讲** — 当用户要求解释 AI 与人工为什么不一致时，优先把 case 归到以下几类：①经营利益相关被误判成普通活动/调研；②结果通知/状态通知被误判成能力推广或流程引导；③权限/资格/规则变更提醒被低估为普通 CTA；④订阅消息把“发送基础”和“当前申请可通过性”混了；⑤资金/赔付/票据/异常修复类结果通知被表面文案带偏。先抽象模式，再举例。
33. **AI复盘模式下，不要把“我对人工的理解”伪装成“人工原始理由”** — 只要用户在做 AI vs 人工对比，就必须把三层信息拆开：人工原始结果/理由、AI原始结果/理由、我对差异的归因总结。没有人工原文时，不能补造“人工大概率是因为……”。
34. **遇到经营型人群 + 调研/活动/奖励词时，先做反向排除** — 不要先按调研招募/活动拉活拒绝；先问：这是不是经营型人群？奖励是不是经营优惠权益/经营收益？动作完成后是不是经营效果提升？只要答案是“是”，就先进入经营利益相关池，再审频控和前置项。
35. **遇到文案里有 claim / verify / confirm / check / tap now 等 CTA 时，先问主信息是否已经发生** — 如果退款已完成、权限已获得但即将失效、贷款已获批、发票已生成、奖励已到账/已解锁、比赛已晋级/胜出，则优先按结果通知判断，不要机械按“有动作引导”拒绝。

## 八、审批 SOP

1. **拿完整输入**：文案、发送场景、发送目的、目标人群、用户是否已有前置行为、是否已有状态变化/结果产出
2. **做前置校验**：合规评估、Channel-Category 匹配性（消息内容是否匹配该 Category 的用途说明）、必达/非必达一致性、Priority、内容格式、**图片素材识别**（规则 G）
3. **做初判**：是否必须告知 / 是否已发生结果 / 是否只是运营转化
4. **做边界复核**：主信息是什么 / 人群是否收敛 / 频控是否合规 / 退订权利是否保障
5. **落结论**：通过 / 拒绝 / 需补充信息
6. **写 review notes**：只写真正支撑结论的原因，不要泛泛复述文案
7. **如需落表**：必须写满全部 7 列（AI审批结果、AI判断逻辑、AI给业务反馈的拒绝原因、AI置信分组、AI置信分组逻辑说明、命中规则编号、前置校验清单）。流程：先读表头定位列号 → 建立 `id -> 行号` 映射 → 读回目标区间确认 `id + title/template_name` → 一次性写入 7 列 → 写完立即 read-back 校验 7 列全部正确 → 批量结束后二次枚举检查漏写与串写

什么叫"完成审批"：已给出明确结论 + 已写清核心依据 + 若有风险点已指出 + 若需落表已完成 **7 列全部写回** 并校验无误。只写了部分列不算完成。

## 九、输出模板

### 通过

- 结论：倾向通过
- 核心依据：属于必须告知 / 已发生结果通知，且后果已生效；或虽在活动/流程场景中，但与经营意愿、经营权益直接相关，且人群精准，不属于泛化运营拉动
- review notes：建议确认目标人群仅覆盖明确受影响用户；若依赖订阅机制，需确认仅触达主动订阅用户

### 拒绝

- 结论：倾向拒绝
- 核心依据：主信息仍是活动引导 / 功能推广 / 运营催促 / 分享传播，不属于必须告知
- review notes：如需重提，建议改为结果通知口径（到账、处罚生效、结果已出），或补充经营权益关联，并收敛到明确受影响用户

### 需补充信息

- 结论：待补充
- 核心依据：当前信息不足以 final
- review notes：需补充完整文案 / 目标人群 / 用户是否已有前置行为 / 是否已有状态变化

### 推荐措辞

**通过**：这条更像必须告知 / 已发生结果通知，不是运营拉动，倾向通过。核心原因：`[原因1]`、`[原因2]`。需要补充确认：`[人群范围校验项]`

**拒绝**：这条主信息还是活动引导 / 功能推广 / 运营催促，不属于必须告知，倾向拒绝。核心原因：`[原因1]`、`[原因2]`。如果要重提，建议收敛到：`[结果通知口径 / 精准人群 / 去营销化表达]`。**若拒绝点包含频控偏松，还要补一句明确改法，且默认必须写成：`频控建议调整为30天1次`**

**面向业务的拒绝原因写法约束**：只写**不符合的点 + 可执行修改建议**，不要把“虽然利益相关/虽然有人群基础但……”这类分析过程写给业务。分析过程留在 AI判断逻辑或 review notes 即可。若拒绝点是频控，整改建议要写**对应场景的频控标准**：普通系统消息写 `30天1次`；订阅消息写 **1天≤1条、1周≤3条**。

**重复引导/催促类拒绝（面向业务）**：直接写成：**不符合系统消息对同一活动/同一触达目的避免重复触达的规范要求；如有必要，可采用订阅制。** 若同时存在频控偏松,继续补一句：**频控建议调整为30天1次。** 不要再向业务展开“虽然利益相关但……”这类分析过程。

**需补充**：目前只能先给阶段性判断：`[倾向通过/拒绝]`。还缺：`[缺失信息]`。补齐后再 final。

**含图片（追加在任一结论后）**：`[含图片-待确认]` 该消息包含图片素材，基于文字内容`[倾向通过/拒绝]`，但最终结论需确认图片内容：`[需要确认的图片信息]`。
