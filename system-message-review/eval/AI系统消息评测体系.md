# AI 系统消息审批评测体系

## 一、目标

用标准化、可量化的方式评测 AI 系统消息审批质量，驱动审核规则持续优化，提升 AI 审批结果的准确性和可信度。

核心逻辑：**评测不只是打分，而是反向驱动规则优化的闭环。**

---

## 二、评测对象

AI 对 TikTok 系统消息/站内信/通知触达的审批结果。

### 审批结论

| 结论 | 含义 |
|------|------|
| `通过` | 消息符合系统消息定位，可以发送 |
| `拒绝` | 消息不符合系统消息定位（营销/活动引流/功能推广等），不应发送 |
| `待补充` | 工单信息不足，无法给出最终判断 |

### AI 输出结构（7 列）

每次审批必须输出以下全部 7 项，缺一不可：

| 字段 | 内容 | 评测用途 |
|------|------|---------|
| AI审批结果 | `通过` / `拒绝` / `待补充` | 准确率计算 |
| AI判断逻辑 | 核心依据，2-4 句话 | 错误归因、wrong_reasoning 判定 |
| AI给业务反馈的拒绝原因 | 拒绝时填写，面向业务方 | 可用性评估 |
| AI置信分组 | `高置信通过` / `高置信拒绝` / `边界需人工看` / `信息不足` | 人工复核优先级排序 |
| AI置信分组逻辑说明 | 为什么归入该置信分组 | 辅助错误归因 |
| 命中规则编号 | 1-3 个规则代码 | 规则命中率计算 |
| 前置校验清单 | 7 项逐项 ✓/✗/— | missed_precheck 判定 |

## 三、审核规则体系

AI 审批依据的规则分三层，全部已沉淀为可执行的 skill 文件：

### 第一层：主流程（SKILL.md 步骤 1-9）

```
明确审核对象 → 前置校验（7 项） → 三轴初筛 → 高置信通过口径 → 高置信拒绝口径 → 边界案例主信息判断 → 人群最小化 → 频控 → 落结论
```

### 第二层：修正规则（review-rubric.md 规则 A-G）

针对复盘中发现的高频误判，沉淀为具名规则：

| 规则 | 作用 |
|------|------|
| A-活动从严 | 活动体系内消息默认从严，不因"状态变化"直接通过 |
| B-结果通知 | 明确哪些才是真正可通过的结果通知 |
| C-活动三档 | 活动内分"已到账/边界池/拒绝"三档 |
| D-金融主信息 | 金融类先看用户是否有主动申请行为 |
| E-订阅 | 用户主动订阅是单独可通过通道 |
| F-经营型人群 | 创作者/商家经营权益相关不能简单按推广拒绝 |
| G-含图片 | 带图片的消息需额外确认图片素材 |

### 第三层：前置校验（7 项）

| 校验项 | 检查内容 |
|--------|---------|
| 工单完整性 | 必填字段是否齐全 |
| 合规评估 | 是否已通过合规评估 |
| Channel-Category 匹配性 | 消息内容是否与所选 Channel-Category 的用途说明匹配 |
| 必达一致性 | 声称必达但 Category 可退订 → 矛盾 |
| Priority | 是否符合 Priority 标记条件 |
| 内容格式 | emoji/超长/大图/敏感内容 |
| 图片素材 | 是否含图片需额外确认 |

### 规则代码体系

每条审核结果必须输出命中的规则代码（1-3 个），用于自动计算规则命中率。完整代码表见 `references/review-rubric.md` 第十一节，分三类：

- **主流程规则**：`4.1-必须告知`、`4.2-结果通知`、`5.1-功能推广`、`5.3-金融营销` 等
- **修正规则**：`规则A-活动从严`、`规则D-金融主信息`、`规则F-经营型人群` 等
- **前置校验**：`前置-工单不完整`、`前置-Channel-Category不匹配` 等

## 四、防错机制：写回前自检

AI 写入审批表前必须通过 4 项一致性检查，防止"结论与逻辑写反"：

| 检查项 | 规则 |
|--------|------|
| 结果 vs 置信方向 | 通过 → 不能配高置信拒绝；拒绝 → 不能配高置信通过 |
| 结果 vs 判断逻辑 | 逻辑说"属于结果通知"但结果写了拒绝 = 必须修正 |
| 拒绝时拒绝原因非空 | 拒绝了但没写拒绝原因 = 必须补上 |
| 命中规则 vs 结论方向 | 只命中 5.x 拒绝类规则但结论=通过 = 必须修正 |

矛盾时以 AI判断逻辑的实际论证方向为准。

## 五、评测指标

### 核心指标

| 指标 | 公式 | 目标 | 说明 |
|------|------|------|------|
| 整体准确率 | 一致数 / 总数 | >90% | AI 结论与人工结论的总体一致程度 |
| 简单案例准确率 | 简单案例一致数 / 简单案例总数 | >95% | 基本盘不能出错 |
| 拒绝召回率 | 正确拒绝数 / 应拒绝总数 | >95% | **最重要**：漏放代价最高 |
| 通过精确率 | 正确通过数 / AI 判通过总数 | >90% | AI 说通过的里面有多少真的该通过 |
| 规则命中率 | 依据命中正确规则的比例 | >85% | 结论对了但引用的规则也要对 |

### 优先级

**拒绝召回率 > 整体准确率 > 通过精确率 > 规则命中率**

漏放（该拒绝没拒绝）的业务风险远大于误杀（该通过没通过）。

## 六、错误分类

对 AI 与人工不一致的案例，按以下四类归因：

| 错误类型 | 含义 | 调优方向 | 优先级 |
|---------|------|---------|--------|
| `false_pass`（漏放） | 人工拒绝但 AI 通过 | 加强拒绝口径 | 最高 |
| `false_reject`（误杀） | 人工通过但 AI 拒绝 | 放宽通过口径或补充边界规则 | 次高 |
| `wrong_reasoning` | 结论一致但依据引用错误 | 修正规则表述 | 中 |
| `missed_precheck` | 未检查前置项 | 强化前置校验 | 中 |

## 七、评测数据集

### 数据来源

从历史审批表中提取，按难度和类别标注后存入 `eval/cases/` 目录。

### 数据格式

每条案例一行 JSON（JSONL 格式）：

```json
{
  "id": "40520578",
  "difficulty": "simple|boundary|controversial",
  "category_tag": "compliance|activity|finance|feature_promo|subscription|rule_change",
  "input": {
    "template_name": "...",
    "channel": "...",
    "category": "...",
    "title": "...",
    "content": "...",
    "send_reason": "...",
    "target_audience": "...",
    "trigger_logic": "...",
    "estimated_users": 98300,
    "new_user_receive": false,
    "frequency_control": false,
    "is_must_reach": false,
    "is_priority": false
  },
  "expected": {
    "conclusion": "pass|reject",
    "reasoning": "...",
    "key_rules": ["4.2-结果通知", "规则D-金融主信息"]
  }
}
```

### 数据集分层

| 数据集 | 内容 | 用途 |
|--------|------|------|
| all-cases.jsonl | 全量案例（含 difficulty 标签） | 整体准确率评测 |
| regression.jsonl | 历史误判案例（AI 与人工不一致） | 回归测试，确认改进不引入新问题 |

按 difficulty 分层：

| 难度 | 典型案例 | 评测重点 |
|------|---------|---------|
| `simple` | 合规通知、纯营销推广 | 基本盘准确率 >95% |
| `boundary` | 金融类、活动体系、经营型人群 | 边界判断能力 |
| `controversial` | 人工之间也有分歧的案例 | 识别体系盲区 |

按 category_tag 分层：

| 标签 | 说明 |
|------|------|
| `compliance` | 合规/安全/处罚类 |
| `activity` | 活动体系（邀请/签到/催促/奖励到账） |
| `finance` | 金融触达（放款/approved/claim now） |
| `feature_promo` | 功能推广/新功能上线 |
| `subscription` | 订阅机制相关 |
| `rule_change` | 规则/收费变更通知 |

## 八、评测流程

### 单轮评测

```
准备案例 → 批量跑 AI 审核（batch-review-writeback skill）
→ 与人工结论逐行对比 → 标记一致/不一致 → 对不一致案例分类错误类型
→ 输出评测报告（各指标 + 错误分布 + 典型错误案例）
```

### 调优闭环

```
评测报告 → 按错误类型聚类 → 定位 SKILL.md / review-rubric.md 中的问题
→ 修改规则 → 重跑 regression.jsonl 确认无回归 → 重跑全量确认改进
→ 将新发现的误判案例收入 regression.jsonl
```

### 调优优先级

1. `false_pass` 最优先修 — 放过了不该放的
2. 边界案例的 `false_reject` 次优先 — 过度保守会影响业务效率
3. `wrong_reasoning` 最后修 — 结论对但依据不精准

## 九、评测表结构

### AI 输出列（7 列）

| 表头名称 | 内容 |
|---------|------|
| AI审批结果 | `通过` / `拒绝` / `待补充` |
| AI判断逻辑 | 核心依据，2-4 句话 |
| AI给业务反馈的拒绝原因 | 拒绝时填写 |
| AI置信分组 | `高置信通过` / `高置信拒绝` / `边界需人工看` / `信息不足` |
| AI置信分组逻辑说明 | 归组原因 |
| 命中规则编号 | 1-3 个规则代码 |
| 前置校验清单 | `完整性✓ 合规✓ Channel-Category✓ 必达✓ Priority— 格式✓ 图片—` |

### 人工复核列（4 列）

| 表头名称 | 内容 |
|---------|------|
| 人工审批结果 | `通过` / `拒绝` |
| 人工拒绝原因 | 拒绝时填写 |
| AI是否准确 | `0` 结果不对 / `0.5` 结果对但逻辑/拒绝原因不对 / `1` 完全匹配 / `2` 结果不匹配但 AI 更合理 |
| 进一步结论 | 补充说明 |

### 打分标准

| 分值 | 含义 | 对应错误类型 |
|------|------|-------------|
| 0 | AI 结论与人工不一致 | `false_pass` 或 `false_reject` |
| 0.5 | 结论一致，但判断逻辑或拒绝原因有误 | `wrong_reasoning` |
| 1 | 与人工完全匹配 | 无错误 |
| 2 | 结论不一致，但 AI 的判断更合理 | 人工标准需修正 |

## 十、批量执行

通过 `batch-review-writeback` skill 实现批量审核和写回：

1. 读取审批表 → 动态定位列 → 自动补齐缺失列
2. 筛选 AI审批结果为空的行
3. 逐行执行 `system-message-review` 全流程
4. 写回前自检（4 项一致性检查）
5. 写入 7 列 → read-back 校验
6. 全部处理完毕后输出汇总统计
