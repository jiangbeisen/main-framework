# 系统消息审核技能

按下面流程执行,不要跳步。遇到边界案例或需要细则时,读取 `references/review-rubric.md`。需要校验 Channel-Category 时,读取 `references/channel-category-map.md`。

## 0. 最高优先级硬规则（先看这个，再看后文）

以下规则优先级**高于其他默认判断直觉**；一旦命中,必须先执行,不能被后文一般性描述覆盖:

1. **频控只看 `freq_detail`**
   - `trigger_notice` / `exit_mechanism` / `reason_for_unlimited_freq` / PRD 文字说明 / 业务口头解释,都只能补充背景,**不能覆盖 `freq_detail`**
   - 在当前执行口径下,**频控是前置硬门槛**: 只要 `freq_detail` 不合规,最终结论不得写“通过”,即使内容本身像结果通知/必须告知
2. **系统落地口径优先于理想口径**
   - 对本应一次性的消息,理想上应写”一次/生命周期一次/同一事件仅一次”
   - 但若系统能力不支持这样填写,而历史协作已确认申请人只能填 **`30天1次`**,则后续必须把 **`30天1次` 视为合规替代写法**
   - **`无频控` 默认不合规**;**唯二例外**:
     - **例外①:用户行为直接触发的事件型结果通知**(举报结果 / 申诉结果 / 退款结果 / 审批结果 / 动账完成 / 放款成功等),若同时满足下述两个条件,可视为合规事件触发型频控,不按”无频控”硬伤拒绝:
       - ①-a 文案主信息是「某事件已发生 / 已处理 / 已完成」的直陈结果回告(`Your X has been Y` / `Your X is Z` / 已到账 / 已退款 / 已完成审核)
       - ①-b `trigger_notice` 描述的触发条件是用户的明确动作(用户提交申诉 / 用户下单 / 用户提现 / 用户举报 / 用户申请贷款)
     - **例外②:用户状态终态已生效告知**(本轮新增,2026-05),若同时满足下述三个条件,可视为合规事件触发型频控:
       - ②-a 文案主信息为「某状态已实际生效 / 已不可逆变更」(`X is now Y` / `X is currently Z` / `unavailable in your region` / 账号已注销 / KYC 已完成 / 年龄段已升级)
       - ②-b 状态变更对**同一用户是终态**(不会反复进入退出;与状态可重入档相反)
       - ②-c 业务侧实际只触达**一次**(系统幂等保障 / 命中身份属性后单次发送)
       - 典型 case:BA 账号已转为 Personal Account(已生效)、账号已注销、终态降级
     - **反例(任一例外都不命中,仍按”无频控不合规”硬伤拒)**:
       - 文案主信息是「将变更 / 即将生效 / 即将降级 / N 天后」等预告类(BA T20/T30 预告 / 邮件授权变更预告 / 费用变更预告)
       - 业务方主动推送的合规告知 / 规则变更告知 / 一次性新功能上线告知,trigger 是身份属性命中而非用户明确动作,且文案为预告或营销
       - 业务自述”用户行为触发”但文案主信息为预告或营销话术(规则D-金融主信息:看文案不看业务自述)
3. **订阅授权范围成立后,先认定“消息类型本身有发送基础”**
   - 一旦确认消息落在用户订阅授权范围内,后续若拒绝,只能优先拒在**订阅频控 / 完整性 / 图片格式 / 前置合规项**
   - **不得再回头用“内容本身不能发 / 福利召回不能发 / 更新召回不能发”直接否掉**
4. **状态重入口径优先**
   - 对 age restricted / permission restricted / risk state / eligibility state 这类状态类通知
   - 若历史结论 / MEMORY / PRD / 工单已表明该状态可重复进入,则后续**不得再退回一次性通知口径**
5. **当前会话已纠正过的 case 口径优先**
   - 若用户/人工已在当前会话明确纠正某条 case 的关键口径,后续复核、稳定性测试、批量审批必须继承,**不得回退默认判断**
6. **先分两层,再落结论**
   - 先判断：**消息类型本身是否有发送基础**
   - 再判断：**当前申请版本是否能通过**
   - 不得把两层混成一句话,导致把“可发但本次不通过”误写成“内容本身不能发”
7. **先分通道 / 人群 / 承接关系,再判是否普通活动**
   - 先看是不是 `Live Studio` / `live APP only` / `Live Studio Event` 等非主端特殊通道
   - 再看对象是不是创作者 / 达人 / 商家 / 主播 / 广告主 / Creator Center 人群 / 核心成长线人群
   - 再看消息是在：①拉人做事；还是 ②承接已经发生的资格/状态/结果/邀请/成长线进展
   - 只有在以上都不成立时,才默认按普通活动拉活/功能推广处理
8. **前置项 / 文案自洽 / 频控 是最终三道闸门**
   - 只要**完整性失败 / 文案与申请说明不自洽 / `freq_detail` 不合规**任一命中,最终结论都不能写“通过”
   - 即使消息类型本身有发送基础,也只能落为**拒绝或待补充**
9. **写回前必须做 case 一致性自检**
   - AI判断逻辑里提到的产品、场景、行为、规则点,必须和当前行 `title/content/template_name` 一致
   - 若出现明显串案关键词,必须重审,不能直接写回
10. **拒因排序按“最可整改优先”**
   - 同时命中多个拒绝点时,对外优先写：**工单/合规工单缺失 → 频控不合规 → 订阅频控不合规 → emoji/格式 → 人群未最小化 → 内容类型不合规**
   - 不要优先输出抽象的大类判断,要优先输出业务最容易直接改的拒绝点
10. **拒因排序按“最可整改优先”**
   - 同时命中多个拒绝点时,对外优先写：**工单/合规工单缺失 → 频控不合规 → 订阅频控不合规 → emoji/格式 → 人群未最小化 → 内容类型不合规**
   - 不要优先输出抽象的大类判断,要优先输出业务最容易直接改的拒绝点

## 0.1 冲突仲裁表（遇到冲突时按下表处理）

| 冲突场景 | 优先规则 |
|---|---|
| `freq_detail` vs `trigger_notice` / `exit_mechanism` / 业务解释 | `freq_detail` 优先 |
| 理想一次性写法 vs 系统只能填 `30天1次` | 系统落地口径优先 |
| 订阅授权范围成立 vs 文案带 `claim` / `join` / `reward` | 先认定有发送基础,再审频控 |
| 状态可重入 vs 看起来像一次性状态通知 | 状态重入口径优先 |
| `freq_detail=无频控` vs 用户行为直接触发的事件型结果通知(满足硬规则 § 2 例外①双条件) | **例外①优先**(视为事件触发型合规,不按"无频控"硬伤拒) |
| `freq_detail=无频控` vs 用户状态终态已生效告知(满足硬规则 § 2 例外②三条件) | **例外②优先**(视为事件触发型合规,不按"无频控"硬伤拒) |
| 状态已生效告知 vs 状态预告类(将变更 / 即将生效) | 已生效告知走例外②;预告类仍按硬伤拒 |
| Channel-Category 不在 map 表 vs 内容与 Category 字面用途相符 | 不前置拒,放行进内容层判断(map 是参考,非白名单) |
| Channel-Category 用途与消息内容明显错配(必达通道 vs 营销内容) | 前置拒,与内容类拒因等优先级 |
| 频控配置「一天一次」对一次性事件偏宽 vs 实际事件单次 | 视为事件去重等价,放行(详见 § 5.1.2 频控偏宽判定决策表) |
| 订阅消息 freq_detail 只写日上限或只写周上限 | 前置拒,要求双上限完整(同时写「一天≤1条 + 一周≤3条」) |
| 当前会话已纠正口径 vs skill 默认旧判断 | 当前已纠正口径优先 |

## 0.2 开始审批前的 10 条短检查（每次都先过一遍）

### 默认规则
- **默认一律按“独立审批模式”执行**
- 只有当用户**明确要求**做对比人工、算准确率、整理不一致 case、参考另一张人工 sheet 回写、或复盘 AI 为什么判错时，才切到**评测/复盘模式**
- 在独立审批模式下，**不要假设存在人工结果、人工信号或人工标准**，也不要为了迎合可能存在的人工口径而提前收缩/放宽结论

1. **我现在审的是“消息类型本身可不可发”，还是“当前申请版本能不能过”？** 不要混
2. **这次任务是不是用户明确要求的评测/复盘任务？** 若不是，就按独立审批模式，不引入人工视角
3. **频控最终是不是只看 `freq_detail`？** 不能被别的字段带跑
4. **如果这是一次性消息，系统是不是只能填 `30天1次`？** 若是，就按系统落地口径，不要拿理想口径卡
5. **如果这是订阅消息，我是否已经确认订阅授权范围成立？** 若成立，就先承认有发送基础
6. **如果这是订阅消息且最终拒绝，我是不是拒在频控/前置项，而不是拒在内容类型？**
7. **如果这是状态类通知，我是否先判断了状态能不能重复进入？** 若能重入，不能按一次性通知拒绝
8. **当前会话里有没有已经纠正过这条 case 的关键口径？** 若有，必须继承
9. **我有没有被“经营利益相关 / 奖励已解锁 / 经营人群”这些长期口径带偏？** 独立审批时，也必须先回到“主信息是否必须告知 + 是否动作导向 + 频控是否硬合规”
10. **最终输出时，我能不能分别回答：①为什么这条消息类型可发/不可发；②为什么这次申请能过/不过？** 若答不清，先别写结论
11. **我有没有把“特殊场景下的承接消息”过早压扁成“普通活动营销消息”？**
   - 尤其检查：经营人群经营收益类、Creator Center 人群、核心成长线、邀请成功后的通知、`ready/approved/available` 类承接文案、live app only 通道

### 0.3 这轮复盘新增的 AI 易错点（极简版，后续默认纳入自检）

后续默认先防 8 类误判：

1. **别被 CTA 词带偏**
   - `claim / verify / confirm / tap now` 不等于营销；先看结果是否已发生
2. **别把经营人群一律打成普通活动**
   - 先看对象是不是创作者/达人/商家/主播/广告主
   - 再看是否直接承载经营收益、经营机会、经营效果
3. **别把订阅消息和普通活动混审**
   - 先判“是否落在订阅授权范围内”
   - 再判“这次申请的频控/图片/完整性是否合规”
4. **复盘时别脑补人工理由**
   - 只区分：人工原始结果 / AI原始结果 / 我的复盘归因
5. **别把“结果通知”默认放宽成可重复通知**
   - 先问自己：这是不是围绕“本次具体事件”的一次性通知
   - 若是单次 bug 事故、单次税务/规则变化、单次迁移影响、单次开通完成、单次资格下线前通知，默认按一次性通知审
   - 只有明确存在“同类状态可重复进入 / 同类事件天然高频重复发生”的证据时，才允许进入可重复通知档
6. **别用业务自述去替代 `freq_detail`，但也别忽视业务自述暴露出的“语义形态”**
   - `freq_detail` 决定最终能不能过
   - 但 `trigger_notice` / `exit_mechanism` / `reason_for_unlimited_freq` / PRD 若明确写了“仅一次 / 每月一次 / 一次性通知”，说明这条消息的**语义形态**应优先按一次性或低频通知理解
   - 后续应据此判断：这次申请版本是否把 `freq_detail` 配错了，而不是反过来把消息语义误放宽
7. **别漏掉“文案与申请说明不对应”**
   - 要同时看 `title/content` 与 `reason_for_sending/trigger_notice`
   - 若申请说的是状态变化/审批结果,但文案看起来像营销/招募/功能推广,优先按**工单不自洽**拒绝
8. **别把别条 case 的判断写到当前 case 上**
   - 写回前快速检查：AI判断逻辑里的产品名/场景名/行为词,是否与本行一致

### 0.4 已沉淀的人工口径(评测复盘累积,优先级 = 硬规则)

每次评测复盘后,把人工已实证接受的口径明面化,后续审批必须直接套用,不再用 SKILL 默认旧判断回卷:

| 口径 | 适用场景 | 落地写法 |
|---|---|---|
| 用户行为触发的事件型结果通知,可写「无频控」 | 举报结果 / 申诉结果 / 退款结果 / 审批结果 / 动账完成 / 放款成功等;触发条件是用户的明确动作,文案主信息是结果回告 | 不按"无频控"硬伤拒,视为事件触发型合规;前提是满足硬规则 § 2 例外①双条件 |
| 用户状态终态已生效告知,可写「无频控」 | BA 已降级转 Personal、账号已注销、年龄段已升级、终态资格变更等不可逆状态告知 | 不按"无频控"硬伤拒,视为事件触发型合规;前提是满足硬规则 § 2 例外②三条件(已生效 + 终态 + 实际单次);**预告类(将变更/即将生效/N天后)仍拒** |
| 经营人群 + 明确现金 / 优惠券激励 + 首次承接,可发 | TikTok GO 投稿赚现金、Promote 完成任务发优惠券、调研给 Promote coupons / ad credits | 不按规则A 一刀切;先看是否命中 5.1 例外 2.1「从宽」一栏 |
| 经营效率提升可视为明确利益点 | 已在使用某经营能力的用户(规则F 例外 3)+ 文案是 `more exposure for same budget` / `higher ROI` / `better targeting` 等可量化经营改善 | 5.1 例外 2.1「利益点」从宽列已扩展;不再因"无具体金额"卡 |
| Channel-Category 不在 map 不构成前置拒 | LIVE / System notifications、Creator monetization / System notifications 等 map 没列出但语义相符的组合 | 按 § 2 第 3 条 A 类处理,放行进内容层判断;仅当用途明显错配(B 类)才前置拒 |
| 订阅消息频控必须双上限 | 任何订阅消息(Plan of Publisher / Subscriptions、Minis、CSI Newsletter、TT Gaming 订阅等) | `freq_detail` 必须同时写出「日上限 + 周上限」(一天≤1条 + 一周≤3条);单维度写法(只写日或只写周)前置拒 |
| 一天一次对 per-user / 全局一次性事件 = 事件等价单次 | 用户 setup 完成 / 订阅成功 / 榜单结算后获奖通知 / 状态终态生效等只发一次的场景 | 不卡频控偏宽,放行(详见 § 5.1.2 决策表) |

**使用规则**:
- 评测后发现新沉淀口径,**必须更新本表**,不能只在某个 case 里隐式应用
- 本表与 SKILL 其它章节冲突时,**本表优先**
- 后续若实操中证伪某条沉淀口径,要从本表撤下并备注证伪 case 编号

## 1. 明确审核对象

从工单中抽取以下信息:

- 消息文案 / 标题 / 正文(必须有)
- 发送原因(必须有)
- 目标人群(必须有)
- 触发逻辑 / 退出机制(必须有)
- 业务方提供的 PRD 等文档(必须有)
- Channel、Category、新用户是否可收到、是否有频控、是否为必达消息、是否优先推荐(Priority)、发送用户量预估
- 用户是否已发生某个行为 / 是否已产生结果或状态变化

**字段核准规则**:在引用工单信息时,先核准原文究竟来自哪个字段(`reason_for_sending` / `target_users` / `trigger_notice` / `exit_mechanism` / `freq_detail` 等),再做解释。不要因为某句话语义上像"触发逻辑"、"退出机制"或"频控"，就跳过字段核对直接复述。输出时优先写成"`trigger_notice` 写的是..."、"`exit_mechanism` 写的是..."。如需进一步推断(例如某条退出机制暴露出重复召回思路),必须先说清**字段事实**,再说**推断结论**,不能把推断当成字段原文。

如果用户没给全,不要凭空补;但能审主信息时,先基于已知信息给阶段性判断,再指出缺口。**注意:阶段性判断不等于可直接放行。只要前置完整性不通过,即使主信息看起来像结果通知、处罚通知、权限提醒,也不能输出"通过",只能输出拒绝。**

## 2. 前置校验

### 2.0 最终结论前三问（强制）

在写“通过”之前,必须连续回答 3 个问题：
1. **前置项都过了吗？**（完整性 / 合规 / 格式 / 图片 / 合规工单）
2. **文案和申请说明自洽吗？**（发送原因、目标人群、触发逻辑是否真的由 title/content 承载）
3. **`freq_detail` 合规吗？**

只要任一答案是否,最终结论**不得写“通过”**。

在进入主判断之前,完成以下校验(有问题直接标记)。**顺序不能改**：先完整性 → 再频控 → 再订阅频控/格式/图片/人群 → 最后才看内容类型。

1. **工单完整性**:必填字段(文案、发送原因、目标人群、触发逻辑、退出机制、合规工单/PRD、发送用户量预估、频控)是否齐全。**即使消息内容本身合理,若必填字段缺失也应拒绝并要求补充**。若 `reason_for_sending`、`target_users`、`trigger_notice`、`exit_mechanism` 等字段写成"历史模版,待补充"或其他明显占位内容,也视为缺失,直接命中工单不完整。**同时做字段位置校验**:若后续判断要引用某个关键信息(如"多次曝光无点击"、"one time sending"、"无频控"),必须先确认它到底写在哪个字段里,避免把 `exit_mechanism` 误说成 `trigger_notice`、把其他字段误说成 `freq_detail`。
   **补充一条字段自洽校验**:若 `reason_for_sending` / `trigger_notice` 描述的是某类消息目的(如"被成功邀请时通知用户"、"结果已产生时通知用户"、"权限变更通知"),但 `title + content` 的信息不覆盖这个目的,则应按**工单信息不自洽 / 发送原因与文案不匹配**处理。此类 case 的核心拒绝点不是单纯文案不好,而是**工单申请的发送原因与实际申请文案主信息不一致**。
2. **合规评估**:是否已通过合规评估,未通过的默认不处理
3. **Channel-Category 匹配性**:读取 `references/channel-category-map.md`,检查消息内容是否与所选 Channel-Category 组合的**用途说明**匹配。**`channel-category-map.md` 是参考样本,不是严格白名单**;CC 错配分两类,处理方式不同:
   - **A 类:CC 选项在 map 中没列出,但语义与消息内容相符** → **不前置拒**,放行进入内容层判断。例:`LIVE / System notifications` 装奖励到账通知、`Creator monetization / System notifications` 装经营人群承接通知 — 即使 map 里没列这个组合,只要 Category 字面用途(系统通知 / 服务类通知)与消息内容相符,不卡 CC
   - **B 类:CC 选项与消息内容用途明显错配** → **前置拒,与内容类拒因等优先级**。典型场景:
     - 把 promote 活动 / 唤醒 / 拉新 / campaign 招募 / 任务催促 塞进 `Account Updates / System notifications`、`TikTok / Announcements`、`Report Inbox` 等必达 / TOP 优先级通道
     - 把金融状态变化告知放在 `Activities` 等可退订通道
     - 把内容举报 / 安全处罚通知塞进 `Activities` / `Surveys` 等非合规通道
   - 判别口径:**先看消息真实内容(营销 / 拉活 / 任务催促 vs 必须告知 / 结果通知 / 状态变更),再看 CC 通道权限属性(必达 / 可退订 / TOP 优先级)是否被滥用**。A 类不卡,B 类必拒
4. **必达合法性**: 满足以下条件任一可以用必达（"出于隐私、安全或其他合规要求必须对用户进行告知的消息"、"用户必须知道的账号相关改动、交易动账、视频下架通知等"、"与用户行为/利益直接相关的信息，例如举报、下单后的物流信息"、"用户点击后有无门槛可获得的利益点，例如达人入驻成为商家佣金可减免、用户收到无门槛获取免费样品的机会"），否则不可以必达
5. **Priority 标记**:仅限"必须 x 分钟内处理"或"与账号/钱相关且需用户操作",不满足则建议去除
6. **内容格式**:不支持 emoji、不允许大图、不允许时事政治/自然灾害内容;**标题和正文都要分别校验**,不要只看正文漏掉标题里的 emoji / 强营销词 / 明显格式问题
7. **图片素材校验**:若消息包含图片(文案中提及图片、工单附有图片素材、模版含图片占位符、或 PRD 中说明消息带图),标记为 `[含图片-待确认]`。图片内容无法仅通过文字工单判断是否合规,需额外向业务方确认图片素材详情。详见 `references/review-rubric.md` 规则 G。
8. **频控是否与消息类型匹配**:默认要求频控为`30天1次`。只有三类例外可以突破该默认基线：①**订阅消息**，但必须同时满足订阅规范 **一天至多1条、一周不超过3条**(`freq_detail` **必须同时写出双上限**,只写"一天1次"或"每7天N次"等单维度写法视为不完整,前置拒;典型不合规写法:`一天一次`、`每7天2次频控`、`每7天3次`,需补齐为「一天≤1条 + 一周≤3条」)；②**结果通知 / 状态变更类消息**，且必须确实存在**短期内多次独立触发**的业务合理性；③**用户行为直接触发、且同类事件天然可重复发生**的通知，可按事件触发频控理解;此类场景若 `freq_detail=无频控`,需额外校验是否满足硬规则 § 2 例外①的双条件(文案主信息为结果回告 + `trigger_notice` 是用户明确动作),满足则视为事件触发型合规,不按"无频控"硬伤拒;不满足则仍按频控不合规处理。**用户状态终态已生效告知**(BA 已降级 / 账号已注销等不可逆状态)若 `freq_detail=无频控`,按硬规则 § 2 例外②校验三条件(已生效 + 终态 + 实际单次),满足则视为合规。**频控判断以 `freq_detail` 字段为准**;不要用 trigger_notice / exit_mechanism / reason_for_unlimited_freq / PRD 文字描述 / 业务口头解释 等任何其他信息去覆盖 `freq_detail` 的结论。**审核时要与实际执行机制保持一致:系统最终只按 `freq_detail` 生效,因此审批也必须只按 `freq_detail` 落最终频控结论。** 若该消息不是订阅消息,也不是结果通知/状态变更类例外,也不是用户行为直接触发的事件型结果通知,则即使它属于经营利益相关、活动奖励、活动参与激励、升级身份后可获得更多经营利益等内容,**也不能突破 `30天1次` 默认基线**。

**频控判断顺序固定为四步**：
- 第一步：先判断这条消息默认是否应按 `30天1次` 理解
- 第二步：若不是默认档,再判断是否属于**一次性通知**、**可重复状态变更通知**、或**订阅通知**
- 第三步：再核对 `freq_detail` 是否与该消息形态一致
- 第四步：若 `freq_detail` 与消息形态冲突,一律按频控不匹配处理

**一次性通知识别**：若消息从业务语义上应当是**一次性通知**（如单次异常处置、单次迁移影响、单次功能开通完成、规则/功能下线前通知、一次性补通知）,理想口径下 `freq_detail` 应写成“一次/生命周期一次/同一事件仅一次”；若写成“一天一次”“一周一次”等更宽表达,按**频控与消息形态不匹配**拒绝。**不要因为业务说“理论上以后可能再发生一次新的事故/新的迁移/新的开通”,就放宽当前这条消息的频控。** 对 bug 事故通知、迁移通知、开通完成通知等 case,如果业务语义上是围绕**本次具体事件**的单次通知,就必须要求 `freq_detail` 收敛到“同一事件仅一次”。

**系统落地口径补充（强制）**：若我们已知当前审批系统/提单系统**无法让申请人把 `freq_detail` 明确写成"一次/生命周期一次/同一事件仅一次"**，则在这类一次性消息场景下，业务若填写 **`30天1次`**，应视为**满足当前系统能力下的最低频次要求**，不得再仅因它没有写成理想的一次性表达而拒绝。也就是说，后续审批要同时区分：①**理想频控口径**；②**系统可落地口径**。在系统受限前提下，`30天1次` 可视为一次性消息的合规替代写法。**对一次性合规告知 / 状态告知 / 规则变更告知**(非用户行为触发),`无频控` 仍然不合规;**对用户行为直接触发的事件型结果通知**(且满足硬规则 § 2 双条件),`无频控` 视为事件触发型合规,不按硬伤拒。

**可重复状态变更通知识别**：若同一用户在生命周期内**可能多次进入、退出、再进入**同一种状态（例如权限受限后恢复、恢复后再次受限；满足年龄要求后又再次不满足；风控状态反复命中；资格状态反复生效/失效），则这类消息**不要机械按一次性通知处理**。此时应先判断：这种状态对同一用户是否存在真实的重复触发机制。若存在，则 `一天一次` / 更严格的事件去重型频控可以接受；若不存在，仍应按一次性通知要求收敛。

**状态重入优先规则（强制）**：只要消息属于 age restricted / permission restricted / risk state / eligibility state 这类状态类通知，且我们**已有历史结论、长期记忆、PRD正文或工单描述**表明该状态对同一用户可能重复进入/重复触发，则后续审批时**不得再回退成“一次性通知”口径**，也不得仅因看到 `一天一次频控` 就直接拒绝。必须先按“可重复状态通知”理解，再判断当前 `freq_detail` 是否与该重入机制匹配。只有在**没有任何证据支持状态可重入**时，才允许回到一次性通知口径。

**若最终因频控偏松而拒绝,给业务方的拒绝原因里必须明确写出可执行修改方案：系统消息默认建议按同一功能、同一触达目的收敛到 `30天1次`; 订阅消息则应明确写为满足“1天≤1条、一周≤3条”的订阅频控要求; 一次性通知则应明确写成“生命周期一次/同一事件仅一次”。若消息类型本身有发送基础，但最终卡在频控，也要把结论写成“消息类型本身有发送基础，但当前 `freq_detail` 不合规，因此拒绝”，不要误写成“消息类型本身不该发”。**

**执行优先级补充（本轮新增）**：在当前执行口径下，频控校验优先于内容可发性判断。也就是说，若某条消息虽然在内容上可解释为结果通知/资格承接/经营机会通知，但 `freq_detail` 仍不合规，则最终结论必须先拒在频控，不要先输出高置信通过再在补充里说“频控有点问题”。同时，对外拒因排序默认优先写频控，不要优先展开抽象内容分类。**

**执行优先级补充（本轮新增）**：在当前执行口径下，频控校验优先于内容可发性判断。也就是说，若某条消息虽然在内容上可解释为结果通知/资格承接/经营机会通知，但 `freq_detail` 仍不合规，则最终结论必须先拒在频控，不要先输出高置信通过再在补充里说“频控有点问题”。同时，对外拒因排序默认优先写频控，不要优先展开抽象内容分类。**
9. **人群最小化严格校验**:即使主信息本身属于规则变更、费用变更、资格变化等可承接类型,也要继续核查目标人群是否只覆盖**明确受影响用户**。若目标人群扩大到潜客、泛用户、仅有账号但未实际受该规则/收费影响的人群,则应按**人群未最小化**拒绝,不能仅因"通知内容重要"就放行。
10. **写回一致性校验**:批量审批或写表前,再快速核对一次：AI判断逻辑中的产品/活动/能力/场景词,是否与当前行 `title/content/template_name` 一致。若不一致,按串案处理,重审后再写回。

## 3. 三轴初筛

1. **是否属于必须告知** → 偏通过
2. **是否与用户已发生的行为或利益直接相关** → 偏通过
3. **是否本质上只是功能推广、活动引流、运营催促** → 偏拒绝

## 4. 高置信通过口径

### 4.1 必须告知类

- 合规 / 安全 / 隐私 / 处罚 / 年龄限制类通知
- 对明确受影响用户必须同步的规则变更
- 用户必须知道的账号改动、交易动账、视频下架

核心特征:不发会影响知情权;业务方在履行告知义务,不是在拉动用户做事。

### 4.2 已发生事实或结果通知类

- 交易动账、资产状态变化、权限变更
- 账号绑定 / 授权请求 / 安全操作结果
- 举报结果、审核结果
- 用户发起行为后的结果回告
- **用户完成任务/达成门槛后的结果通知**(如奖励已解锁、已获得领取资格、毕业奖励已可得),即使文案中带有 claim / 领取 / 使用奖励 等动作引导,只要用户确实已完成前置任务且结果已产生,主信息仍是结果通知
- **用户主动申请后的审批结果**(如贷款申请获批/放款、认证申请结果),即使文案中带有"use your funds"等引导语,只要用户确实发起过申请且结果已产生,主信息仍是结果通知

核心特征:事实已发生、状态已变化、结果已产出;用户收到的是"结果通知",不是"行动召回"。

### 4.3 无门槛可获得利益点

用户点击后有**无门槛**可直接获得的利益点(如达人入驻佣金减免、免费样品)。注意与"利益诱导"区分:无门槛直接获得 → 可通过;需完成动作才能获得 → 按拒绝处理。

## 5. 高置信拒绝口径

### 5.1 功能推广 / 活动引流 / 运营催促

新功能推广、面向**普通用户**的活动拉新/拉活、任务催促、裂变激励、分享海报、继续完成任务/邀请/探索功能、利益诱导，默认不通过。

但这里有 3 个重要例外，别机械拒绝：
1. **已完成前置任务 / 已达成门槛 / 已产出结果**
   - 若消息是在通知**奖励已解锁 / 已获得领取资格 / 已可领取**，优先按 `4.2-结果通知` 处理，不因 `claim` 文案自动拒绝
2. **经营型人群的经营利益相关消息**
   - 若对象是创作者 / 达人 / 商家 / 主播 / 广告主 / 已开通商业化能力用户
   - 且消息与**经营收益 / 经营优惠权益 / 经营机会 / 经营效果提升 / 商业化资格 / 能力使用收益**直接相关
   - 且已满足**必要性 + 人群最小化 + 非重复催促**
   - 则先认定”**消息类型本身有发送基础**”，不要仅因有 `join` / `claim` / `setup` / `unlock` / `try now` 等动作词就直接拒绝

   **2.1 投稿 / 参与激励类 campaign 的边界判别(从严 vs 从宽)**

   面向经营型人群的 campaign 招募 / 投稿激励常被规则A 误伤,执行时按下表判别:

   | 维度 | 从宽(进 5.1 例外,可发) | 从严(规则A 拒,改订阅 / 站内 banner) |
   |---|---|---|
   | 利益点 | ① 明确现金 / 优惠券 / ad credits / Promote coupons(有具体金额);**② 已在使用某经营能力的用户**(规则F 例外 3)的经营效率提升类(`more exposure for the same budget` / `higher ROI` / `better targeting` / `more total reach`),即使无具体金额也可视为明确利益点 | 无明确利益点 / 仅”特别支持” / “更多曝光” 但对象**不是已使用经营能力的用户** / 偏社群引导 |
   | 触达定位 | 首次告知活动 / 首次告知奖励 | 同一活动倒计时 / 任务催办 / “再做一个就有”反复催促 |
   | reward 状态 | 用户参与/完成 X(明确动作)即可获得 Y(明确金额) | “再做一个就有奖” / “Continue to next stage” / “还差一步”(reward 尚未真正解锁) |
   | 频控 | `30天1次` 或事件触发型 | 一周一次 / 一天一次 等反复推送 |

   **典型从宽 case**:
   - TikTok GO Golden Week campaign「投稿出游内容拿最大 2400 円」(经营人群 + 明确现金 + 首次邀请) → 通过
   - Promote「完成任务发优惠券」奖励已 unlocked 的承接通知(已发奖) → 通过
   - 调研招募 + 完成后给 Promote coupons / ad credits 等经营激励(参考第 6 节 Surveys 类) → 通过
   - 已活跃 Promote 广告主的经营效率提升告知(`more total exposure for the same budget`) → 通过(规则F 例外 3 + 利益点扩充档)

   **典型从严 case**:
   - L0 Creator Open Chat 招募(无明确利益点,偏社群引导) → 拒
   - “Just one more task to earn your reward” / “Continue to the next stage”(reward 未解锁,任务催促) → 拒
   - 同一活动反复推送 / 倒计时提醒 / 报名后未做任务的二次召回 → 拒

3. **已在使用某经营能力的用户**
   - 例如已投放 `Promote` 的广告主，对该能力天然存在经营意愿
   - 若消息是在通知更好的经营效果、更多曝光、更高 ROI、更强经营效率，也优先进入经营利益相关池

**重复催促仍从严**：即使消息属于经营利益相关，只要已经变成同一活动/同一触达目的下的**倒计时提醒 / 任务催办 / 再次召回参与 / 反复提醒继续完成**，仍应拒绝；如有持续提醒诉求，建议改订阅机制。

详细边界、经营型人群判断三步法、研究/调研 + 经营权益纠偏案例，统一看 `references/review-rubric.md` 的 `规则F-经营型人群` 与“常见误判”章节。

### 5.1.2 频控偏宽判定决策表(用户行为/状态触发的事件型 4.2 结果通知)

| `freq_detail` | 实际触发语义 | 判决 |
|---|---|---|
| `无频控` | 业务声明"事件触发去重",且满足硬规则 § 2 例外①或例外②条件 | **通过**(视为事件触发型合规) |
| `无频控` | 业务方主动推送 / 预告类 / 不满足例外条件 | **拒**(频控硬伤) |
| `一天一次` | 实际 per-user 单次(setup 完成 / 订阅成功 / 状态终态已生效) | **通过**(事件去重等价,不卡频控偏宽) |
| `一天一次` | 实际全局单次(榜单结算 / 活动结算后获奖通知) | **通过**(事件去重等价) |
| `一天一次` | 同一活动期内可能反复推送给同一用户 / 二次召回 / 任务催促 | **拒**(频控反复推送) |
| `一周一次` 及以上但低于 `30天1次` | 任何场景 | **边界**:看是否反复推送同一活动;若实际单次按通过,若反复按拒 |
| `每7天N次` / `每月N次`(N>1) | 同一活动反复推送 | **拒**(频控反复) |
| `30天1次` | 任何场景 | **通过**(默认基线) |
| 一次性消息但写 `30天1次` | 系统受限只能填 `30天1次` | **通过**(系统落地口径,硬规则 § 2) |

**落地原则**:对**一次性事件**(per-user 一次 OR 全局单次结算),`一天一次` 视为事件去重等价,不卡"频控偏宽"。仅当频控配置导致**同一用户在同一活动期内反复收到**时,才按频控反复拒。


### 5.2 强营销导向的金融触达

**未经用户主动申请**的金融营销触达:claim now / get approved / fast disbursement / exclusive offer → 即使业务方说 must reach,也优先按促转化拒绝。

**注意**:若用户已主动申请贷款/信用额度,且消息是告知审批结果(approved / disbursement),则属于 4.2 结果通知,不在此拒绝范围内。区分的关键是**用户是否有主动申请行为在先**。

## 6. 边界案例:先判断"主信息"

很多消息同时包含"结果通知 + 引导语",不要被局部措辞带偏,要判断**主信息**。

- 主信息是"已发生/已到账/已生效" → 倾向通过
- 主信息是"继续参与/完成任务/探索功能/领取/分享/促首播" → 倾向拒绝
- 若消息面向**特殊人群**（创作者/商家/主播/达人/广告主/已订阅用户/已获得资格用户），先额外判断四件事：
  1. 该人群是否已具备经营意愿、商业化行为、明确资格或订阅关系
  2. 消息是否与经营权益 / 经营效果 / 能力收益 / 资格状态 / 订阅关系直接相关
  3. 是否已命中必要性并做人群最小化
  4. 是否属于**首次承接通知**，而不是后续催做
- 若 1-4 基本成立，则先进入边界偏通过池，而不是机械按普通活动营销拒绝
- **活动即将结束提醒**、**倒计时提醒**、**继续参与/继续投稿/继续完成任务**，即使面向经营型人群，若不直接对应经营权益、资格状态、收益结果，仍按纯活动营销/重复催促拒绝
- **活动入场承接通知**可单独看边界：若用户已被拉入活动、但若不用系统消息就可能不知道入口或无法承接，且缺少更自然稳定的送达路径，可按一次性承接通知进入边界池；但不能升级成必须告知，也不能后续反复催促
- **用户主动触发通知他人**也可单独看边界：若平台是在承接用户A的明确动作、通知明确的用户B，且不送达会影响双方既有利益承接，可进入边界偏通过池；否则仍按普通活动催做处理

**一句话区分**：普通用户重点看“已发生结果”还是“诱导继续行动”；经营型人群则先看“是否利益直接相关 + 是否首次承接 + 是否已最小化”，再决定是否进入边界池。

**特殊通道**:

- **Live APP only**(仅在 Live Studio 等直播工具类 App 内触达的消息):不在普通系统消息审核标准约束范围内,可通过
- **Surveys 类**:若 Channel 对应 Category 为 Surveys 类型,且人群精准、符合频控,可通过。补充说明：若面向的是**经营型人群**，且完成调研后给予的是 `Promote coupons` / 商业化优惠券 / `ad credits` 等**经营相关激励**，则不能再把它按“普通调研招募”从内容层面直接拒绝；应先认定其与经营利益相关，再继续审频控及其他前置项。若最终仍拒绝，优先拒在频控/完整性等硬伤，而不是内容类型本身。
- **订阅消息专项**:当消息声称面向"已订阅用户/已订阅消息号/订阅人群"时,不能只因"已订阅"就直接通过。必须额外结合订阅 PRD/规范正文核查:①订阅行为是否发生在业务自有场景,而非系统消息场景;②是否为用户主动订阅,而非默认订阅/行为等同订阅;③订阅内容是否明确告知;④是否提供同级、快捷退订入口;⑤先确认**授权范围是否成立**,再继续判断**当前申请消息是否真的落在这个范围内**。**第⑤项必须结合 PRD/规范正文判断,不能只看表格字段或消息表面类型。** 若表格信息不足以确认授权范围,必须继续读取对应 PRD/规范正文后再判断;不能在未读 PRD 的情况下直接按订阅消息通过。**若结论里涉及“是否属于用户订阅授权范围”判断,必须在 AI判断逻辑或 review notes 中明确写出一句：`根据PRD中用户订阅时被授权接收的消息范围，当前消息属于/不属于该范围。` 若写不出这句,说明 PRD 还没读透,不能提交。若当前 PRD 只有业务玩法/活动逻辑/通知文案,但**没有用户订阅入口、订阅授权文案、退订路径或订阅流程 Demo**，则不能视为订阅授权范围已被充分证明；此时应按**信息不足拒绝/需补充材料**处理，并明确要求业务补充**包含订阅流程信息的 PRD / Demo** 后再提审。**若已读到订阅流程图/设置页/弹窗 demo，并能明确看到用户在业务内主动触发订阅、显式打开开关或点击确认、且授权文案指向某个具体小程序/业务的 updates、notify、福利、体力恢复、内容更新等消息，则可据此认定“授权范围成立”；这种图示证据与正文描述具有同等效力，不必拘泥于必须出现长篇文字说明。**

  **订阅口径放宽补充**: 在用户已主动订阅的前提下,对“是否落在授权范围内”的判断可以**适当放宽**,不必机械要求消息只能是纯结果通知/纯状态更新。若 PRD 中授权的是某类任务/活动/业务的 updates、notify、reminder 等范围,则当前申请消息即使带有一定动作引导(如 `publish now` / `join now` / `claim now`),只要其主信息仍可合理解释为该任务/活动/业务的**更新、提醒、参与相关通知**,即可视为**属于授权范围**,而不再机械按普通活动引导排除。也就是说,对订阅消息,**“属于授权范围”** 与 **“主信息带有参与引导”** 可以并存;只要授权范围本身覆盖更新/提醒/参与相关通知,就可以进入通过判断。  
  但要注意: **授权范围成立**只代表用户同意接收某类消息,不代表当前申请消息当然可发;仍必须继续判断当前消息的频控、文案、图片、前置合规项等是否满足要求。以上任一不满足,仍不得按订阅消息放行。**频控仍以 `freq_detail` 为准**,同时订阅消息的频控标准需满足: **一天至多1条,一周不超过3条**;超出即不能按订阅口径通过。**强制纠偏**：一旦已经确认“当前消息落在订阅授权范围内”，后续就**不得再用“这不是必须告知 / 属于福利召回 / 属于更新召回，所以内容本身不能发”**作为直接拒绝理由。此类 case 若最终拒绝，必须优先拒在**订阅频控不合规、工单不完整、图片/格式风险、或其他前置硬伤**上，而不是把“有发送基础的订阅消息”重新打回成“内容类型本身不该发”。

遇到活动类、金融类、订阅类等边界案例时,读取 `references/review-rubric.md` 中的修正规则 A-F 和冲突样例。

## 7. 人群最小化

- 是否只发给**明确受影响用户**?"可能感兴趣"等群体不应在发送人群中
- 对**特殊人群活动消息**额外判断:如果目标人群已具备订阅关系、经营身份、活动资格、经营成长链路身份,不要机械按"普通活动消息"处理;要审查其是否已做到最小化圈选,且消息是否服务于该特殊人群的经营/资格/订阅承接
- 新用户(注册/登陆 3 天内):除用户行为触发或合规/交易动账类通知外,不对新用户下发
- 量级 >10M(非合规类):需先小流量 (<10%) 验证转化率 >2% 且 CTR >7.5%

## 8. 频控

- **最低频次原则**:除用户行为(举报、下单)直接触发的通知,或合规、交易动账类的系统通知外,**同属一功能/活动**的信息,至多对单个用户下发一条消息通知;即使文案不同、发送时间不同,只要触达目的一致,仍按同一消息从严处理。由于平台能力限制,配置为30天1次时,可视为满足该最低频次要求
- **默认档**:拿不准时,先按 `30天1次` 理解,只有明确命中例外时才放宽。**补充一条执行优先级**：若历史协作中已明确“受系统限制,某类本应一次性的消息只能由申请人填写为 `30天1次`”，则后续审批必须优先采用这条**系统落地口径**，不能再回退到“没写成一次/生命周期一次所以拒绝”的理想口径。
- **一次性通知档**:单次异常处置、单次迁移影响、单次开通完成、单次规则/功能下线通知、一次性补通知等,应按“同一事件仅一次/生命周期一次”理解
- **可重复状态变更档**:若同一用户可能多次进入/退出同一种状态,例如权限恢复后再次受限、年龄状态反复切换、资格状态反复生效/失效、风控状态重复命中,则不要机械要求“一次性”;可以接受 `一天一次` 或更严格的事件去重型频控,但前提是业务上确有重复触发机制,且 `freq_detail` 明确写出相应控制方式
- **订阅通知档**:必须满足 **一天至多1条、一周不超过3条**。若 `freq_detail` 只写了“一天一次”但没有同时体现“一周不超过3条”，也应按**订阅频控不完整**拒绝；不能因为它已经写了日上限，就默认周上限也成立。**若某条消息已经确认属于订阅授权范围，则这里的拒绝点必须写成“订阅频控不合规”，而不是再回退成“内容属于福利召回/更新召回所以不能发”。**
- **经营机会通知的频控补充**:对经营型人群的经营机会/经营能力通知,即使消息类型本身可发送,也不代表可以高频反复触达。若该消息不是必须告知、不是结果通知/状态变更,且不属于订阅消息,则应按**系统消息最低频次原则**处理,默认建议频控收敛到 `30天1次`。不要因为它属于经营型人群、且利益相关,就默认接受 `一天一次`、`一周一次` 等更高频次。
- 因合规或其他业务强诉求需进行多次触达的信息,也必须严格遵循最低频次原则,优先减少用户打扰

**频控判断口径补充**：不要把“是否属于结果/状态通知”与“是否只能发一次”画等号。结果/状态通知里有两类：一类是天然一次性的结果通知；另一类是状态可能反复进入的通知。后者应先判断状态是否可重入,再判断 `freq_detail` 是否匹配。**若人工已经在当前会话或历史协作中明确纠正过某个具体 case/类型“该状态可以重复进入”，则后续稳定性测试、复审或再次批量审批时，必须继承这条纠正后的口径，不能重新退回“一次性通知”默认判断。**

细则见 `references/review-rubric.md`。

## 9. 落结论

在落最终结论前,若用户在当前轮明确纠正了某条 case 的关键审批口径(例如某字段实际为"历史模版,待补充"、频控应收敛到 `30天1次`、某事实前提并不成立),后续对同一 case 的复核、稳定性测试、5次复跑,必须以**纠正后的口径**为准,不得继续沿用已被否定的旧判断。

### 9.1 判定顺序

0. 前置校验(第 2 节)
1. **Step A：先判断“消息类型本身是否有发送基础”**
   - A1. 排除明显不承接类型(面向普通用户的功能推广、活动引流、任务催促、分享传播)
   - A2. 是否必须告知(合规、安全、处罚、授权请求、规则变化)
   - A3. 是否外部后果已生效的结果通知(资金到账、权限变化、举报结果、赔付到账)
   - A4. 活动体系专项(到账可通过、已解锁/已获得领取资格可按结果通知处理、邀请/加入进边界池、继续引导拒绝)
   - A5. 特殊人群活动专项(若目标为创作者/商家/主播/达人/广告主/订阅用户/已获资格用户,先判断是否已命中必要性 + 是否已做人群最小化 + 是否属于首次承接通知;若三者成立,再判断其是否属于经营权益/经营收益/资格状态/订阅关系/经营机会承接,再决定通过、边界或拒绝。**若消息已经明确发给被业务圈定的经营机会适格人群,且文案核心是在告知其可通过参与/投稿等动作获得直接经营收益,不要仅因存在 `invite` / `join` / `reward` 表达就退回普通活动引导池。** 若已是重复提醒/催促,直接拒绝并建议订阅机制)
   - A6. 金融类专项(放款成功通过、approved 边界池、claim now 拒绝)
   - A7. 订阅专项：若已确认属于订阅授权范围,则此步必须给出“**消息类型本身有发送基础**”的结论
2. **Step B：再判断“当前申请版本是否能通过”**
   - B1. 人群最小化
   - B2. 频控
   - B3. 图片/格式/其他前置合规项
   - B4. 最终输出为：通过 / 拒绝 / 需补充信息

**强制要求**：最终判断中必须能明确区分这两层——
- `消息类型本身有发送基础，但当前申请版本不通过`
- `消息类型本身就没有发送基础`

不得把前者误写成后者。

### 9.2 输出格式

- **结论**:通过 / 拒绝 / 需补充信息
- **前置校验清单**:逐项列出每项校验结果(✓通过 / ✗不通过 / -不适用),包括:工单完整性、合规评估、ChannelCategory、必达、Priority、内容格式、图片素材
- **核心依据**:1-3 条
- **拒因排序**:若为拒绝,默认按“工单/工单不自洽 → 频控 → 订阅频控 → 格式/图片 → 人群 → 内容类型”择最可整改项写给业务
- **命中规则编号**:列出本次判断依据的规则代码(见 `references/review-rubric.md` 附录:规则代码表)
- **review notes**:只写支撑结论的补充判断;若消息含图片,必须在 review notes 中注明 `[含图片-待确认]` 并说明需要业务方补充哪些图片信息;**若拒绝点包含频控偏松,则在 review notes 或 AI给业务反馈的拒绝原因里,至少一处要明确写出业务修改建议,且默认必须落到 `30天1次` 这一标准建议值**；若拒绝点是**重复引导/催促**,则建议明确写出：**不符合同一活动/同一触达目的避免重复触达的规范要求；如有持续提醒诉求，建议改为订阅机制**。注意:即使 review notes 中保留了"该消息类型本身有发送基础"之类分析,也不能把这部分泄露到面向业务的拒绝原因中。

推荐措辞模板和审批表写法见 `references/review-rubric.md`。

## 9.3 评测 / 复盘模式（仅在用户明确要求时启用）

只有用户明确要求“对比人工 / 算准确率 / 整理不一致 / 复盘误判”时，才启用本节。

### 9.3.1 三层信息必须拆开

1. **人工原始事实**：人工审批结果、人工拒绝原因
2. **AI原始判断**：AI审批结果、AI判断逻辑、AI拒绝原因
3. **我的复盘归因**：为什么不一致

规则：
- 人工拒因只抄原文，不改写、不脑补
- 人工列为空，就明确说为空
- “我理解人工为什么这么判”只能放复盘，不要写回人工列

### 9.3.2 不一致清单怎么筛

只按这一条筛：
- `AI审批结果 ≠ 人工审批结果`

不要把“结果一致但理由不同”混进去。

### 9.3.3 `AI是否准确` 简化规则

- 结果不一致 → `0`
- 结果一致，但关键理由不一致 → `0.5`
- 结果和关键理由都一致 → `1`

### 9.3.4 复盘模式下的额外自检

1. 先确认有没有**串写/错位**：若 AI理由和本行消息明显对不上，先标记为串写，别急着总结口径
2. 再区分是真分歧，还是只是前置材料缺失
3. 复盘结论里明确写方向：
   - `AI更保守`
   - `人工更保守`
   - `不是口径分歧，是串写/回写错误`

## 10. 审批表写回

写回审批表时,**必须写满以下全部 7 列**,缺一不可:

| 列 | 表头名称 | 内容 | 是否必填 |
|----|---------|------|---------|
| 1 | AI审批结果 | `通过` / `拒绝`  | 必填 |
| 2 | AI判断逻辑 | 核心依据,2-4 句话 | 必填 |
| 3 | AI给业务反馈的拒绝原因 | 拒绝时只写**不符合的点 + 可执行修改建议**，不要展开“也有通过基础但……”这类分析过程; 通过/待补充时留空 | 拒绝时必填 |
| 4 | AI置信分组 | `高置信通过` / `高置信拒绝` / `边界需人工看` | 必填 |
| 5 | AI置信分组逻辑说明 | 为什么归入该置信分组,1-2 句话 | 必填 |
| 6 | 命中规则编号 | 1-3 个规则代码,逗号分隔(代码表见 `references/review-rubric.md` 第十一节) | 必填 |
| 7 | 前置校验清单 | 7 项逐项结果,格式:`完整性✓ 合规✓ Channel-Category✓ 必达✓ Priority- 格式✓ 图片-` | 必填 |

### 写回前自检(必须在写入前完成)

写入表格之前,**逐项核对以下一致性检查**,任何一项不通过则修正后再写入:

1. **结果与置信方向一致**:
   - AI审批结果=`通过` → AI置信分组只能是 `高置信通过` 或 `边界需人工看`,不能是 `高置信拒绝`
   - AI审批结果=`拒绝` → AI置信分组只能是 `高置信拒绝` 或 `边界需人工看`,不能是 `高置信通过`
   - 如发现矛盾,以 AI判断逻辑的实际论证方向为准,修正 AI审批结果 或 AI置信分组
2. **结果与判断逻辑一致**:AI判断逻辑中的论证方向(倾向通过 / 倾向拒绝)必须与 AI审批结果一致。如果逻辑说"属于结果通知/必须告知"但结果写了拒绝,或逻辑说"属于营销/活动引导"但结果写了通过,必须修正
3. **拒绝时拒绝原因非空**:AI审批结果=`拒绝` 时,AI给业务反馈的拒绝原因 不能为空
4. **面向业务的拒绝原因只写拒绝点**:拒绝原因里只写"不符合的点 + 修改建议",不要写任何符合项,也不要写"虽然有发送基础/虽然利益相关,但是..."这类分析过程; 这些分析应留在 AI判断逻辑 / review notes,不要混到面向业务的话术里。即使你内部判断某条消息"类型本身有发送基础",也不要把这部分写进给业务的拒绝原因。
5. **若命中频控拒绝,拒绝原因必须可执行**:如果命中了 `8-频控`,或 AI判断逻辑中明确写到"频控偏松 / 不符合最低频次原则",则 AI给业务反馈的拒绝原因里必须明确写出业务可执行修改方向。普通系统消息默认写法:对非必须告知 / 非交易 / 非合规类消息,建议按同一功能、同一触达目的收敛到 `30天1次`; **订阅消息默认写法**:需满足订阅频控要求,即 **一天至多1条、一周不超过3条**。**若最终拒绝点已经收敛到“频控不符合系统消息最低频次原则”,则面向业务的话术直接写：`不符合系统消息最低频次原则。请将频控收敛为 30天1次 后再提审。` 不要再向业务解释“对该类经营机会通知偏高”等内部分析口径。**
6. **若同时命中多个拒因,优先把最可直接整改的那个写给业务**:默认优先级为 工单缺失/不自洽 > 频控 > 订阅频控 > emoji/格式 > 人群最小化 > 内容类型
6. **若同时命中多个拒因,优先把最可直接整改的那个写给业务**:默认优先级为 工单缺失/不自洽 > 频控 > 订阅频控 > emoji/格式 > 人群最小化 > 内容类型
6. **频控命中时必须显式出现对应整改标准**:只要本条消息的最终结论受频控问题影响(包括"主信息本可通过,但因频控过松而拒绝/待调整"),则最终输出中至少一处必须出现明确整改标准。普通系统消息应出现 `30天1次`; **订阅消息**应出现 **“一天至多1条、一周不超过3条”**。若没有出现对应标准,视为答案不完整,不能提交
7. **命中规则与结论方向一致**:命中的规则应支撑结论方向(如结论=通过但只命中了 5.x 拒绝类规则,说明有矛盾)

### 写回流程

1. **定位列**:先读表头行,按名称找到上述 7 列的实际列号;若列不存在,在表格最右侧追加缺失列的表头(详见 `batch-review-writeback` skill 第 1.5 步)
2. **建立行映射**:先用 `id -> 行号` 建立映射;批量处理时,必须以 `id` 为主键回写,禁止仅凭连续区间、肉眼顺序、或“看起来是连续行”去假设行号
   - 尤其是大表、中后段、补写 60 行后 / 100 行后 / 尾行时,必须先重新读取当前有效数据范围
   - 发现漏行风险时,先重读实际区间,再补写;不要靠口头估算“后面应该没有了”
3. **读回确认行号**:读取目标行区间,确认要写的是正确的行,且该行的 `id + template_name/title` 与待写 case 一致
4. **自检**:执行上述写回前自检,确认无矛盾
5. **写入**:一次性写入该行的全部 7 列
6. **逐行 read-back 校验**:写完立即回读,确认 7 列都已正确写入,且本行的 `id + 结论 + 关键逻辑方向` 与目标 case 一致
7. **批量任务结束后二次枚举**:全表再扫一次,检查是否存在"业务行 AI审批结果为空"、"结果非空但逻辑明显属于别的 case"、或"尾段漏写/尾行未覆盖"的问题
8. **频控字段优先级自检**:若本次判断涉及频控,必须先确认是否严格以 `freq_detail` 为准;若你的结论引用了 trigger_notice / exit_mechanism / reason_for_unlimited_freq / PRD 文字描述 / 业务解释 来覆盖 `freq_detail`,则说明判断不合规,需要重做
9. **订阅消息授权范围自检**:若本次判断涉及订阅消息,必须逐项自检:①我是否读过对应 PRD/规范正文;②我是否能明确复述用户订阅时被授权接收的消息范围;③我是否能明确说明当前消息属于/不属于该范围;④我是否确认当前材料里真的包含订阅流程信息(至少能看到订阅入口/授权文案/退订路径/流程 Demo 之一)。若任一做不到,则不能输出最终“通过”或授权范围判断;若缺的是第④项,应明确要求补充包含订阅流程信息的 PRD / Demo
10. **订阅消息拒绝点反查**:若 AI判断逻辑里已经明确写出“当前消息属于订阅授权范围/有订阅发送基础”,则 AI给业务反馈的拒绝原因里**不得**再出现“内容本身不能发 / 不是系统通知 / 福利召回不能发 / 更新召回不能发”等内容层拒绝点;若出现,说明把“可发性”和“本次申请是否通过”混了,必须重做
11. **状态重入反查**:若 case 属于 age restricted / permission restricted / risk state / eligibility state,且 MEMORY/当前会话/PRD 已明确其状态可重入,则最终判断中**不得**再以“一次性通知 / 生命周期一次”作为主拒绝理由;若出现,必须重做
12. **系统落地口径反查**:若 case 属于一次性消息,且历史协作已明确系统只能让申请人填写 `30天1次`,则当 `freq_detail=30天1次` 时,**不得**再以“没写成一次/生命周期一次”作为拒绝理由;若出现,必须重做
13. **两层结论反查**:最终输出前,必须能单独回答以下两个问题——①这条消息类型本身有没有发送基础? ②这次申请版本为什么能过/不过? 若这两个问题答不清,说明把“内容可发性”和“当前申请可通过性”混了,必须重做

对相邻工单尤其谨慎,不要把 A 行的结论写到 B 行。

## 11. 文档深挖补充规则

当工单/表格里的消息信息**不足以全面判断**,尤其是争议点落在"业务真实逻辑 / 用户状态前提 / 资格是否已推进 / PRD 是否把这条定义为结果通知还是流程引导"时,不要停留在表格字面信息上。

必须按以下顺序继续深挖:
1. 先从表格对应行读取 `prd` 列;若拿到的是文档标题、wiki 标题或可读文本但不是完整 URL,也不要直接放弃
2. 用 `feishu_search_doc_wiki` 按 PRD 标题中的**完整标题**搜索对应文档
3. 命中目标文档后,用 `feishu_fetch_doc` 读取正文,再基于正文里的业务逻辑、用户状态定义、触发条件、文案矩阵重新判断
4. **不要只按文档顺序盲读前几屏就下结论。** 若当前要确认的是某个特定信息是否存在(如:订阅流程、授权文案、退订路径、settings 开关、demo、资格定义、里程碑奖励、结果通知文案),应先在文档中做**关键词定位**,再重点阅读命中的正文块。订阅场景优先关键词包括: `订阅` / `subscribe` / `subscription` / `settings` / `开关` / `退订` / `unsubscribe` / `channel` / `category` / `入口` / `demo` / `授权`。若关键词已命中相关段落,必须继续把该段及其前后上下文读完,不能因前半段没看到就提前下“没有/不涉及”的结论。
5. 只有在**确实无法读到正文**时,可以得出AI审批结果为`拒绝`，AI置信分组为`边界需人工看`，AI判断逻辑里写是因为无法读取到PRD;若已经读到正文,就必须按正文修正审批结论,不能继续只凭表格摘要或经验判断

**订阅消息补充硬规则**:
- 若消息属于订阅人群场景,上述读 PRD 步骤为**强制步骤**
- 必须读到订阅 PRD/规范正文后,再判断当前消息是否落在用户订阅授权范围内
- 在未读到 PRD 正文前,不得仅凭表格里的“已订阅用户/订阅消息号”等字段就直接按订阅消息通过

适用场景包括但不限于:
- 文案看起来像能力推广,但怀疑实际是资格状态变化后的流程承接通知
- 需要判断用户是否已完成前置验证 / 已进入某资格状态
- 需要核实某条消息在 PRD 中对应的人群状态、触发条件、页面跳转逻辑
- 表格中的 `prd` 列只有标题,没有直接可点开的 URL
