# PM Review
## 目标
定义 Requirement Review 中 **Part 2.2.c PM 视角** 的评审规则。
核心问题：
**该模块下的方案是否符合对应产品规范，交互是否合理，是否具备推进条件。**

PM Review 在 Part 2.2 模块循环中按模块各跑一次。本文件描述**单个模块内**的 PM 评审规则。

> 本 reference 遵守 SKILL.md「共享评审原则」，以下不再重复共享规则。

---
## 评审输入
进入某模块的 PM review 前，至少应获得：
- PRD 主文档
- Part 1.2 的该模块识别与范围判定结果（含该模块的 `degradation_mode`）
- Part 1.3 的全局 `complexity.level`
- Part 2.2.a 已为该模块完成 `required_spec_docs` 的读取（即 `spec_coverage.<module>.gate_passed = true`）
- 命中对象对应的 one page 产品规范文档
- 若 one page 继续引用下层规范，则补充读取对应规范
### 规范来源与读取失败处理
- [主架构产品规范 one page] 为默认权威入口
- 若总文档或 one page 继续指向具体模块规范，则以被命中的具体模块规范为直接评审依据
- 若未命中具体模块，但可识别为某 feature，应至少参考其所属容器 / 页面规范

### 降级模式与复杂度响应
`degradation_mode × PM reviewer` 与 `L1 / L2 × PM reviewer` 的响应规则详见 [degradation-matrix.md](degradation-matrix.md)。

## 评审方法
PM review 的**首要任务是判断方案是否符合产品规范**，而非给 PRD 提优化建议。
执行顺序：对象识别 → 规范读取 → 规范一致性判断 → 链路与目标合理性。规范判断必须先于其他维度。
### 1. 确认规范对象
基于 Part 1.2 该模块结果明确：
- 产品域
- 页面 / 容器名称
- 对象层级（Page / Container / Feature）
- 对应 one page / 模块规范文档
未完成上述识别，不直接判断"是否符合产品规范"。
### 2. 记录规范来源
输出判断前，需明确写出：
- 命中对象
- 对应规范文档名称
- 是否补读下层规范
- 规范读取是否成功
### 3. 先做组件准入判断（高于一般规范一致性判断）
在判断“是否符合产品规范”之前，必须先判断该方案是否属于**现有规范中已开放的组件能力**，以及是否已遵守“优先复用现有组件”的原则。

至少检查以下 3 项：
- **是否为现有开放组件**：方案是否能稳定映射到 one page / 模块规范中明确存在的组件，而不是一个未开放的新形态/异化形态
- **是否优先复用已有组件**：若现有组件理论上可承接相同目标，PRD 是否明确论证“为什么不能复用现有组件”
- **是否属于异化准入场景**：若方案是新组件/异化形态，PRD 是否明确说明其长期定位、必要性与复用价值

若判断为“规范未开放的新组件/异化形态”，且 PRD 没有完成“为何不能复用现有组件”的论证，则应直接记为 `blocking_issue`，不得先降级成优化建议。

### 4. 做规范一致性判断
在组件准入已通过或至少不是 admission blocker 的前提下，再检查以下 4 项：
- **模块定位是否一致**：方案是否符合该模块在 one page 中定义的核心定位、使用目的、用户心智
- **入口与承接是否符合规则**：当前模块允许承接什么类型的内容、页面与交互，是否超出既有承接边界或优先级规则
- **用户链路是否成立**：进入、使用、退出是否完整，是否存在跳转断裂、路径冲突、状态缺失或预期错位
- **目标、定位、交互是否一致**：是否存在"目标写的是 A，但交互承接实现更像 B"的错位
---
## 重点评审维度
### 1. 是否符合产品规范（最高优先级）
已读取到规范时，**必须**逐项检查并在 review notes 中明确写出规范判断结论（符合/不符合/待确认），而不是跳过规范判断只给建议。
- 是否符合对应页面 / 容器的使用规则
- 是否符合入口、承接、页面约束
- 是否违反展示要求、优先级规则或承接边界
- 是否存在"借用某模块承接非该模块职责玩法"的情况
- 是否绕过现有开放组件体系，直接新增未开放的信息表达/交互形态

### 1.1 组件准入 blocker（高优先级）
以下任一情况，默认属于 blocker：
- 方案使用的是现行规范未开放的新组件 / 异化形态
- 规范已明确“优先复用现有组件能力”，但 PRD 未论证为何现有组件无法承接
- 方案只是“长得像某个容器里的表达”，却没有证据说明它就是该组件，而 reviewer 试图按现有组件直接放行
### 2. 交互链路是否合理
- 主链路是否完整
- 主操作、次操作、负反馈、返回路径是否清晰
- 点击后承接是否仍符合该模块原本职责与用户心智
- 资源优先级、频控和退场规范是否完整，用户打扰是否过重
### 3. 方案目标是否自洽
- 目标是否清晰
- 方案是否真正服务于目标
- 页面 / 容器定位、业务目标、最终交互是否一致
### 4. 范围与依赖是否清楚
- 本需求做什么、不做什么是否明确
- 外部依赖是否已说明承接方式与边界

## blocker 判定参考
### 规范型 blocker（需有规范支撑）
- 明显不符合对应产品规范
- PRD 交互与命中对象的 one page 定位冲突
- 借用某页面 / 容器承接不属于该对象职责的玩法
- 点击后承接链路与模块核心用户心智不一致
- Part 1.2 命中 A 对象，但 PRD 实际承接逻辑更像 B 对象，存在归属错配
### 非规范型 blocker（不依赖规范是否读取成功）
- 核心交互链路不成立或关键路径缺失
- 入口、承接、退场逻辑存在明显冲突
- 需求目标与方案设计明显错位
- 关键前置依赖未识别，导致方案当前不可推进
### 通常不单独构成 blocker
- 文案或状态描述可进一步收敛
- 边界场景未完全展开，但主链路已成立
- 表达略分散，可通过补充结构化整理解决

## 输出风格
- 重点写清"是否符合产品规范"与"交互是否合理"
- 规范来源要写清楚
- 规范未读到时，要明确说明判断边界
