# Design Review

## 目标
本文件用于定义 Requirement Review 中 **Part 2.2.d 设计视角** 的评审规则。

它回答的问题是：
**该模块下的设计方案，是否符合对应页面 / 容器 / 组件的官方设计规范要求，并是否存在明确的设计阻塞或体验风险。**

Design Review 在 Part 2.2 模块循环中按模块各跑一次。本文件描述**单个模块内**的 Design 评审规则。

> 本 reference 遵守 SKILL.md「共享评审原则」，以下不再重复共享规则。

---
## 评审输入
进入某模块的 Design review 前，至少应获得：
- PRD 主文档（含设计稿、截图等设计材料）
- Part 1.2 的该模块识别与范围判定结果（含该模块的 `degradation_mode`）
- Part 1.3 的全局 `complexity.level`
- Part 2.2.a 已为该模块完成 `required_spec_docs` 的读取

---
## 判定原则
- 设计 review 的**首要任务是判断设计方案是否符合对应模块的设计规范**，而非给设计稿提优化建议
- 已读取到设计规范时，**必须**在 review notes 中明确写出规范判断结论（符合/不符合/待确认），不能跳过规范判断只给通用建议
- 所有设计规范均以**动态读取的官方最新版本**为准
- 检查结果应尽量对应明确的规范依据，不做无依据推断
- 仅检查设计相关内容，不判断产品逻辑、业务策略或开发实现方案
- 不做主观审美评价
- 设计材料是否达到进入正式评审的最低门槛，由 Part 1.1 完整度检查负责；本 reference 不重复做完整度拦截

### 降级模式、复杂度与设计材料响应
`degradation_mode × Design reviewer`、`L1 / L2 × Design reviewer`、`design_material_access × Design reviewer` 的响应规则详见 [degradation-matrix.md](degradation-matrix.md)。

## 设计规范权威读取路径
设计视角的规范读取应遵循以下权威路径，不得跳步：
1. **先确认改动的页面 / 容器是什么**
- 以 Part 1.2 已识别的该模块页面 / 容器结果为起点
- 若当前容器识别仍不稳定，应先承认范围不确定性，不得强行进入设计规范判断
2. **查看主架构 one page 中对应的容器产品规范文档**
- 权威入口文档：[主架构产品规范 one page]
- 应优先通过 one page 确认当前改动对象命中的页面 / 容器，以及其对应产品规范
3. **定位产品规范中引用或关联的设计规范文档**
- 设计 reviewer 不应绕过产品规范，直接凭经验挑选设计规范
- 若产品规范已明确关联设计规范，应优先读取该设计规范作为主依据
- 若产品规范未明确给出设计规范，再补充匹配通用或专项设计规范
4. **基于命中的设计规范检查是否符合要求**
- 仅在已读取到对应设计规范后，才可做"符合 / 不符合规范"的强判断

执行约束：
- 不得跳过 one page 与产品规范，直接从零散设计规范库中主观挑选依据
- 不得在页面 / 容器识别不稳定时，伪造设计规范归属
- 链路未走通时在 `summary`、`evidence` 或 `missing_information` 中说明判断边界
- 主链路完成后可补充读取专项组件/子模块规范；多个规范命中时以主容器关联的为主

## 核心检查维度

> 以下各维度中的具体数值阈值（如 WCAG AA+、44pt、200ms）为**通用设计原则兜底值**，仅在未读取到对应模块设计规范时作为参考依据。当已读取到命中规范且规范给出明确阈值时，以规范值为准。在 `evidence` 中应注明判断依据来自"命中规范"还是"通用设计原则"。

### 1. 基础样式规范
符合对应模块设计系统规范：
- 色彩在设计系统色板范围内，文本对比度符合 WCAG 2.1 AA
- 字体、字号、字重、行高符合模块规范
- 间距、圆角、阴影等样式参数与统一规范一致
- 优先使用组件库标准组件；自定义组件需说明差异点

### 2. 交互状态规范
覆盖关键交互状态并提供清晰反馈：
- 包含全量状态：默认/hover/点击/禁用/加载/成功/失败/空态
- 所有操作有明确即时反馈
- 动效时长、曲线符合全局动效规范（偏差 <200ms）

### 3. 多场景适配
覆盖主流场景，无明显体验断层：
- 深色模式适配完整
- 小屏（≤5.5英寸）内容无裁切，可点击区域 ≥44pt
- 长语言场景文案无溢出、布局无错乱
- 横屏/折叠屏适配符合全局规范

### 4. 全链路一致性
与同类型交互及同模块历史设计保持一致：
- 同类型交互逻辑跨场景一致
- 与同模块历史设计风格、组件使用统一
- 跨端（iOS/Android/Web）符合各自系统设计规范

## judgement 判定规则
- `pass`：已读取到对应设计规范或足够设计依据，未发现明确设计 blocker，仅有轻量优化建议
- `conditional-pass`：主体设计方向可接受，但存在需补状态、补适配、补专项规范对齐或补设计说明等前置事项
- `no-pass`：已读取到对应设计规范，且存在明确不符合规范的阻塞问题；或存在足以影响上线 / 实验推进的明显体验断层
---
## 问题分层规则
- `blocking_issues`：有明确规范依据、明显影响关键交互 / 核心体验、且足以阻塞推进的问题
- `non_blocking_suggestions`：可优化但不阻塞推进的问题
- `missing_information`：当前材料不足，导致无法稳定完成某一专项检查，或未读取到对应规范
---
## 访问性与证据要求
必须显式说明本次判断依据：
- 是否读取到设计稿 / 截图 / PRD 文本
- 是否读取到对应模块设计规范
- 关键结论来自哪些规范或哪些设计材料

---
## 输出要求
Design reviewer 输出 schema（含 `design_material_access` 和 `spec_basis` 扩展字段）、字段级约束与 `design_material_access` 判定规则，详见 [contracts.md](contracts.md)「四、Design Reviewer 扩展」。
