# 元素识别模板（Element Recognition Template）

> **本文件说明**：这是为 Stage 2 元素识别准备的**空白模板**。每个一级页面（或一组视觉结构相似的一级页面）对应一个 `elements-*.md` 文件，所有文件都按本模板的结构组织。添加新 reference 文件、或者扩充现有文件里的元素清单时，都参考本模板。

---

## 适用范围

> 在真实 reference 文件里，此处应写明：**本文件覆盖哪些 Stage 1 page slug**。
>
> 例如：
> - `elements-single-video-feeds.md` → 适用于 `foryou` / `following` / `friends`(顶部形态) / `stem`
> - `elements-shop.md` → 适用于 `shop`

---

## 页面总体结构

> 用 3-5 句话描述该页面的整体视觉骨架，让模型在看元素清单之前有个鸟瞰。包括：页面有几个明显的视觉分区（顶部/中部/底部/左侧/右侧/悬浮），每个分区大致放了什么内容。
>
> 示例："推荐流页面从上到下分 3 个区：①顶部导航区（LIVE 入口 + 横排子 tab + 搜索入口）、②视频主体区（占屏幕主要面积，承载视频画面 + 右侧互动悬浮栏 + 左下信息区）、③底部 tab 栏。所有元素都落在这 3 个区之一。"

---

## 元素清单

把该页面上**所有稳定可识别的元素**列出来，分组呈现（按"视觉分区"分组最自然）。每个元素都要有**结构化的描述**，字段如下：

### 元素字段结构

每个元素用以下结构描述：

```
#### <元素 slug>

- **中文名**：<人类可读的名字>
- **位置**：<在页面哪个分区，大致坐标描述>
- **视觉特征**：<图标形状/文字内容/颜色/尺寸 等让模型认出它的线索>
- **可操作性**：`tap` / `long_press` / `swipe_up` / `swipe_down` / `swipe_left` / `swipe_right` / `type` / `none`（可多个）
- **点击后行为**：<触发后会发生什么，比如跳到哪个页面 / 弹出什么层 / 切换什么状态>
- **用户常见指代**：<用户描述时可能用什么词指这个元素，帮助匹配 user_referenced>
- **别名/变体**：<同一个元素在不同上下文下的其他叫法或视觉形态>
- **条件性**：<什么情况下会出现/消失，例如"仅登录用户可见"、"有未读消息时有红点"、"某些地区可能没有"等>
```

### 元素分组示例

按视觉分区分组，典型结构如下：

#### 顶部导航区

> - 列出所有顶部区域的元素

#### 主体内容区

> - 列出视频/列表/网格等主体区域的元素

#### 右侧悬浮栏（如适用）

> - 推荐流/视频详情等有右侧互动栏的页面

#### 底部导航/输入区

> - 底部 tab、输入框等

#### 叠加层/弹窗内元素（如适用）

> - 如果该页面常见某些叠加层，把叠加层上的关键元素也列出来
> - 格式：`#### <overlay_slug>:<element_slug>`

## 常见子状态

> 如果该页面有明显的几种子状态（例如 inbox 的好友数 0/1/2/3+ 态、创作者态、带 banner 态），在此列出：
>
> - **子状态 A 名称**：触发条件 / 视觉差异 / 该子状态下是否出现独有元素
> - **子状态 B 名称**：...

这一节的目的是让 Stage 2 识别时，能**标记当前处于哪个子状态**，并理解为什么某些元素可能缺失或形态不同。

---

## Stage 2 输出格式

基于 Stage 1 的 JSON，追加 `elements` 字段：

```json
{
  "...Stage 1 字段...": "...",
  "elements": {
    "sub_state": "<该页面的子状态 slug，如果有>",
    "user_referenced": [
      {
        "element": "<元素 slug>",
        "element_zh": "<中文名>",
        "confidence": "high" / "medium" / "low",
        "why_matched": "<为什么认为用户描述的就是这个元素，1 句话>",
        "user_phrase": "<从用户原话里摘出的指代片段>",
        "visible_in_screenshot": true / false
      }
    ],
    "all_visible": [
      {
        "element": "<元素 slug>",
        "element_zh": "<中文名>",
        "bbox_hint": "<大致位置描述，如 'top-right' / 'bottom-center'>",
        "state": "<该元素当前的状态，如 'active' / 'disabled' / 'highlighted' / 'default' / 'has_badge:3'>"
      }
    ]
  }
}
```

### 字段说明

- **sub_state**：当前页面的子状态（如果该页面定义了子状态）。无则填 null
- **user_referenced**：仅在用户描述中有指示性表达时填充。按相关性排序（最相关的第一个）
  - `element`：从本 reference 的元素清单中选出对应的 slug
  - `confidence`：匹配的置信度
    - `high`：用户指代非常明确、元素在截图中清晰可见
    - `medium`：用户指代有一定歧义、或元素部分可见
    - `low`：用户指代模糊、或元素不可见只能靠上下文推测
  - `why_matched`：解释为什么这个元素匹配用户描述
  - `user_phrase`：用户原话里的哪个短语触发了这次匹配
  - `visible_in_screenshot`：该元素是否在当前截图里可见（有时用户问的东西恰好被遮挡或没出现）
- **all_visible**：可选。把本 reference 清单里的元素对照截图逐个扫描，列出当前可见的那些
  - `bbox_hint`：简单的位置描述，不需要精确坐标
  - `state`：元素当前处于什么状态（如 tab 是否激活、按钮是否置灰、红点数量等）

### 何时填 `user_referenced` / `all_visible`

| 用户场景 | user_referenced | all_visible |
|---|---|---|
| 用户只问"我在哪个页面" | `[]` | `[]` |
| 用户明确指代某个元素 | 必填（至少一个） | 可选（帮助下游了解上下文） |
| 用户问"这个页面能干什么" / "帮我列出所有按钮" | `[]` | 必填（详细列出） |
| 用户指代的元素在截图里不可见 | 必填 + visible_in_screenshot=false | 可选 |

## 未识别元素的处理

如果用户指的元素**不在本 reference 的清单里**（可能是新元素、少见变体、或你没列全），在 user_referenced 中用：

```json
{
  "element": "unknown",
  "element_zh": "<你观察到的元素描述>",
  "confidence": "low",
  "why_matched": "<用户原话匹配到的内容>",
  "user_phrase": "...",
  "visible_in_screenshot": true,
  "visual_description": "<从截图里描述出来让下游人类能识别的细节>"
}
```

这同样是一个**扩展口**——标 unknown 的元素越多，越能帮你发现哪些元素需要补进 reference 文件。
