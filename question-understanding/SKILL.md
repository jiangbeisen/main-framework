# 问题理解技能

## 最高优先级约束（先于一切分类规则）

**只有高置信度才允许直接输出并继续路由；中置信度和低置信度一律视为“待确认”，必须由 orchestration 先追问一次，再决定后续路由。**

这条约束优先级高于所有经验性判断、默认值和快捷归类。宁可多追问一句，不可误判路由。

额外执行约束：
- 不要因为“看起来大概像”就把中置信度问题硬判成高置信度。
- 不要把“上一轮已经在聊某个方向”当成这轮一定高置信度的理由；要先判断这句话本身是在**延续同一任务**、**切换到知识管理**，还是在**纠正分类/流程**。
- 遇到短句追问（如“还有吗”“为什么”“高么”“那这个呢”“这里你怎么没识别意图”）时，必须结合**上一轮任务状态**做分类，禁止脱离上下文按字面随手归类。

## 核心任务

对工作场景中出现的问题，从三个维度进行分类标注：

1. **提问意图** — 提问者想达成什么目的
2. **作用实体类型** — 问题指向的业务对象是什么
3. **产品域** — 问题涉及哪个产品

每个问题标注一个**主标签**，如果问题确实跨越多个类别，可追加**次标签**（最多一个）。大多数问题只需要主标签，次标签仅在问题明确涉及第二个维度时才添加，不要过度标注。

> **全局约束：本技能执行全程禁止使用 memory search。** 分类判断完全基于问题文本本身和本文档中的分类体系，不查询任何 memory 文件。

## 调用规则

- 不直接面向用户问题触发。
- 仅接受 `orchestration` 调用。
- 接收：原始问题、用户对话历史。
- 输出：结构化分类结果（见「输出契约」）。

## 分类体系

### 维度一：提问意图

| 意图标签 | 含义 | 典型问法 |
|---------|------|---------|
| **信息查询** | 想知道谁负责、谁来跟进、该找谁，或想了解现状、进展、具体内容、背景 | "这个归谁管？""进展到哪了？""数据是多少？" |
| **同步周知** | 向对方传递信息、对齐认知、通报进展或结论，方向是"推送"而非"索取" | "同步一下……""FYI：方案已定" |
| **意见判断** | 想听对方的看法、建议、判断，或提交需求/PRD/方案请求评审 | "你觉得呢？""评审一下这个PRD""给点建议" |
| **闲聊** | 不涉及工作事项的日常对话、寒暄、生活话题 | "今天午饭吃啥""哈哈哈" |

#### 内部意图

内部意图用于系统内部路由，前缀带 `[内部]` 标记。**内部意图不需要判断实体类型和产品域，识别后直接返回。**

| 意图标签 | 含义 |
|---------|------|
| **[内部]知识管理** | 涉及知识库维护、知识沉淀、文档管理、skill 文档引用登记等管理操作 |
| **[内部]技能评测** | 对指定 skill 进行质量评测 |

**判断要领：**
- 内部意图优先级高于常规意图——如果识别为内部意图，跳过实体和产品域分类，直接返回
- 只有当问题明确属于内部意图覆盖的场景时才使用，模糊情况仍走常规意图分类
- **凡是要求对知识/文档进行"记录、登记、沉淀、更新、删除、整理、归档、补全、查漏、归类、维护"等管理动作的，一律归 [内部]知识管理**，判断关键：用户的焦点是"管理这份知识/文档的存放与结构"而非"查询其中的内容"
- **如果上一轮已经进入“术语整理 / 值不值得沉淀 / 还有哪些该记下来 / 怎么归档 / 如何补齐知识清单”语境，则后续像“还有别的么”“还有吗”“就这些吗”“有没有漏的”“再想想”“补全一下”这类续问，默认按 [内部]知识管理 处理，而不是普通信息查询。**
- **如果用户在纠正分类、路由或 skill 执行方式，例如“这里你怎么没识别意图”“这是什么意图”“你这里判错了”“应该路由到哪个 skill”，且焦点是改进分类/路由规则本身，则优先归 [内部]技能评测；如果焦点是让你沉淀、更新、维护知识/规则文档，则归 [内部]知识管理。**

**常规意图判断要领：**
- 问"谁负责/谁来跟进/该找谁"，或问"是什么 / 怎么样 / 多少 / 什么时候" → **信息查询**
- 问"什么标准""准入标准是什么""定义是什么""口径是什么""规则是什么" → **信息查询**（索取既有标准/定义/规则，不是征求主观看法）
- "评审""review""评估""给点建议""你觉得""怎么看""合不合理""请求sign off""能否批准上线" → **意见判断**
- "能不能/要不要/行不行"看语境——请求拍板或征求看法 → 意见判断；摸底信息 → 信息查询
- "同步""对齐""周知""通报""FYI" → **同步周知**。注意："请同步给我进展"（索取）→ 信息查询
- 表面问信息但实际推动决定 → 按**表层语义**标主标签，**隐含意图**标次标签
- **转发 / 粘贴长文后的意图识别规则：**若用户贴来一段长同步、PRD、方案说明、群聊长消息，并希望你“看看 / 分析 / 判断 / 再分析看看 / 你觉得呢”，不要机械按该文本原始体裁（如同步周知、专项汇报）给当前轮分类；应优先判断**用户此刻要你对这段内容做什么**。
  - 若用户是让你提炼事实、总结现状、抽取结论 → **信息查询**
  - 若用户是让你判断方案是否合理、哪些点有风险、该如何推进/对齐/拍板 → **意见判断**
  - 若用户是在纠正你刚才对这段内容的分类/路由 → **[内部]技能评测**
- **专项 vs 需求 的实体收紧规则：**当一段“专项同步”正文主体是在逐条讨论若干具体功能诉求 / 资源位申请 / PRD 条目（如头像框、挂件、锚点异化、入口等），并围绕“是否支持、是否冲突规范、怎么修改才能过”展开时，主实体应优先标为 **需求**，而不是笼统标为 **专项**。只有当问题焦点是专项整体背景、目标、组织推进、跨团队协同、整体风险时，才标 **专项**。
- **专项下需求盘点类问题优先判专项：**当问题同时出现“专项/战役/活动主题”（如世界杯、双十一、618、黑五等）与“需求”时，必须先判断用户是在问**某条具体需求**，还是在问**专项维度的需求全集 / 汇总 / 总览**。若用户是在问“有哪些 X 相关的需求”“是否有汇总/统一入口/总览”“想了解整体情况/整体盘子/覆盖范围”“为了更好支持该专项，想先盘点相关需求”这类问题，则主实体优先标为 **专项**，次实体标为 **需求**。只有当焦点落在某个明确需求项、某类具体功能诉求、某个 PRD / feature / 申请单时，主实体才标为 **需求**。
- **信息源 vs 真正对象 的拆分规则（高优先级）：**当用户说“去 X 里找 Y / 在 X 里查 Y 的进展 / 从 X 看看 Y / 用 X 验证 Y”时，`X` 是**信息源/检索范围/证据来源**，`Y` 才是**真正要分类的对象**。分类时主实体必须跟着 `Y` 走，不能因为句子里出现了文档、周报、群聊、知识库、表格、邮件等载体，就把主实体错判成 **工作汇报 / 文档 / 群聊内容**。
  - 例：**“去主架构周报里找智能客服相关进展”** → 主实体是 **业务方向（智能客服）**，不是 **工作汇报**；“周报”只是信息源。
  - 例：**“在群聊里找这个需求的结论”** → 主实体是 **需求**，不是群聊。
  - 例：**“从知识库里看这个模块的准入规则”** → 主实体是 **产品模块**，不是知识库。
- **仅当用户真的在问载体本身时，才把载体当对象。** 例如“这篇周报讲了什么”“上周周报里哪几条最重要”“这个群里昨天讨论了啥”，这时实体才可跟随周报/群聊这类载体内容走。
- **禁止把自己脑中补出来的“资料载体 / 承载规范的文档 / 某份写着规则的文档”当成新的实体候选。** 如果用户原话问的是“XX 的规范是什么 / XX 怎么用 / XX 的准入规则是什么”，默认仍是在问 **XX 本身**；文档只是后续求证来源，不参与实体类型竞争。
- **对“XX 的规范/规则/标准是什么”这类句式，优先判断 `XX` 是什么对象，再去找规范；不要反过来先把“规范文档”当对象。** 只有当用户显式问“哪份文档写了 XX 规范 / XX 规范在哪篇文档里 / 给我 XX 规范文档链接”时，文档才进入问题焦点。
- **若 `XX` 本身已是 one page 或权威索引可直接命中的标准页面/容器/模块名（如头像挂件、首页挂件、锚点、Tab 框架、异形卡），分类阶段默认直接收敛为“产品模块（高置信度）”，不得为了求稳额外制造“你是在问规则本身还是在问文档”这类伪歧义。**
- **短句追问必须强制参考上一轮任务状态**：像“为什么”“高么”“还有吗”“那这个呢”“所以呢”“这里你怎么没识别意图”这类句子，单看字面通常不够分类，必须先判断它是在：
  1. 追问上一轮的事实内容 → 延续原主意图
  2. 纠正上一轮的分类/路由 → [内部]技能评测
  3. 推动沉淀、补全、归档上一轮知识对象 → [内部]知识管理
- **当用户在同一话题里，从“问内容”切换到“问这件内容该不该沉淀/如何整理/是否遗漏”时，主意图随之切到 [内部]知识管理，不再沿用原来的信息查询标签。**

### 意图优先级排序

当多个意图并存时，按以下顺序裁决主标签：意见判断 > 信息查询 > 同步周知 > 闲聊

### 维度二：作用实体类型

| 实体标签 | 含义 | 举例 |
|---------|------|------|
| **专项** | 跨团队的专项项目、战役、大型攻坚 | "双十一专项""安全合规专项" |
| **产品模块** | 产品内的功能模块或子系统 | "支付模块""推荐引擎""消息中心" |
| **业务方向** | 业务线、赛道、战略方向 | "国际化""To B""社区业务" |
| **指标口径** | 指标本身，或围绕指标/归因/统计对象的定义、口径、框架、计算方式、分析方法 | "DAU""转化率""GMV""打开理由是什么""打开理由口径""归因口径是什么" |
| **流程** | 工作流程、审批流、规范机制 | "发布流程""需求评审流程" |
| **需求** | 具体的产品需求、feature、用户故事 | "支持微信登录""增加批量导出功能" |
| **问题反馈** | 已经出现的具体问题、异常、bug、用户反馈问题项 | "按钮点击无反应""线上报错" |
| **工作汇报** | 日报、周报、双周报、月报、季度报、年报等周期性工作总结 | "周报""Q3总结" |
| **组织事务** | 招聘、行政、HR、财务、法务等职能性事项 | "一面面评""offer审批""团建安排" |
| **无** | 不涉及任何明确的业务实体对象 | 日常闲聊、生活话题；纯定义解释类提问 |

**判断要领：**
- 实体类型看的是问题**指向的对象**，不是问题本身的形式
- 同时涉及两类实体时，以**问题焦点**为主标签（回答主要需要哪类实体的知识）
- 区分**实体**和**实体的属性**：指标/成本/排期作为某对象的属性出现时，实体是那个对象本身。只有指标本身，或围绕指标的**定义/口径/归因/统计框架**是焦点时，才标 **指标口径**
- 区分**流程**和**组织事务**：焦点在"流程怎么走/能不能改" → 流程；焦点在"职能性的事情本身" → 组织事务
- 周期性工作总结 → **工作汇报**，不归流程或需求
- "这个问题/这个bug/这个异常"且焦点是已发生的问题项 → **问题反馈**；明确讨论新增能力/方案设计 → 需求
- 问"是什么""什么意思""怎么理解""和 X 有什么区别"，若只是解释名词定义、概念边界、缩写含义，这属于**信息内容类型**，不单独构成实体类型；默认按 **无** 处理，除非问题同时明确指向某个业务对象（如模块、需求、流程、指标口径等）
- 若问题焦点是**指标、归因体系、统计对象、计算方式、分析口径**本身，如“打开理由是什么”“XX 口径是什么”“这个指标怎么算”，优先标 **指标口径**
- **禁止因为短语中含有容器词，就把整个短语判成容器。** 例如“购物车锚点”虽然带“锚点”，但应优先理解为**锚点容器下的业务实例**，不是“锚点”容器本身。
- **强制实例优先规则：** 只要用户提问中的对象比 one page 可直接命中的页面/容器更具体（如“购物车锚点”“好友推荐异形卡”“推送授权弹窗”），即使其中包含容器词，也必须优先标注为**产品模块中的业务实例/Feature/Instance**，不能回退标成容器本身。

### 维度三：产品域

当前工作上下文为**字节跳动 - TikTok 产品域**。

| 产品域标签 | 说明 |
|-----------|------|
| **TikTok** | TikTok 主端（默认值） |
| **TikTok Lite** | TikTok 轻量版/小包 |
| **TikTok Pro** | TikTok Pro 版本 |
| **抖音** | 抖音及抖音相关产品 |
| **CapCut** | 剪映国际版 |
| **Lemon8** | Lemon8 社区产品，也经常叫 L8 |

**判断要领：** 未明确提及产品名 → 默认 TikTok。显式提及才标其他产品。跨产品域以焦点为主标签。**对于主实体为“概念/术语”的问题，如未明确提及其他产品域，也默认标注为 TikTok，不再返回 null。**
- **产品域只能由显式产品名或强产品专属标识触发，不能由业务词、场景词、能力词触发。** 例如“电商 / 图文 / 营销 / 锚点 / 标签 / 券 / button / 大卡 / 自然流”这类词，只能用于判断实体、场景或需求内容，**不能据此把产品域判成抖音或其他产品**。
- **禁止用“高共现语境”替代显式证据。** 即使某些表述在经验上“更像抖音常见讨论”，只要问题里没有明确出现“抖音/抖音主端”等产品标识，仍必须维持默认产品域 TikTok。
- **出现跨产品比较时，按用户当前实际求助对象判断产品域。** 例如“INS 和 TT 广告在图文营销上有差异，希望看看主端同学建议”中，INS 只是对比对象，TT/主端才是当前问题落点，因此产品域应判为 TikTok，而不是因为提到电商图文就切到抖音。
- **“主端”本身不是抖音证据。** 在当前工作上下文中，若仅出现“主端同学”“主端建议”“主端反馈”而未显式带出抖音，默认仍按 TikTok 处理。

## 分类流程

1. **先看这是不是“续问 / 纠错 / 补全”** — 对短句、代词句、省略句，先结合上一轮任务状态判断它是在延续原任务、纠正分类，还是切到知识管理/技能评测；没有完成这一步，禁止直接套字面规则
2. **判断内部意图** — 先检查是否匹配内部意图。如果匹配，跳过实体和产品域分类，直接输出
3. **三维分类** — 按前述规则完成意图 × 实体 × 产品域的标注
4. **关键词脱敏验证** — 从原始问题中移除触发主意图的关键词（如"review""评审""帮我""看看""sign off"），只看剩余内容重新判断意图：一致 → 通过；不一致 → 以脱敏后的判断为准，修正主意图
5. **置信度评估** — 根据以下条件输出置信度等级：

| 置信度 | 条件 |
|:---:|------|
| **高** | 意图和实体均明确，无歧义；且这句话与上一轮上下文的关系明确（是延续、切换还是纠错） |
| **中** | 意图明确但实体有歧义，或实体明确但意图在两个之间犹豫；或需要依赖上一轮上下文才能成立，但上下文指向不唯一 |
| **低** | 意图和实体均模糊，无法确定唯一分类；或是短句/省略句，脱离上下文完全不可判 |

## 易错场景举一反三

### 1. “还有吗 / 还有别的么 / 有没有漏的 / 就这些吗”
- 如果上一轮是在**枚举事实清单**，这类句子默认是对原枚举任务的**补全追问**
- 如果上一轮已经进入“**这些内容值不值得沉淀 / 该怎么整理 / 还有哪些该记下来**”语境，则应切到 **[内部]知识管理**
- 不要机械按“还有什么”判成信息查询，要先看用户是在问“内容”，还是在问“知识对象的整理范围”

### 2. “为什么判断成 X / 置信度高么 / 这里你怎么没识别意图”
- 这类不是普通信息查询，默认是在**检查分类器/路由器本身是否工作正确**
- 若焦点是“你为什么这样分类/路由” → **[内部]技能评测**
- 若焦点是“把这类规则写进 skill / 更新文档 / 以后别再错” → **[内部]知识管理**（因为已经进入规则维护）

### 3. “这是知识管理意图” / “这应该是 X 意图”
- 这类句子是用户在**直接纠偏分类结果**
- 默认按 **[内部]技能评测** 理解其校正动作；若同时要求“更新 skill/记住规则/写进文档”，则升级为 **[内部]知识管理**

### 4. “详细举一反三一下，更新问题理解的技能，之后别再理解错意图了”
- 这是标准的 **[内部]知识管理**
- 因为用户明确要求：
  - 沉淀规则
  - 更新 skill 文档
  - 把经验写进去供后续复用
- 不应仍停留在 [内部]技能评测，因为动作已经从“评估对错”切到“维护知识资产”

### 5. 同一话题中的意图切换
- 用户可能先问事实（信息查询），再问该不该沉淀（知识管理），再纠正你的分类（技能评测）
- **禁止因为主题没变，就默认意图也不变**
- 每一轮都要重新判断：用户此刻是在问内容、评估分类器，还是维护知识

### 6. “术语/概念”不再作为实体类型
- “术语/概念”描述的是**问题形式**或**信息内容类型**，不是业务里的实体对象。
- 因此，像“XX 是什么”“XX 什么意思”“XX 和 YY 有什么区别”这类问题，不能再把“XX”自动标成实体类型“概念/术语”。
- 若问题只是纯解释定义，且未指向明确业务对象，主实体标 **无**。
- 若问题虽然是解释型问法，但实际指向明确业务对象，仍按对象本身标实体。
- 若问题焦点是**指标体系、归因框架、统计口径、计算定义**，则标 **指标口径**。
- 例如：
  - “Inbox 是什么？” → 若语境在主框架，可按 **产品模块** 理解
  - “打开理由是什么？” → 按 **指标口径** 处理
  - “DAU 口径是什么？” → 按 **指标口径** 处理
  - “抖音打开理由定义文档有吗？” → 若焦点是找该口径对应文档，可仍按 **指标口径** 理解其查询对象，文档只是载体

### 7. 规范问法防漂移（必须命中）
- 对以下问法，默认都先锚定 **实体本身**，再进入“去哪里验证”的问题，不允许在分类阶段把焦点漂移到文档载体：
  - “XX 的使用规范是什么”
  - “XX 的准入规则是什么”
  - “XX 有什么标准”
  - “XX 怎么接入 / 怎么上线”
- 判断顺序必须固定为：
  1. 先识别 **XX 是什么实体**；
  2. 再判断该实体属于哪个分类（产品模块 / 流程 / 指标口径 / 需求等）；
  3. 最后才决定去哪个权威来源验证。
- **禁止倒序思考：** 不能因为脑中先浮现“规范通常写在文档里”，就把问题改写成“用户是不是在问某份文档”。
- 反例：
  - “头像挂件的使用规范是什么？” → 先判 **头像挂件 = 产品模块**，再去找规范。
  - 不能判成：“用户可能在问承载规范的文档，所以实体待确认”。

### 8. 长背景 + 找协同对象类问题（必须命中）
- 当一句话前半段包含较长的历史背景 / 方案背景 / 法务背景 / 推进背景，后半段出现以下落点时：
  - “建议可以找谁……”
  - “该拉谁一起……”
  - “和谁对齐……”
  - “谁来一起看……”
  - “找谁沟通可行性……”
  主意图默认优先判为 **信息查询**，因为用户最终是在索取**联系人 / 协同对象 / 负责方**，而不是索取主观看法。
- 即使句中同时出现“是否可以”“可不可以”“建议”“一起评估”等措辞，也不能因此优先判成 **意见判断**；这些词在此类问题中常常只是礼貌表达或协同语气，不一定代表真正想听主观看法。
- **最终落点优先于前置背景。** 对这类长句，必须优先看用户最后真正要执行什么动作，而不是被前面的背景叙述带偏。
- 例：
  - “UG法务建议先和TT主端沟通可行性，想问一下是否可以拉你一起，或者建议可以找谁一起对齐” → 主意图优先判 **信息查询**。

### 9. 协同背景词不抢主实体（必须命中）
- 句子中出现以下词时，若它们只是描述参与方、推进路径或沟通关系，默认视为**背景协同信息**，不能直接决定主实体：
  - 法务 / UG法务 / 中台 / 主端同学 / Leader / 团队 / 一起评估 / 推进到某层面
- 主实体必须回到“这件事本身在讨论的对象”上判断。
- 若背景协同信息服务的是某个明确的产品/能力/机制问题（如 DID 去持久化、锚点能力、挂件样式、登录机制），主实体优先按该产品/能力对象归类，而不是按组织事务归类。

### 10. 技术/产品对象优先于治理词（必须命中）
- 当一句话里同时出现：
  1. **技术/产品对象**（如 DID、锚点、挂件、弹窗、登录、标识机制、功能能力名）
  2. **治理/推进词**（如评估、沟通、推进、法务层面、可行性、对齐）
  应优先判断技术/产品对象是否是问题真正所指的对象。
- 只有当用户真正问的是“流程怎么走 / 审批怎么过 / 法务机制是什么 / 应该走哪条流程”时，才把主实体判成 **流程** 或 **组织事务**。
- 如果用户是在围绕一个具体产品/能力问题问“找谁对齐 / 谁来一起看 / 谁负责”，则主实体优先判为 **产品模块**。
- 例：
  - “之前 iOS 端 DID 去持久化，近期想重新评估，建议找谁一起对齐” → 主实体优先判 **产品模块**，不是 **组织事务**。

### 11. 背景协同语气不保留为次意图（必须命中）
- 当句中出现“是否可以拉你一起”“可不可以一起看”“建议一起评估”“麻烦一起沟通”这类表达时，若它们只是**协同语气 / 礼貌表达 / 邀请参与方式**，而不是用户真正要听主观看法，则**不得保留为次意图 `意见判断`**。
- 只要当前问题的最终落点已经明确是“找谁 / 和谁对齐 / 谁负责 / 谁一起推进”，则这些协同语气默认视为背景噪音，**次意图写 null**。
- 只有当用户明确在问“你觉得可不可行 / 要不要做 / 合不合理 / 是否值得推进”时，才保留 **意见判断** 作为主意图或次意图。

### 12. 背景参与方不保留为次实体（必须命中）
- 当“法务 / UG法务 / 中台 / Leader / 评估 / 对齐 / 一起推进”只是描述参与方或协同路径，且主实体已经明确锁定为具体产品/能力对象时，**次实体默认写 null**，不得再额外保留 `组织事务` 或 `流程`。
- 只有当用户真的在追问这些对象本身（如“法务流程是什么”“该走什么审批流程”“组织上谁来拍板”）时，才允许把它们提升为主实体或次实体。
- 例：
  - “UG法务建议先和TT主端沟通可行性，想问找谁一起对齐” → 主实体是 **产品模块**，次实体应为 **null**。

### 13. “review + 背景材料”优先锁定意见判断（必须命中）
- 当用户明确说“帮忙 review / 辛苦帮忙 review / 评审一下 / 看看是否合理 / 帮忙判断是否可用”时，默认主意图优先锁定为 **意见判断**。
- 即使正文主体是大段活动背景、客户背景、玩法说明、素材说明，也不能因为脱敏后剩下内容像“在同步材料”，就把主意图改判成 **同步周知**。
- 对这类问题，背景材料只是用户为 review 提供的评审上下文，不是主意图本体。
- **脱敏验证例外规则：** 如果原句里已出现明确的 review / 评审 / 判断请求，则脱敏后不得仅因剩余文本像“信息同步”而把主意图改成同步周知；只有当用户原句根本没有评审/判断请求时，才允许判为同步周知。

### 14. 需求承载模块不保留为次实体（必须命中）
- 当用户是在评审一个具体申请、方案、活动玩法、PRD 或 quota 使用场景时，若句中出现“头像挂件 / 头像框 / 锚点 / 异形卡 / 弹窗”等模块词，而这些词只是**需求方案的承载对象**，默认不保留为次实体，**次实体写 null**。
- 只有当用户真的同时在问两个对象（例如既在问需求本身，又在单独追问该模块规范/owner/准入）时，才允许把模块保留为次实体。
- 例：
  - “商业化 quota 申请头像挂件的使用，辛苦帮忙 review” → 主实体应为 **需求**，次实体应为 **null**，不能因为出现“头像挂件/头像框”就补一个次实体 **产品模块**。

### 15. 数据查询诉求不自动改写主实体（必须命中）
- 当用户在问“有没有看板 / 能不能查这些数据 / 是否支持分层 / 哪里可以看数据 / 是否有相关数据”时，先判断这些数据是**围绕哪个对象展开**。
- 如果这些数据是围绕某个页面、容器、模块、功能能力展开的，则主实体优先跟随该对象，标为 **产品模块**；不能因为出现“渗透 / 规模 / 分层 / 看板 / 数据”就自动把主实体改成 **指标口径**。
- **数据视角只是信息查询方式，不自动决定主实体。**
- 只有当用户真正问的是指标定义、统计口径、计算方式、归因框架、分层规则本身时，才标 **指标口径**。
- 例：
  - “有没有看板看个人主页链接、合集的消费渗透？” → 主实体应为 **产品模块**，不是 **指标口径**。
  - “个人主页外挂链接、有合集作者规模能不能查？” → 主实体应为 **产品模块**。
  - “消费渗透口径怎么算 / 作者规模如何定义 / 粉丝分层规则是什么？” → 才标 **指标口径**。

### 16. 发问方业务背景不抢主实体（必须命中）
- 当句中出现“我们XX业务 / XX团队 / XX组 / XX方向目前在盘点……”这类表述时，默认先视为**提问背景**，不是主实体。
- 不因这些背景词直接把主实体标成 **业务方向**。
- 主实体必须跟随后文真正被询问的对象。
- 例：
  - “我们海外生服业务目前在盘点个人地点榜单业务，想看个人主页链接、合集的数据看板” → 主实体应优先判 **产品模块**，而不是 **业务方向**。

### 17. 容器词误导防呆（必须命中）
- 对产品模块类 owner 问题，若用户表述是“更长短语 / 具体场景 / 卡片名 / 弹窗名 / 锚点实例名”，即使短语中包含容器词，也**先按业务实例理解**。
- 以下反例必须优先触发：
  - **购物车锚点 ≠ 锚点容器**
  - **好友推荐异形卡 ≠ 异形卡容器**
  - **推送授权弹窗 ≠ 弹窗容器**
- 若分类时已经能判断“用户问的是实例，不是容器”，则后续执行阶段只允许两种结果：
  1. 找到**实例级** owner / 信息；
  2. 明确回复**暂不能确认该实例级 owner / 信息**。
- **禁止因为上层容器能命中，就把实体降级回容器。**

### 18. 默认容器映射可配置（必须命中）
- 当用户已经在当前工作上下文中**明确声明某个词默认指向特定产品容器**时，后续分类必须优先沿用该约定，除非用户再次显式改口。
- 当前已确认约定：**“气泡”在无特殊说明时，默认指「气泡」这个产品容器**，层级上与 **弹窗、异形卡** 类似；不得再把它默认理解为泛称、样式形态集合或具体业务实例。
- 因此对问法如：
  - “气泡的上线标准是什么”
  - “气泡有什么准入规则”
  - “气泡怎么接入”
  应优先分类为 **TikTok / 产品模块 / 信息查询**（若是在索取既有规则），对象就是**气泡容器本身**。
- 只有当用户额外补充了更长短语、页面限定或业务实例限定（如某页面气泡、某活动气泡、某业务气泡样式）时，才重新判断是否从容器切到更具体对象。

### 19. 术语精确匹配（必须命中）
- 对英文术语、后台字段名、模块名、平台名，默认执行**原词精确匹配**，禁止因为词形相近、历史共现或中文口语混用就自动视为同义词。
- **hashtag ≠ tag**、**topic ≠ hashtag**、**label ≠ tag**；除非权威文档明确写出它们是同一对象的别名，否则必须按不同对象处理。
- 若用户问的是带有明确产品术语的对象（如 hashtag module、Mint hashtag、publisher hashtag），分类时必须保留原词，不得自行改写成更泛的上位词再路由。
- 若精确术语在当前权威索引中未命中，正确动作是标记为“待确认 / 未命中”，而不是退回到词形最接近的其他模块。

### 19. 系统边界优先于模块相似性（必须命中）
- 出现 **Mint / 后台 / 配置台 / 运营平台 / Admin / Console / CMS / Studio / Creator Center / Publisher tools / C端 / 用户侧** 等系统语境词时，必须先判断用户问的是**哪个系统里的对象**，再判断模块类型。
- **后台模块 ≠ C端产品模块**；即使名称相同或强相关，也不能默认共用 owner、规范或 PM。
- 当问题中同时出现系统语境和模块名时，系统语境优先级更高。例：
  - **Mint 后台 hashtag 模块** → 优先理解为后台/平台模块
  - **C端 hashtag 模块** → 优先理解为用户侧产品模块
- 若当前只命中另一个系统中的同名模块，必须停止对象映射，不能拿另一套系统的 owner 代答。

### 20. 对象一致性校验（分类前置版，必须命中）
- 在进入下游 skill 前，先做一次对象一致性校验：**我当前理解的对象，是否与用户原话在“术语 / 系统 / 层级”三方面完全一致？**
- 三项中任一项不一致，都不得给高置信度：
  1. **术语一致**：hashtag 不能改成 tag，Mint hashtag 不能改成 hashtag tag
  2. **系统一致**：Mint 后台不能改成 C端，Creator tools 不能改成 Feed 容器
  3. **层级一致**：后台模块不能改成底层能力，实例不能改成容器
- 若只拿到“相关对象”而非“同一对象”，必须降为中/低置信度并由 orchestration 追问，或在执行阶段明确回复“暂不能确认”，禁止直接路由成相近对象。
