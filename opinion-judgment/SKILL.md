## Invocation Rule

- 不直接面向用户问题触发。
- 仅接受 `orchestration` 路由调用。
- 需要接收如下上下文：
  - 原始问题
  - 识别意图（意见判断）
  - 识别实体
  - 实体关键词

## 场景判定

进入本 skill 后，先判定用户问题的**场景**：

| 场景 | 判定条件 | 典型问法 |
|------|---------|---------|
| **提供参考** | 用户征求看法、建议、判断，期望参考意见而非正式评审结论 | "你觉得呢？""这样合理吗？""给点建议""评估一下""你怎么看" |
| **给出决策** | 用户提交具体需求/PRD/方案，请求完整评审并给出通过/不通过的决策 | "评审一下这个PRD""review这个需求""帮我评审这个方案" |

判定后进入对应的处理分支。

## 场景一：提供参考

### Entity Routing

优先按问题焦点选择一个主实体类型；若同时涉及多个实体，仅保留一个次实体作为辅助。

- 业务方向
- 专项
- 产品模块
- 指标
- 流程
- 需求
- 系统消息
- 问题反馈
- 其他（待补充）

### 1) 需求

- **需求的提供参考不应触发到此分支。如果触发了，先确认用户是否需要正式评审（给出决策场景）；若确认不是，提示用户联系主架构人工确认**

### 2) 系统消息

- **系统消息的提供参考不应触发到此分支。如果触发了，先确认用户是否需要正式评审（给出决策场景）；若确认不是，提示用户联系系统消息审核负责人人工确认**

### 3) 所有其他实体

- 正常基于 context 回复用户即可
- **主架构立场优先级规则（高优先级，必须先判断）**：当问题涉及上线形态、模块组合、用户体验路径、实验形态是否可调整时，判断优先级必须是：
  1. **是否偏离原先约定好的产品方案**
  2. **是否改变原先约定好的用户体验**
  3. 实验效率、拿数速度、流量大小、试错成本
- **资源不足不构成改方案的充分理由**：如果用户提出“因为人力不足 / 资源未就绪 / 排期来不及 / 依赖方尚未适配，所以先降配、改单模块、改展示形态、改实验方案”，必须先判断该变化是否实质上改变了既定方案或既定体验。若答案是“会改变”，则默认**不支持**，不能因为流量小、风险低、可以先拿数据，就转而支持。
- **‘实验 / 试点 / 预实验 / 过渡方案’不自动中和方案偏差**：不能因为是小流量实验或临时过渡，就默认允许对既定方案做降配替代。只有当用户明确说明“该阶段形态本来就是方案中正式约定的一部分 / 已被正式认可为阶段性方案”时，才可按可支持方向继续判断。
- **对这类问题的默认答题框架**：先回答“是否支持”，再给出判断依据；若不支持，核心理由优先写“不能因资源问题改变既定产品方案 / 用户体验”，不要先从‘流量小、可先拿数、风险可控’展开。

## 场景二：给出决策

### Entity Routing

### 1) 需求

- 调用 `requirement-review` skill 执行完整评审流程
- 读取 `/skills/requirement-review/SKILL.md` 并按其指引执行
- 向 `requirement-review` 传递以下上下文：
  - 原始问题
  - 识别意图（意见判断 / 给出决策）
  - 识别实体及实体关键词
  - PRD 主文档链接或用户提供的 PRD 文本
  - 交互设计稿图片或链接（如用户提供）

### 2) 系统消息

- 调用 `system-message-review` skill 执行完整评审流程
- 读取 `/skills/system-message-review/SKILL.md` 并按其指引执行
- 向 `system-message-review` 传递以下上下文：
  - 原始问题
  - 识别意图（意见判断 / 给出决策）
  - 识别实体及实体关键词
  - 待审核的系统消息工单内容（文案、发送原因、目标人群、触发逻辑、Channel-Category 等字段）
  - 业务方提供的 PRD / 合规工单链接或文本（如用户提供）

### 3) 其他实体

- 基于 context 给出判断和结论
